# Rust port of smb1client

Status: Approved
Design date: 2026-08-20

## Problem

The operator maintains `github.com/macourteau/smb1client`, a pure-Go SMB1/CIFS
client library used to talk to legacy file servers that speak nothing newer;
every `file:line` citation in this document is into that repository at commit
`b948f59` (`b948f59ffec56d02ec206f5f184cae3d1f43150b`), and every line number
in them will drift from any later commit. That repository holds root-level and
`internal/` files of the same name, so a citation is written out in full
wherever a bare name would collide: a bare `file.go` or `session.go` is the
root-level file, and its `internal/client` twin is always given as
`internal/client/file.go` or `internal/client/session.go`. New
tools are being written in Rust and must reach those same servers. No pure-Rust
SMB1 client exists: the canonical Rust SMB crate (`smb`, the smb-rs family)
implements SMB2/SMB3 only, and the most-downloaded alternative (`pavao`) is a
GPLv3 FFI wrapper around libsmbclient. So the Go library is ported.

**Who this is for.** The operator's own Rust tools, which must interface with
SMB1-only servers. The crate is named `smb1client`, matching the Go module, and
**publishing it to crates.io is the operator's decision to make and has not been
made** (see Deferred and out of scope). It is not chasing a wide audience in any
case, and its scope is set by what those tools need — not by what a
general-purpose SMB1 library might offer. Nothing else in this design turns on
the answer: the crate is written as a publishable one throughout — dual-licensed,
with the fixtures its tests need inside the package — so that publishing stays a
decision rather than a project.

**The library must self-maintain.** SMB1 is frozen and deprecated; the protocol
will not change. What will change is the Rust ecosystem around the crate, so the
design is judged partly on how little attention it demands after it works: few
dependencies, automated updates, and no reliance on fast-moving pre-1.0 crates.

**Correctness outranks fidelity to the Go original.** Where the evidence
campaign found the Go library mishandling an edge case — and it found several —
the port does the right thing instead. Guiding principle 1 states the rule in
full.

## Technical Plan

### Guiding principles

These bind every decision below. Where a later section appears to conflict with
one, the principle wins and the section is wrong.

1. **Correctness outranks fidelity to the Go original.** Where the Go library is
   known-good it is the reference implementation and the differential-testing
   oracle; where the evidence campaign found it wrong, the port does the right
   thing and the Go defect is recorded in a git-excluded note in the Go
   repository rather than reproduced. Acceptance Criteria enumerates the
   behaviours the test suite must contradict.
2. **Idiomatic Rust outranks faithful translation.** The crate will be
   maintained by someone whose expertise is not Rust, so code that reads as
   ordinary Rust to any Rust programmer is worth more than code that mirrors the
   Go source's shape. Where the two conflict, idiom wins.
3. **Prefer the conventional answer; do not over-design.** The goal is a
   userspace SMB1 client that behaves like an ordinary Rust library, not a
   maximally general one. Where a question has a settled convention, the
   convention is the answer and the question is not reopened. This principle
   does not extend to protocol correctness or to the defect classes recorded
   below: those are decided on evidence, because no convention speaks to them.

4. **Established dependencies are preferred to hand-rolled equivalents.**
   "Established" is load-bearing: it means a stable major version with a calm
   release history, not merely a popular crate. This is why tokio is acceptable
   and the smb-rs leaf crates are not — pre-1.0 with eight breaking minors in
   2025 is a standing maintenance subscription, and the self-maintenance
   priority is what rejects it.

### Runtime model

**The crate is async-only, on tokio.**

SMB1 is a multiplexed protocol: requests carry a 16-bit multiplex ID (MID) and
responses return out of order, so something must read frames continuously and
route each to whichever caller is waiting on that MID. In Go that is a goroutine
and a MID-keyed map of channels. In Rust the direct equivalent is a spawned
tokio task feeding per-request oneshot channels, and cancellation is expressed
by dropping a future rather than by threading a cancellation token through every
call.

Chosen because the consuming programs are predominantly long-running servers,
which are async in Rust as a matter of course; because tokio has been 1.x since
December 2020 with no breaking release since, so it costs almost no ongoing
attention despite its size; and because an async network crate is what the
ecosystem expects, which principle 2 makes decisive.

The cost is accepted knowingly: tokio is a far larger dependency tree than the
Go original's two dependencies, and a synchronous caller must either adopt a
runtime or block on the futures itself.

### Connection architecture

**The connection is an actor.** One tokio task owns the TCP stream and the
table of requests outright. Nothing about the connection is shared, so there is
no mutex anywhere in the transport. Callers hold a cheap handle that sends the
task a request together with somewhere to put the reply, and await the answer.

This is chosen over the direct translation of Go's structure — a reader
goroutine plus a mutex-protected MID-keyed map — because it addresses three
known defect classes rather than carrying them forward as things to remember:
partial transactions and silent response loss become unrepresentable, and
admission control is enforced centrally rather than left to each call site. It
is also the message-passing ownership idiom a Rust programmer expects here.

**The handshake completes before the actor takes ownership of the stream.**
Negotiate and session setup run on the freshly dialled socket, and what the
actor is handed is an already-negotiated, already-authenticated connection.
Three consequences follow, and they are why the order is fixed rather than left
to the implementer: the handshake is bounded by the connect timeout, not by the
per-request timeout, because there is no request table yet to time anything out
in; it consumes no multiplex ID, so the pool and the admission limit describe
only requests a caller asked for; and the negotiated parameters reach the actor
as values it is constructed with rather than as state it must observe, which is
exactly what makes them injectable for the test seam (see What fixtures cannot
prove, and what covers it). Build order step 3 wires the two together in that
order.

#### The request table

**Every request the connection issues is in exactly one state**, and the actor
owns one table of them. Capacity and multiplex-ID identity are facets of a
request's state rather than resources managed beside it, so there is one place
that answers "how many requests are outstanding" and "which IDs are taken", and
no way for the two answers to disagree. SMB1 contributes exactly one
complication here: there is no way to cancel an outstanding request, so a
request can be finished for the client and still running at the server. That
forces one state, **Orphaned**. A second, **Lapsed**, is this design's own
policy rather than the protocol's — the client eventually stops charging
capacity for a request the server has not answered, because otherwise a server
that goes on answering other requests while never finishing this one would spend
the connection's capacity on requests that will never complete. The wholly
silent server is not what Lapsed is for: it is failed and evicted after one
overall deadline of silence (see Connection caching and reconnection).

| State | Meaning | Charges capacity | Holds a multiplex ID |
|---|---|---|---|
| **Queued** | admitted to the actor, not yet on the wire | no | no |
| **Live** | on the wire, a caller is waiting | yes | yes |
| **Orphaned** | on the wire, no caller is waiting | yes | yes |
| **Lapsed** | the client no longer charges capacity, but the server may still answer | no | yes |
| **Done** | finished | no | no |

Four things can befall a request from outside. The table below is exhaustive
over those four events and nothing else: it gives the twelve live cells, and the
four it leaves blank cannot occur. Dispatch is the transition the actor makes
on its own, and it has two targets rather than one. A request whose caller is
waiting goes Queued → Live. A request with no caller at all — a close enqueued
by `Drop`, which has nobody to return to — goes **Queued → Orphaned**,
dispatched already orphaned, and its reply is logged there like any other reply
nobody is waiting on. Capacity below gives the condition, and it is the same
for both.

| From | a message arrives | caller drops | timeout or deadline | connection dies |
|---|---|---|---|---|
| **Queued** | — | Done | — | Done, error to caller |
| **Live** | a continuation is held for reassembly and the request stays Live; on completion, deliver to the waiter, Done | Orphaned | error to caller, Lapsed | Done, error to caller |
| **Orphaned** | a continuation is held for reassembly and the request stays Orphaned; on completion, apply whatever the caller arranged to outlive it, log, Done | — | Lapsed | Done |
| **Lapsed** | the message reaches the request, which has no buffer to reassemble into, so its bytes are dropped there and the request stays Lapsed; on completion, log, Done; on a protocol error, log, Done — what becomes of the multiplex ID in each case is the general rule (see Identity) | — | given up after eight overall deadlines: Done, and the multiplex ID is retired rather than returned | Done |

Two of the columns need a word. The first event is **a message arriving, not a
transaction completing**: a multi-message TRANS2 reply is several arrivals, and
the arrival that ends a request is the one that completes the reply — the last
fragment of the declared totals, or a complete response arriving in their place —
or the one that corrupts it (see Routing and reassembly). **Whether the reply
arrived whole** is what decides whether that request's multiplex ID returns to
the pool or is retired, in every row alike, and a complete reply of any status
returns it, an error status as much as a success (see Identity). Every one of those
arrivals resets the per-request clock of a request in Live or Orphaned, which
measures silence and not elapsed work (see Frames that are not replies); in
Lapsed nothing is reset, as the give-up below sets out. And Queued has no
timeout cell because **the
per-request clock starts at dispatch**: time spent waiting for capacity does not
consume it, so a caller behind a slow server on a serial connection is held by
the backpressure Flow control describes rather than failed by a timeout that
never reached the wire.

Five of those transitions turn on a reason the state names do not carry, and
those reasons are the design:

- **Live → Orphaned when the caller drops.** Dropping a future withdraws
  nothing from the wire; the server still owes a reply, and until it arrives the
  request is as outstanding as any other and is charged as one. Ceasing to
  charge for it at the drop would put requests the server is still working on
  over the negotiated ceiling with no bound at all, and would leave invariant 3's
  test with no defined pass condition, since "outstanding" would be the term in
  dispute. Detection is lazy: the actor learns the caller has gone when it tries
  to deliver, not the moment the receiver drops. Nothing turns on noticing
  sooner, because Live and Orphaned charge capacity alike and hold the same
  multiplex ID; what laziness changes is only when the transition becomes
  observable, so a test that asserts it drives the request to delivery rather
  than watching the table after a drop.
- **Live or Orphaned → Lapsed on a timeout.** A timeout is not proof the server
  finished. It is a client-side policy decision to stop charging capacity, and
  it is what lets a server that leaves particular requests unfinished — while
  answering everything else, so the connection never falls silent — degrade
  throughput rather than wedge the connection permanently: the cost is bounded
  at the admission limit multiplied by the timeout, after which throughput
  recovers on its own, with no operator action and without restarting the
  consuming process.
  Lapsing is logged. The timeout is the per-request one, which every message
  reaching the request resets, or the overall deadline that bounds those resets
  (see Frames that are not replies). A connection that has fallen silent
  altogether never gets this far: it is failed and evicted (see Connection
  caching and reconnection).
- **Lapsed → Done returns the multiplex ID, and only a complete reply gets it
  there.** A Lapsed request holds no reassembly buffer — the buffer goes when a
  request leaves Live or Orphaned (see Routing and reassembly) — so it cannot
  reassemble a continuation: it drops each message's bytes while still tracking
  coverage of the declared totals, and stays Lapsed until its reply has arrived
  whole — those totals covered, or a complete response arriving in their place.
  That is what keeps the ID reserved for exactly as long as the server
  may still be sending. Returning it on the first continuation instead would
  release the ID mid-reply, and the messages still to come would either fail the
  connection as unroutable or land on whichever new request had been handed the
  recycled ID — precisely the crosstalk Identity exists to foreclose, reached
  through this table. The *complete* late reply is the proof Identity requires,
  so the ID is safe to reuse then; retiring it for the life of the connection
  instead would spend the retirement budget below on the one case that proves
  the ID is safe to reuse. The two reassembly guards go with the
  buffer: a request with nothing to reassemble into cannot fail a reassembly, so
  neither the fragment cap nor the empty-message tolerance applies in Lapsed,
  and what bounds a server dribbling messages at a request nobody waits on is
  the give-up below rather than a count. What the coverage tracking can still
  catch is a protocol error — totals revised upward, a fragment outside the
  declared range, a fragment overlapping bytes already covered, or more returned
  than the request asked for (see Routing and reassembly) — and that ends the
  request the way a give-up does rather than the
  way a complete reply does: there is no waiter to fail, so it is logged, the
  request goes Done, and its multiplex ID is retired rather than returned, which
  is what a corrupting arrival does from any state (see Identity).
- **Lapsed → Done when the reply never comes, and the multiplex ID is retired
  rather than returned.** A request that has been Lapsed for **eight overall
  deadlines** without its reply arriving whole is given up on: it goes
  Done, and its ID is withheld from the pool for the life of the connection.
  The server may still answer, and the whole point of Lapsed is that an
  unanswered request's ID is unsafe to reuse, so there is nothing to be learned
  by waiting longer and nothing safe to do with the ID.
  **That clock runs from the lapse and nothing resets it**: a message arriving
  at a Lapsed request advances the coverage it is still tracking and buys no
  more time. Were it to reset, a server dribbling messages at a request nobody
  waits on would hold the ID for as long as it cared to, and this bound and the
  retirement budget below would both be unreachable. That bounds how long any
  one request sits Lapsed; a second bound covers the server that keeps producing
  them, since retiring IDs consumes the pool: the connection fails once
  **1,024 IDs have been retired**, by this route or by an arrival that ended a
  request without completing it, in any state — a sixty-fourth of the ID space.
  That bound does two jobs, because a retired ID is remembered rather than
  forgotten (see Identity): it caps what the pool loses, and it caps the memory
  the table spends remembering retired IDs so that a late frame on one can be
  recognised and logged instead of killing the connection.
  Both this bound and the give-up above are reachable only against a server that
  answers *something* inside every silence window while never completing
  particular requests; one that answers nothing at all is failed by the silence
  rule long before either matters. A server doing
  the first is one this client should stop talking to. Failing is the ordinary
  teardown, so the cache re-dials on the next call (see Connection caching and
  reconnection).
- **Orphaned → Done applies whatever the caller arranged to outlive it.** A
  cancelled write's chunks record their acknowledged ranges on the caller's
  progress handle from here, and leave its chunk group (see Cancelling a
  write). That is a reply reaching its request, not a discard, which is why
  invariant 2 names only one exception.

**Capacity.** Admission is one act, not two. A request leaves Queued — for Live,
or for Orphaned if it never had a caller — only while `|Live| + |Orphaned|` is
below the connection's admission limit, which is
`min(negotiated MaxMpxCount, 50)`. A server reporting a
`MaxMpxCount` of 0 or 1 is saying under [MS-CIFS] that it does not multiplex, so
its admission limit is **1** and the connection is serial. Reading the 0 as Go's
`maxPipeline` of 30 instead was considered and rejected: it is not an inherited
behaviour at all, because `supportsPipelining := maxMpxCount > 1`
(`internal/client/file.go:196,638`) gates entry to the pipelined paths, which
leaves the Go client serial against exactly these servers and the 30 inside
those paths unreachable there. The number is not unreachable everywhere:
`capabilities.go:60-67` derives it — under the name `effectiveDepth`, the name
`maxPipeline` belonging to `internal/client/file.go:284-291` and `:707-714`
where the same ladder is computed for a call — and `capabilities.go:76-77`
reports it publicly, so a server reporting `MaxMpxCount = 0` is told
`EffectivePipelineDepth: 30` beside `SupportsPipelining: false`. That pairing is
the 0 case alone — at 1 the reported depth is 1. What is dead is
the behaviour, not every mention of the constant, and the conclusion is the
same. Relocating that number to a connection-wide admission limit would make the
port thirty times more concurrent than the library it
ports, against the servers least able to cope. The 50 is the Go library's
inherited pipeline depth cap, and it survives here only as a ceiling on the
negotiated value; its job is to bound reassembly memory, since a request holding
a reassembly buffer is a request charging capacity. Go instead allows all 65,536
MIDs to be outstanding and relies on each call site limiting its own pipelining,
which is safe only because goroutines are spawned per call; under an async
runtime, where a consumer may cheaply spawn thousands of concurrent tasks,
aggregate outstanding requests would otherwise exceed what the server
negotiated. The derivation lives here and nowhere else; other sections cite the
limit rather than re-deriving it.

**Lapsing is the one place the design knowingly leaves more outstanding at the
server than it negotiated.**
The client stops charging capacity for a Lapsed request while the server may
still be working on it, so what the server has outstanding can exceed the
`MaxMpxCount` it negotiated — by the rate at which requests lapse multiplied by
the timeout, which is the bound invariant 3 states. Against a server that
enforces the limit, that excess arrives as a rejection, and **the port cannot
tell that rejection from an oversized transaction**: Windows returns
`STATUS_INSUFF_SERVER_RESOURCES` for both, with nothing beside it to separate
them, and that status is already mapped to the oversized-transaction error (see
Sizing transactions). The port keeps that reading rather than inventing a
second, because it is the one the campaign measured and the one a caller can act
on. What it costs is stated here so nobody spends the time twice: a rejection
earned by lapsing surfaces as a transaction-size error naming the wrong likely
cause, on a connection that is in fact holding too many requests at the server.
That one request fails, and there is no special recovery state to enter — though
where the rejection answered a `READ_ANDX` or `WRITE_ANDX` rather than a
transaction it leaves a lasting mark all the same, downgrading the connection's
chunk size for the rest of its life (see Sizing transactions). The
Lapsed set drains on its own, each late reply that completes ending its request
and one that never comes being given up on at eight overall deadlines, so a
connection that meets the rejection keeps every other request it holds and goes
on dispatching without operator action.

**Identity.** A multiplex ID is assigned on entry to Live and held through
Orphaned and Lapsed. **What decides whether it comes back is the arrival that
ended the request, not the state the request ended from**: only an arrival that
completes the reply returns the ID to the pool on Done, while an arrival that
ends the request any other way retires it for the life of the connection
instead. There are two such ways and they differ in reach: a protocol error in
the reassembly can end a request from Live, Orphaned and Lapsed alike, since
coverage is tracked in all three, while either reassembly guard tripping (see
Routing and reassembly) can only end one holding a reassembly buffer, which is
to say one in Live or Orphaned. A complete
reply is proof the server is finished with that ID, which is the only thing that
makes it safe to reuse; a server that sent a malformed reassembly, or one it
never finished, has demonstrated nothing of the kind and may still be sending
against that ID. A Lapsed request given up on retires its ID for that same
reason (the give-up above). That is what forecloses crosstalk: a server
answering a request the client abandoned or lapsed meets that same request,
never a different one that has been handed the same ID in the meantime.

**A retired ID is remembered, not forgotten.** Retirement takes an ID out of the
pool of IDs that may be *issued*; it does not take it out of the request table's
memory, which keeps every retired ID with enough state to recognise it. So a
frame arriving on a retired ID does not route to nothing: it routes to a retired
entry, is logged at debug with the ID and the command, and is discarded, and the
connection carries on. That is what makes the rules written around a server that
goes on sending true as stated — a corrupted reassembly failing one request and
not the connection, the two reassembly guards, and a Lapsed request given up on
at eight overall deadlines while the server may still answer. Retirement is a
property of the identity and not another row in the table above: the request
itself reached Done when its ID was retired, and nothing about it is
outstanding.

The pool
is 65,535 IDs rather than 65,536: `0xFFFF` is never allocated, because [MS-CIFS]
reserves it for server-initiated oplock-break notifications. Go allocates it — `allocateMID` (`internal/client/conn.go:140-155`) hands out every 16-bit value in turn, skipping only IDs currently pending — and what this design declines to inherit is the `0xFFFF` specifically: that value is never issued, while the order in which the remaining 65,535 are handed out is the implementer's and is not specified here. The pool is
exhausted only when all 65,535 are held at once — essentially all of them
Lapsed, since Live and Orphaned together never exceed the admission limit — so
what exhausts it is what is held at one moment and not lapses counted
cumulatively over the connection's life: a lapse whose reply does complete gives
its ID back and counts against nothing. The one cumulative count is of retired
IDs, and it is the bound a server that accepts requests and answers none meets:
it fails the connection at 1,024, without the pool having to run out. Both
counts are connection-fatal: the
connection is torn down, and the cache re-dials on the next call.

#### The actor loop

The actor is one `select` over five sources: inbound frames from the socket, the
request channel, the close channel, the timer that expires timeouts and
deadlines, and the socket write currently in progress. Every arrival on the
first four is a transition in the table above and nothing else, which is what
keeps the request states from being reimplemented per call site. The closes
`Drop` enqueues arrive on their own channel (see Handle lifetime), and the
priority below is the only bias in the `select`: among the other four sources
it takes whichever is ready, in no fixed order.

**The close channel is polled with priority, and at most eight closes in a
row.** The `select` is biased: whenever the actor is in a position to admit
anything it takes a waiting close before a waiting request, capacity having just
freed or not. That is what puts a dropped handle's close on the wire ahead of
whatever the caller does next: closes and requests arrive on two different
channels, an unbiased `select` between two ready channels chooses arbitrarily,
and a rule that only ordered them when capacity freed would order nothing in the
ordinary case, where no such event happens at all. It settles send order only
— Handle lifetime says where that is enough and where the operation must await
the close reply instead.

A `Drop`-issued close is otherwise an ordinary request: from dispatch it is in
the table, charging capacity and unable to go on the wire over the limit, so a
burst of dropped handles cannot put more requests on the wire than the server
agreed to.
All that differs is where dispatch puts it, which The request table settles.
Until dispatch it waits in its own channel and not in Queued, by the same rule
that governs requests — Queued holds only what the actor has taken and not yet
put on the wire (see Flow control). So an open-and-drop loop's memory sits in
the unbounded close channel and nowhere else, a close waiting for capacity
blocks no inbound frame, and ordering survives the wait: a request issued after
the close needs capacity too, and the priority above hands the close that
capacity first.

**The eight is what stops closes starving requests.** The close queue is
bounded in memory (see Handle lifetime) and would otherwise be unbounded in its
share of capacity: a task dropping handles in a loop keeps the queue non-empty,
and a loop rule that drained it first without limit would hold every other
task's requests off the wire indefinitely. After eight consecutive closes the
actor admits a request whatever is still queued behind them. The ordering the
rule exists for survives that: a caller's close and the operation it issues next
still reach the wire in that order unless eight other closes are already queued
ahead of the close, which is a burst of dropped handles rather than the
drop-then-operate case — and where the ordering must hold regardless, the
operation awaits the close reply instead (see Handle lifetime).

**A blocked socket write never stops the actor reading replies or firing
timers.** Dispatching means putting bytes on the socket, and a peer whose
receive window has closed can block that write indefinitely — reachable at an
admission limit of 50 against 130 KB replies, and the operator's targets include
single-board computers. An actor that ran the write to completion inside its
dispatch branch would stop reading inbound frames while blocked; the server's
send buffer would then fill, the server would stop reading requests, and the
write would never complete. The timer is in the same `select`, so timeouts, the
overall deadline and the connection-silence rule would stop firing too, and
nothing would break the deadlock. The write in progress is therefore a source of
the `select` in its own right, driven alongside the inbound stream and the timer
rather than awaited inside a branch: a write that cannot proceed leaves the
actor free to read replies, complete requests and expire timeouts, which is what
drains the peer's buffer and releases it.

**Dispatch commits at the first byte written.** Once any byte of a request's
frame has reached the socket the request is on the wire and the actor finishes
the frame, whatever its caller does or the clock says: a caller dropping
mid-write moves the request to Orphaned like any other drop (see The request
table) and does not abandon a half-written message. The per-request clock starts
at that first byte too, so against a peer whose receive window has closed a
request can lapse while its own frame is still going out. That changes what the
request is charged, not what the socket does — the actor finishes the frame and
the request sits Lapsed holding its multiplex ID, exactly as it would have had
the whole frame gone out before the timeout. Abandoning one would leave the
stream desynchronised, with the server reading the tail of a message it has no
header for — a failure that surfaces arbitrarily far from its cause.

**Accepted cost: head-of-line blocking on dispatch.** One task owning the socket
means requests reach the wire one at a time, so a large write is briefly ahead of
whatever is queued behind it. That is a latency cost and it is accepted: a single
TCP connection carrying framed SMB1 messages serializes them regardless, and
these are legacy servers on a local network, so the simplicity is worth more than
the interleaving that separate read and write tasks would buy. What is not
accepted is deadlock, which the rule above designs out — behind a stalled write
the queue waits, but replies, timeouts and the connection-silence rule keep
running.

#### Routing and reassembly

**The unit of routing is a completed transaction, not a frame.** A server may
answer one TRANS2/TRANSACTION request with several messages that all repeat the
request's MID, each declaring the whole reply's `TotalParameterCount` and
`TotalDataCount` and carrying its own bytes at `ParameterDisplacement` and
`DataDisplacement`. Because the connection task owns reassembly, it holds those
fragments until the declared parameter and data ranges are completely covered,
and only then delivers a single reply. Completeness is coverage of each range,
not a running sum of the bytes received: a sum is satisfied by fragments that
overlap at one displacement and leave a hole at another, which delivers a reply
with zero-filled bytes in the middle of it — the silent corruption invariant 1
exists to forbid, arriving through the check meant to prevent it. A caller has
no way to receive a partial transaction, so it cannot mistake one for a whole
one. Coverage rather than a sum is reasoning rather than a measured repair: the
current Go code accumulates by byte count with placement by displacement
(`internal/client/conn.go:304`), so the weakness is live there, but no server in
this campaign produced overlapping fragments and no captured fixture exercises
the case, so what exercises it is a hand-built sequence through the test seam
(see Invariants). Designing it out costs nothing over guarding against it. The
Go defect that silently enumerated a 285-entry directory as 213 was a different
one, since fixed (see Acceptance Criteria).

**The latest message's totals govern, and they may only shrink.** Every message
repeats `TotalParameterCount` and `TotalDataCount`, and coverage is judged
against the pair the latest message declared: a server revising them downward
mid-stream is conforming and is honoured. **Upward and downward are measured
against the current declaration**, never against the largest the server ever
declared — totals of 1000, then 500, then 800 revise upward at the 800 and fail
the request as a protocol error (below), the 1000 being no longer anything the
reassembly holds. Honouring it truncates: bytes already
accepted that a reduced total puts outside the declared range are discarded with
the range, and completeness is judged over what is left, because what reaches
the caller has to be the reply the server last said it was sending. An error
status arriving mid-reassembly is not a fragment but a complete response: it is
delivered to the waiter as the reply and the partial buffer is discarded, rather
than held against totals the server has stopped intending to satisfy.

**One status is classified before that branch and is neither fragment nor
error.** `STATUS_PENDING` is an interim response (see Frames that are not
replies): it contributes no bytes, leaves the reassembly exactly where it is,
and is excluded from the contribution-free message count — counting it would
fail a legitimate reassembly on the second interim, which is a slow server
saying it is still working. Everything else divides into fragment, complete
response and error as above, and `STATUS_BUFFER_OVERFLOW` is not an exception:
on a `TRANS_TRANSACT_NMPIPE` reply it is a *completed* `SMB_COM_TRANSACTION`
whose pipe payload was truncated, so it is delivered as the reply and the
remedy is another pipe read one layer up (see Wire layer). Holding it against
the declared totals as a continuation would wait for messages the server will
never send, and the request would lapse.

**A reassembly the server corrupts fails the request, not the connection.**
Revising the declared totals upward — above the pair the latest message declared,
which is the only comparand — sending a fragment whose bytes fall outside the
range currently declared, sending a fragment that re-covers any byte the coverage
map already holds, and returning more than the request's own
`MaxParameterCount` and `MaxDataCount` allowed (below) are each a protocol
error, and each is scoped the same way: the partial buffer is discarded, the
request fails, its multiplex ID is retired rather than returned to the pool (see
Identity), and the connection carries on. The overlap is an error rather than
something absorbed: unioning the coverage and taking the fragment in silently
would leave a server contradicting itself about its own reply's bytes
unreported, which is the class of silent acceptance invariant 2 exists to
forbid. Any of them corrupts one
reassembly and says nothing about the framing, unlike the three conditions that
fail the connection instead — a frame that routes to no request at all, which a
later frame on that retired ID is not, since the table remembers retired IDs and
logs such a frame rather than failing anything (see The request table); a
NetBIOS message type the port does not recognise; and a response that chains
another command — after any of which the actor cannot trust where the next message
begins (see Frames that are not replies). What failing the request means at a
Lapsed one, which has no waiter to fail, is decided with that row (see The
request table).

**Reassembly has two termination guards**: a cap of **64 fragments** accepted
for one reply, and a tolerance of **one message that contributes no bytes**,
after which the reassembly fails — the request and not the connection, as above.
**`STATUS_PENDING` counts against neither**, for the reason already given where
it is excluded from the contribution-free count above: it is the server saying
it is still working, so counting it would fail a legitimate reassembly — on the
second interim at the tolerance, on the sixty-fifth at the cap.
Both are liveness guards against a server that
never signals completion, not quantities derived from the request size —
neither threshold follows from `MaxDataCount` or from the transaction ceiling.
Both are Go's values, carried rather than derived: `maxTrans2Fragments = 64`
(`internal/client/conn.go:39`) and the `emptyFragments > 1` check beside it
(`conn.go:311-312`). The cap is deliberately far above what any observed server
needs, because nothing in the evidence forbids a server splitting a reply more
finely than the servers observed splitting do — and both of those are
Samba-family, so what was observed is one implementation's habit — while a cap
tight enough to reflect it would hard-fail any server that splits more finely.
The empty-fragment tolerance does the real work of terminating a server that never
finishes: a server that keeps sending is stopped by the second contribution-free
message rather than by the 64th fragment.

**Reassembly is memory-bounded by what the request asked for.** The declared
`TotalParameterCount` and `TotalDataCount` are server-supplied numbers, so
sizing a buffer from them hands the server the allocation decision. The bound
comes from the client side instead: the `MaxParameterCount` and `MaxDataCount`
the request itself sent, which a conforming server may not exceed. The partial
buffer belongs to the request — it is part of that request's row in the table,
not a structure of its own keyed by MID — so the connection-wide bound is that
per-transaction bound multiplied by the admission limit: only a request charging
capacity can hold a buffer, and the buffer goes when the request leaves Live or
Orphaned (see The request table). That is both tighter than the 16-bit totals a
server is free to declare and more diagnostic when it trips — a reply exceeding
it is a server returning more than it was asked for, which fails that request as
a nameable protocol error (above) rather than tripping an anonymous memory
ceiling. The bound is enforced explicitly rather than trusted.

#### Flow control

**Nothing is dropped, and admission is what applies the backpressure.**
Delivery to a waiter is a oneshot. The unit of routing is a completed
transaction, so there is exactly one reply per request: a oneshot can neither
overflow nor block, and Go's receive loop discarding a response when the
waiter's queue is full has no equivalent here because there is no queue to
fill. What limits how much a consumer can have in flight is capacity, and it
reaches the caller through the request channel: while `|Live| + |Orphaned|` is
at the admission limit **the actor stops draining that channel at all**, so
requests accumulate in the bounded channel rather than in Queued, that bound is
the client-side memory bound, and a caller whose send finds the channel full
waits there. **The channel's bound is the admission limit itself** — derived
from it rather than configured beside it, so the two cannot be tuned into
contradiction. Two things follow and are worth naming: a caller blocks once
roughly twice the admission limit is outstanding between the wire and the
queue — the limit's worth on the wire and the limit's worth waiting behind
it — and the client-side memory that bound describes is that many requests'
encoded bytes. Draining into
a Queued set that waits for capacity instead would leave the bound unapplied and
make Queued unbounded; as it is, **Queued holds at most one request** — the one
the actor has taken from the channel and is writing, which becomes Live, or
Orphaned, at the first byte on the socket (see The actor loop). The close
channel is exempt and unbounded, and carries only the closes `Drop` enqueues,
because `Drop` cannot await (see Handle lifetime). The
actor deliberately never awaits a consumer: one reader awaiting room in one
waiter's channel would stall every other multiplex ID behind it, and would
deadlock any consumer that holds one reply while awaiting another.

**The client advertises the number it enforces.** The `MaxMpxCount` in the
client's own session setup carries that same admission limit, as The request
table derives it, so what the server is told to expect is exactly what
invariant 3 holds the client to. Go echoes the server's value back
verbatim (`internal/client/session.go:75,137`), which on every tested server is
the same number, since all three negotiate 50 and the ceiling is 50.

#### Frames that are not replies

**Not every frame answers a waiting caller**, and the actor has an explicit
outcome for each frame that does not. Three of those outcomes fail the
connection rather than one request, and all three are stated here — including
the last below, which is a reply rather than a frame that answers nobody — so
that the connection-fatal *frame* conditions are in one place — not the whole of
what fails a connection: the retirement bound and the exhaustion of the
multiplex-ID pool (see The request table), and the silence rule and
`STATUS_USER_SESSION_DELETED` (see Connection caching and reconnection), do so
as well, and the handshake's four refusals fail the dial before the actor takes
the stream at all (see Security posture):

- **NetBIOS session keep-alives** (message type `0x85`) are transport-level, not
  SMB messages at all. They are consumed and discarded — the one exception
  invariant 2 names. That branch is unreachable rather than merely unobserved,
  and it is kept as defensive code: the keep-alive belongs to the port-139
  session service and this port is 445-only (see Non-goals). No capture in the
  corpus carries a message type other than `0x00`, on any server. Any other
  type means the peer is doing something wrong, so it fails the connection
  rather than being consumed and logged — reading past a frame the port does
  not understand is how a parser ends up confused about frame boundaries.
- **Replies to abandoned requests.** Dropping a future does not cancel anything
  on the wire: SMB1's `SMB_COM_NT_CANCEL` is declared in the Go source and sent
  nowhere, and the server completes the request regardless. The request
  therefore goes Orphaned rather than away, and it keeps its multiplex ID until
  the reply is complete, or the connection ends it, or the ID is retired — after
  eight overall deadlines without the reply, on a protocol error in what does
  arrive, or on either reassembly guard tripping, which an Orphaned request
  still holding its buffer can do; a timeout in between stops it charging
  capacity but does not free the ID (see The request table). Go frees
  the ID immediately in `sendRecv`, and because MIDs are 16 bits and allocation
  only skips those currently pending, an abandoned request's MID is handed to a
  new request while the old one is still unanswered. The old reply then arrives
  against the new request and is delivered *as its answer*: one file's bytes
  returned for another file's read, with no error. That takes both a wrap of the
  ID space and an abandoned reply still outstanding when the ID comes round —
  the wrap alone is not the collision — and in Go the two halves sit on
  different paths: the pipelined paths, which are what make a wrap reachable
  within a single large transfer, mark the request cancelled and keep its MID
  instead of freeing it. So the collision is narrower there than the freeing
  alone suggests. It is designed out here regardless, because Orphaned is what
  invariant 3's accounting needs in any case, and because a design that lets an
  ID be reused while the server may still answer it has to re-argue every time
  that the two halves cannot meet. Here the late reply reaches the request that
  made it: it applies whatever the caller arranged to outlive the drop, it is
  logged, and a reply that completes gives the ID back.
- **Server-initiated requests** cannot occur, and the reason is worth recording
  because it is what lets an unroutable SMB frame be an error rather than a
  message class the actor is quietly losing: the client sets
  `NT_CREATE_ANDX Flags = 0`, so no oplock is ever granted and no oplock break
  can arrive. A future change that requests an oplock would create a message
  class the actor cannot route, and must add a notification path first.
- **Frames that route to no request fail the connection, and a retired
  multiplex ID is not such a frame.** Every ID this design issues is either held
  by a request in the table or remembered there as retired, so an unroutable
  frame means the
  server sent something the design does not model — a duplicate, or an answer to
  an ID never issued — and carrying on past it risks misrouting the next one. A
  frame on a retired ID is neither: it reaches the retired entry the table
  keeps, is logged at debug with the ID and the command, and is discarded, and
  the connection carries on (see The request table → Identity). That is the case
  a server still sending against a request this client gave up on produces, and
  the design expects it.
  Routing is by multiplex ID, and **the reply's command must match the
  request's** as well: an ID that matches under a command that does not is
  unroutable on the same terms, which is a cheap backstop against the crosstalk
  the ID alone cannot exclude. This is a deliberate behaviour change from the Go
  library, which carries on past such a frame without even logging it —
  `internal/client/conn.go:440-444` is a bare `continue`.
- **A response whose `AndXCommand` is anything but `0xFF` fails the
  connection.** The port chains nothing (see Wire layer), so a chained response
  is the server answering something the port did not ask, and parsing on into
  the chain is how a decoder loses frame boundaries. That no committed frame
  chains is what the corpus shows; whether to tolerate a chain or refuse one was
  a design question the evidence could not settle, and it is settled here.

`STATUS_PENDING` is not an error and not a final reply. It is classified as
success by the Go library's error check, which would deliver an interim response
to the caller as the answer; here it means "keep waiting."

**The per-request timeout measures silence, not elapsed work: any message that
reaches a request still charging capacity resets it, and a bounded overall
deadline caps the resets.**
An interim response and a fragment that contributes bytes are the same rule and
not two — a server streaming a large listing across many messages is answering,
as steadily as one saying it is still working, and lapsing it mid-stream would
throw away every fragment already reassembled along with the request. That is
what keeps a legitimately slow server — the operator's targets include
single-board computers — from being killed mid-operation by a timeout it is
working against. A message that contributes nothing and repeats nothing is
bounded elsewhere: the empty-message tolerance and the fragment cap terminate a
server that keeps sending without progressing (see Routing and reassembly). The
overall deadline is what stops a server that resets the clock indefinitely from
charging capacity forever: expiry of either lapses the request (see The request
table).

### Handle lifetime

Every open file, directory search, tree connection and session holds a handle on
the server, and releasing it is a network round-trip. Rust's `Drop` can be
neither async nor fallible, so it can neither await that round-trip nor report
its failure.

**`close()` consumes the handle**, so using a closed handle is a compile error
rather than a runtime one. On a `File`, on a listing iterator and on the
`Client` itself it is `async` and returns errors, for callers who need to know
that the release succeeded — `Client::close()` awaiting the session's goodbye
before it answers (see Connection caching and reconnection). A
`Tree` is the case that rule does not cover, and it is decided where the cache
is: a tree the cache still holds returns `Ok` having sent nothing (see
Configuration and timeouts). **An awaited `close()` that does go on the wire is
an ordinary request on the bounded request channel**, admitted like any other
and waiting for capacity like any other: everything below that is special
about a close — the unbounded channel, the priority in the actor's `select` —
exists because `Drop` cannot await, which a caller that awaits does not need.
Whichever way it is sent, the `SMB_COM_CLOSE` carries `LastWriteTime = 0`,
matching the reference (`internal/client/file.go:149-152`): the field exists so
that a close can stamp a modification time on the file, and zero tells the
server to leave the time it already has alone. Times are set through
`Tree::set_times` and nowhere else (see Filesystem verbs).

**`Drop` enqueues a best-effort close** and logs failures. It neither spawns a
task nor requires a runtime to be running — it hands the close to the connection
actor over a channel, which is a plain non-blocking operation. Two consequences
follow from routing it through the actor:

- **Send order is guaranteed; completion order is not.** The close is queued
  ahead of whatever the caller does next on that connection, because the actor
  takes a waiting close before a waiting request, short of the run of eight that
  keeps closes from starving requests (see The actor loop). That is send order
  and nothing more: the close reaches the wire first, but the server is working
  on up to the admission limit of requests at once and may still be finishing
  the close when it starts the operation behind it. Dropping a listing iterator
  and then deleting the directory it enumerated is therefore safe only when the
  operation **awaits the close reply**
  rather than merely being dispatched after it, and that is what the operations
  needing the ordering do: `Tree::remove_dir_all` awaits the close of each
  level's listing before it deletes from that level — a level it drained to the
  end has closed itself already, and awaiting that costs a round-trip nobody
  makes (see Directory listing). In the Go library neither
  half is available: a lingering FIND search handle — left open because Go asks
  the server to close only on the FIND_FIRST2, below — made `RemoveAll` on a
  just-listed directory report "permission denied" after already deleting the
  contents, and `maxRemoveRetries = 10` with a 50 ms-to-1 s backoff exists to
  retry around it.
  That retry loop is dropped here because the close is awaited, not because
  dispatch is ordered.
- **`Drop`'s closes travel on their own unbounded channel**, not the bounded
  request channel. `Drop` cannot await, so a bounded channel would force a
  fallible non-blocking send that discards when full — the silent-loss shape
  invariant 2 forbids. Close commands are small, and what bounds the queue is the number of
  handles dropped but not yet dispatched — which an open-and-drop loop can drive
  above the number of handles live at any one moment.

When the connection itself goes away, queued closes are abandoned deliberately:
the server releases every handle on TCP disconnect, so a close only matters
while the connection lives.

**A deliberate teardown says goodbye; a failed one does not.** Ending a
connection the client still believes in — `Client::close()`, an idle eviction,
the last handle on it going away — sends `TREE_DISCONNECT` for each tree it
holds and `LOGOFF_ANDX` for the session before the socket closes, so the server
releases its own state at once rather than on whatever timer it keeps for
abandoned sessions; `Client::close()` awaits those replies before it returns
(see Connection caching and reconnection). A connection being torn down *because* it failed sends
neither: there is nothing left to send them over, and TCP teardown releases
everything the server holds anyway (see Connection caching and reconnection).

**Directory searches are handles too, and nothing in the Go library reliably
closes one.** A `TRANS2_FIND_FIRST2` search occupies a server-side handle until
it is closed. Go never sends `SMB_COM_FIND_CLOSE2` — its encoder exists with no
production caller — and relies on `SMB_FIND_CLOSE_AT_EOS` instead. This design previously
recorded that as safe on the ground that Go drains a directory completely, and
that was measured wrong: Go sets `SMB_FIND_CLOSE_AT_EOS` only on the FIND_FIRST2
(`session.go:883`, `internal/client/file.go:1395`), while every FIND_NEXT2 it
sends carries `SMB_FIND_CONTINUE_FROM_LAST` under the source's own comment
"Continue, but don't auto-close" (`session.go:927`,
`internal/client/file.go:1436`). At a batch
size of 100, every listing longer than 100 entries therefore ends on a request
that never asked the server to close, and draining into a `Vec` closes nothing.
That is very likely the mechanism behind the `RemoveAll`-after-`ReadDir` failure
recorded above as undiagnosed, and the reason `maxRemoveRetries` exists.

**The port closes the search on both paths, and between them they cover every
way a listing ends.** It sets `SMB_FIND_CLOSE_AT_EOS` on the FIND_FIRST2 **and
on every FIND_NEXT2**, so whichever request reaches end-of-stream is the one
that asks the server to close it; and it sends `SMB_COM_FIND_CLOSE2` for the
other ending, a listing dropped before EOS, which lazy listing makes ordinary —
taking the first ten entries and dropping the iterator would otherwise leave the
search open. Setting the flag on a FIND_NEXT2 is spec-legal, and it is also a
wire change no server in the corpus has been observed to accept: every captured
FIND_NEXT2 carries `SMB_FIND_CONTINUE_FROM_LAST` alone, because Go never sets
anything else there. The conformance script carries the check (see Acceptance
Criteria).

The port writes the `SMB_COM_FIND_CLOSE2` encoder rather than translating Go's.
It is a standalone SMB command, `0x34`, not a TRANS2
subcommand, but Go's `EncodeFindClose2` (`internal/smb1/trans2.go:536-537`) is
shaped as a TRANS2 parameter block, and it has no production caller at all: its
only caller anywhere is its own test (`internal/smb1/trans2_test.go:478`).
`session.go:953` records that sending the real thing needs a new command type.
The implementer should treat that encoder as evidence the command was never
sent, not as a reference for sending it.

This qualifies the ordering guarantee above rather than extending it. Routing
closes through the actor, and awaiting the close where the ordering must hold,
makes *drop-then-operate* safe. Neither makes it safe to mutate a directory
while an enumeration over it is still open — entries may be skipped or repeated,
and no two SMB1 servers need agree on which. That is why `Tree::remove_dir_all`
exists and why it collects each level fully, and awaits that level's search
close, before deleting from it, rather than deleting as it walks.

**`remove_dir_all` cannot tell a directory symlink from a directory, and the
limit is stated rather than designed around.** Samba advertises `CAP_UNIX`, so
the shares this crate targets can carry symlinks, and at the info level the
listing uses one pointing at a directory is indistinguishable from a directory.
A recursive delete that descends it therefore leaves the tree it was given and
deletes whatever is on the other side. Nothing available at that info level
distinguishes the two, so a caller who cannot vouch for what a tree contains
should walk it itself rather than call this.

### Cancelling a write

A write larger than one message is split across several requests, pipelined
once it passes the write threshold and issued in turn below it. If the
write stops partway, chunks already on the wire still reach the server. No
write-specific machinery accounts for them: a chunk whose caller has stopped
waiting goes Orphaned like any other such request, and each late reply is
handled in its Orphaned cell (see The request table). Cancelling is therefore
not instantaneous — the requests already on the wire cost the round-trip time of
whatever is outstanding before they leave the table — and that is accepted.

What differs between the two ways a write stops is what can be reported at all.

**The library's own per-request timeout fires** on one of the write's requests.
The write future completes normally, with an error, so it can carry a number:
the error carries `written`. A failing chunk stops the loop issuing, and the
loop then **drains what is already outstanding** rather than returning the
moment the first error arrives: every chunk still on the wire is awaited to a
terminal outcome — its reply, its own lapse, or the connection ending it — so
`written` accounts for every request the call made rather than for whichever
answered first, and those requests reach a terminal state instead of settling
behind the caller's back. The first error is the one reported; whatever the
drain turns up afterwards is logged. This is the same rule for any way a chunk
fails, a bad status as much as a timeout.

**The caller drops the future.** A dropped future yields no value — no count and
no error — so nothing reaches the caller on this path, ever. Callers who need
the number here pass `write_all_at` an optional **`WriteProgress`**: the caller
constructs one, keeps its own clone and passes another to the call, so that the
handle outlives the dropped future and is read afterwards. It is `Clone` over a
shared inner value, and that is forced rather than chosen — ranges are recorded
after the caller's future has been dropped, so a borrow could not outlive it.
**The call therefore takes the handle by value**, `Option<WriteProgress>` and
never `Option<&WriteProgress>`: the whole point of the type is to outlive the
future it was passed to, and a reference is the one shape that cannot. The clone
is what the caller keeps; the clone is cheap, being a shared inner value.
It is not
a bare counter: replies land out of order on a pipelining transport, and a
scalar cannot say which bytes reached the server. The handle carries the
**acknowledged ranges**, and a range is recorded from the reply rather than from
the request: the chunk's offset, and the count the `WRITE_ANDX` response
acknowledges, which may be fewer bytes than the chunk asked to write. Recording
what was requested would overstate what landed, which is the one thing the
prefix exists to get right. The contiguous prefix is computed from those ranges
when the caller reads it, and ranges go on being recorded after the drop, which
is why the prefix can still grow then. A chunk that lapses is different: it
leaves the chunk group at the lapse, and if its reply arrives later that
reply is logged in the Lapsed cell and records nothing. A prefix already
declared final may not grow afterwards — a caller may have resumed from it —
and a rule that turned on whether the signal had fired first would be a race.

**`WriteProgress` carries a completion signal as well as the ranges**,
because without one it is a structure nobody can safely read. `Drop` returns
immediately, so the handle is not final at the drop, and nothing else tells the
caller that the write's own requests have all left the table. So the handle also
carries the chunk group the write registered on it — which requests belong to
this write. **One handle serves one write**, for the handle's whole lifetime and
not merely one write at a time. A `WriteProgress` that already carries a group —
registered by an earlier `write_all_at`, finished or not, or by an
`into_writer()` — is refused a second registration, and the refusal is an `Err`
rather than a panic, this being recoverable caller misuse: a prefix computed
across two writes to different offsets means nothing, and a completion signal
that waits for both answers neither. **`into_writer()` is fallible for that
reason and returns a `Result`**, since it takes the handle exactly as
`write_all_at` does. A caller writing twice constructs two handles. Which
variant of the error enum names the refusal is the implementer's.

**`WriteProgress::completed()` is the async wait for that signal**,
and it returns once the group is empty — once every chunk the write registered
has left it. The group and the request table are not the same thing, and the
signal keys on the group: a reply removes a chunk from the group, so does the
connection dying, and so does a lapse, which removes the chunk at the lapse
while the request itself stays in the table as Lapsed, holding its multiplex ID
until a late reply completes it or it is given up on (see The request table).
Waiting on the table instead would hang `completed()` on exactly the case the
handle exists for. Orphaned has three exits and the signal covers all
three, so a caller awaiting it is never left waiting on a connection that has
gone. **`WriteProgress::written()` reads the contiguous acknowledged prefix**:
before the signal it is a lower bound, after it is final, whatever ended the
write. Resuming a transfer is the whole reason to read
the handle, and resuming from a value that may still be increasing is worse than
not resuming at all.

**`written` is the contiguous acknowledged prefix, and it is a lower bound on
what reached the server**, never the total that landed. If a middle chunk fails
while later ones succeed the two differ, and only the prefix is safe to resume
from: the first `written` bytes are on the server and nothing is claimed beyond
them. Because the loop drains before it returns, `written` covers every chunk
the call issued and does not grow afterwards; a caller that passed a
`WriteProgress` reads the same prefix from `written()` thereafter. That
agreement is a property of
the error path alone. On the drop path there is no loop left to drain, ranges go
on being recorded, and what makes the handle's prefix final is the completion
signal and nothing else — so the two are one number only where the drain has
already made them one. No evidence in the campaign produced a discontiguous
case, so this is a stated rule rather than an observed one.

**Why a cancelled write does not simply return a count.** The Go library cancels
through a context, so its write returns `(n, err)` however it ends, and copying
that shape is the easy mistake: a Rust future cancelled by being dropped has
nowhere to put a return value. Go's count is not worth copying either, being
wrong in both directions — cancelling an 8 MiB write at 20 ms reports `n=0`
while roughly 5 MB landed, and at 40 ms reports 7,412,736 bytes for a write that
had fully completed (measured by `spikes/cancelwrite/`; the cancelled-write
finding under "Findings — post-scout spikes" in
`notes/01-rust-port-spike.md`, cited by section because that trail numbers two
different findings `A2`). A caller cannot distinguish "partial, resume at n"
from
"complete, resume nowhere", so retry logic built on that count double-writes.
The timeout path's `written` and the progress handle are what replace it, and
between them they cover both paths for one optional argument.

### Sizing transactions

**Every TRANS2/TRANSACTION request keeps `MaxParameterCount + MaxDataCount` at
or below 66,524 bytes, and sets `MaxParameterCount` from what the reply actually
returns rather than from a round number.**

This rule was measured, not inferred. Windows 11 24H2 rejects a transaction with
`STATUS_INSUFF_SERVER_RESOURCES` on the sum alone, at exactly the same threshold
regardless of how the sum is split. Five splits were tested, with
`MaxParameterCount` from 1024 to 16384, and every one broke at the same sum; the
full sweep is finding W6 in `notes/01-rust-port-spike.md`. The boundary pair at
the two extremes:

| `MaxParameterCount` | `MaxDataCount` | sum | result |
|---|---|---|---|
| 1024 | 65500 | 66524 | accepted |
| 1024 | 65501 | 66525 | rejected |
| 16384 | 50140 | 66524 | accepted |
| 16384 | 50141 | 66525 | rejected |

66,524 is 65 KiB minus 36 bytes, which is the 4-byte NetBIOS header plus the
32-byte SMB header — a fit rather than a derivation, since the reply also
carries `WordCount`, its words, `ByteCount` and padding, none of which those 36
bytes account for. The measurement is exact; the arithmetic beside it is a guess
at the server's reasoning and nothing rests on it. Samba applies no such limit
and accepts 66,559.

**What was measured is narrower than the rule.** The sweep was TRANS2 FIND
against Windows 11 24H2 and nothing else. Applying the same ceiling to every
TRANS2 subcommand and to `SMB_COM_TRANSACTION` is a deliberate extension of that
measurement, on the reading that the limit is the server's transaction buffer
rather than anything specific to FIND. That extension is untested, and no
committed evidence can settle it: a server that disagrees would surface only
against a live one.

**A server whose ceiling is lower has to be diagnosable, and that is all.**
`STATUS_INSUFF_SERVER_RESOURCES` is mapped to a named error giving an oversized
transaction as the *likely* cause, rather than surfacing as the raw status: the
status text points at server capacity and is what sent this campaign's own
diagnosis in the wrong direction for weeks. Likely and not certain, because a
server genuinely out of resources returns the same status — and so does one
rejecting excess multiplexing, which is indistinguishable from this on the wire
(see The request table) — while an error that asserted the size would mislead
in the other direction just as firmly. The port
does not then retry at a smaller size — automatic retry of a failed operation
is a non-goal (see Non-goals), and a silent second attempt at a different size hides
which size the server actually accepts. Deriving the ceiling per server rather
than hardcoding it, the "no hardcoded maxima" candidate raised in design prep,
is rejected on the same ground: it would mean probing with requests the client
expects to fail, reading the one status this campaign found actively misleading,
to replace a measured number with an inferred one.

The consequences matter more than the number.

**The negotiated `MaxBufferSize` is not the ceiling and must not be used as
one.** Windows advertises 4,356 and then accepts a `MaxDataCount` of 65,472 —
fifteen times that. Clamping transaction sizes to `MaxBufferSize` is wrong in
both directions: it cuts throughput by an order of magnitude on every server,
and — because the clamp applies to the two fields independently — it still asks
Windows for 4356 + 1024 against a 4,356-byte buffer, reproducing the very
failure such a clamp is written to fix.

**The Go library's failure is `MaxParameterCount`, not `MaxDataCount`.** Its
TRANS2 encoder sends 1024 + 65535 = 66,559, overshooting by 35 bytes, and the
RAP encoder sends the same 1024; `EncodeTransactNamedPipeRequest`
(`rap.go:364-365`) asks for no parameter bytes at all, so the overshoot belongs
to the TRANS2 and RAP paths rather than to every transaction Go sends.
`MaxParameterCount` is the wrong field to be spending 1,024 bytes on: the reply
parameter block measures 10 bytes for FIND_FIRST2 and 8 for FIND_NEXT2.
Right-sizing it to 64 makes even `MaxDataCount = 65535` succeed on Windows, so
the fix costs no data budget at all and leaves large replies fully exercised.
That 64 is also the floor for every other transaction rather than a FIND-only
number: each sets `MaxParameterCount` from the parameter block its own reply
defines and never asks for less than 64, so a subcommand whose reply parameter
block was mis-sized still has room to answer, and
`EncodeTransactNamedPipeRequest`'s zero becomes the floor too. Against a
66,524-byte ceiling the floor costs nothing worth counting.

**The port's own transactions ask for `MaxDataCount = 65,472`**, which with that
`MaxParameterCount` of 64 sums to 65,536 and leaves 988 bytes under the measured
ceiling. The ceiling is measured; this number is chosen, in the same register as
the timeouts — nothing in the evidence campaign fixes it, and what recommends it
is a round message's worth of reply with the ceiling still visibly above it.
Three things follow from it: it is the byte budget a FIND page is really bounded
by, rather than the `SearchCount` a request asks for (see Directory listing); it
is the per-request reassembly bound, since a conforming server may not return
more than the request asked for (see Routing and reassembly); and it is the
request half of what decides whether a reply needs more than one message at all,
the advertisement below being the half that varies.

`MaxBufferSize` still governs what it actually describes: the size of a single
SMB *message*. It bounds READ_ANDX and WRITE_ANDX chunk sizes only when
`CAP_LARGE_READX` / `CAP_LARGE_WRITEX` are absent; with those capabilities the
bound is the NetBIOS frame instead — a 130,108-byte read reply against a
16,644-byte negotiated buffer was measured against the live Samba container
during the design session, and confirms it. It carries no logged command or
output in `notes/`, unlike findings W6, W7 and W8, so what establishes it is the
large-read fixture: `spikes/capture-large/0018-s2c-cmd2e.bin` is that
130,108-byte reply (see Fixture obligations). What the chunk size is derived
from is the
frame limit *less a reservation*, never the limit itself: the NetBIOS header,
the SMB header, the command's words and `ByteCount` all come out of the frame
before any payload does. Go's `MaxDataSize` of 130,048
(`internal/smb1/encoder.go:34`) is that number with the reservation already
taken — roughly a kilobyte below the 131,071-byte inbound ceiling this design
reads (see Wire layer) — and it is carried for that reason rather than
recomputed from the ceiling (see Constants inherited without derivation).

**The reservation is 1,024 bytes, and the chunk size has three cases.** With
`CAP_LARGE_READX` / `CAP_LARGE_WRITEX` it is that 130,048. Without them it is
`min(65,520, MaxBufferSize − 1024)`: the 65,520 is not derived from the
negotiated buffer at all but from the field that asks for the bytes —
`MaxCountOfBytesToReturn` is 16 bits without the capability, which is why Go
uses a flat 65,520 there (`internal/client/file.go:200,226,274,552`, with the
reason at `:549`) — and the 1,024 is Go's `SMBProtocolOverhead`
(`internal/client/file.go:31`),
which it subtracts from the negotiated buffer at `:233` and `:662`. After the
one-shot downgrade below it is `MaxBufferSize − 1024`. The subtraction is the
whole point in all three: a message carries its headers before it carries
payload, so asking for exactly `MaxBufferSize` overruns the buffer by however
much of it they take — the same mistake the rejected clamp above makes with the
transaction fields, and one the downgrade cannot afford, being reached only
after a server has already rejected something. A server without the
capabilities is bounded by the reservation already, so the downgrade only ever
changes what a capability-bearing server is asked for. **Neither subtraction is
guarded here, and neither needs to be**: a `MaxBufferSize` below the 4,356-byte
SMB1 minimum failed the connection when the negotiate response arrived (see
Security posture), so the value these rules subtract from is at least 4,356 by
construction. The guard is one check in one place on purpose; putting saturating
arithmetic here instead would carry a nonsense buffer size forward silently.

**The capability case diverges from Go deliberately.** Go's sequential read and
write paths clamp to `MaxBufferSize − 1024` whether or not the capability is
present (`internal/client/file.go:233`, `:662`). The port's capability case is
bounded by the frame limit, and below it only where a server bounds itself
lower: the 130,108-byte reply measured
above against a 16,644-byte negotiated buffer is what says that buffer does not
bound a capability-bearing transfer, and clamping to it anyway would spend an
order of magnitude of throughput on a limit no tested server enforces. The
divergence is named because the three cases otherwise imply it without saying
it.

**That chunk size has been measured against Windows as well, and the two
commands answered differently.** The chunk size turns on `CAP_LARGE_READX` /
`CAP_LARGE_WRITEX` being present and on nothing else, and Windows 11 24H2 sets
both — `Capabilities = 0x8001E3FC` — beside a `MaxBufferSize` of 4,356, which is
the pairing that made it worth asking. It **accepts a 130,048-byte `WRITE_ANDX`
in full**: three of them, each acknowledged `Count = 130048`
(`spikes/capture-win-large/`). It **serves every `READ_ANDX`
`min(asked, 65536)`**: 65,520 asked and served, 65,535 asked and served, and
65,536, 65,537, 98,304 and 130,048 all served 65,536, against a 260,096-byte
file, so it is not an end-of-file effect (`spikes/capture-win-readcap/`, one
read per size). Windows therefore caps a read reply at half what it accepts on a
write. The frame limit is what bounds the write; the read is bounded by the
server, below the frame limit and fifteen times above the negotiated buffer. So
`MaxBufferSize` is not the bound in either direction, which is what the rule
above rests on and is why its direction holds; what the rule may not say is that
the frame limit is the *only* bound, because on this server the read meets a
lower one.

**What carries the correctness there is the fill loop, and against Windows it
runs on every large read.** A short read is none of the three statuses that
trigger the one-shot downgrade below, so the downgrade correctly never fires:
the reply is `STATUS_SUCCESS` carrying fewer bytes than were asked for, and
nothing but the byte counts records it. What covers it is the rule the read path
already carries — a chunk answered short is re-issued for the bytes it did not
return, and only a chunk answered with zero bytes ends anything (see Public API
→ Reads and writes). A 130,048-byte read chunk against Windows takes two round
trips rather than one, and a client that read the short answer as end of file
would lose the rest of the file silently, which is exactly what the reference
library does (see Acceptance Criteria → Where the Go library is the oracle, and
where it is not).

**Applying the chunk size to a server outside those two implementations is still
an extension** — the same shape as the transaction ceiling's extension above,
and it is flagged here for the same reason. What has changed is how far the
measurement reaches: both implementations the campaign tested now stand behind
it, Samba's in `spikes/capture-large/` and Windows' in `spikes/capture-win-large/`
and `spikes/capture-win-readcap/`, and neither refuses the size. A server that
refuses it outright is what the one-shot downgrade below exists for, and the
conformance script keeps the check for a server nobody has measured (see
Acceptance Criteria).

**The downgrade is conservative and one-shot.** A server that rejects a large
read or write has that one operation retried once at `MaxBufferSize − 1024`,
and is recorded as small-buffer for the life of the connection, so every later
chunk on it is bounded the same way. This is the one
place the port retries a failed operation, and what makes it the only one is
that a retry re-sends the same request: the downgrade re-issues the read or
write that was refused, at a smaller size. The fall-throughs elsewhere in this
design send a different request instead — RAP giving way to DCE/RPC and a pipe
transact to write-then-read (see Wire layer), `SMB_QUERY_FS_SIZE_INFO` to
`SMB_INFO_ALLOCATION` (see Public API → Filesystem verbs) — so none of them
is a retry. The retry is narrow on purpose: unlike
the transaction ceiling, which is a measured number applied deliberately to
every server, the chunk size is measured on the two implementations this
campaign reached and asserted of the rest, so the cost of being wrong on a third
is an operation that cannot be performed at all. It is a single downgrade
recorded once per connection rather than a retry loop, so nothing is attempted a
third time and which size the server accepts stays visible (see Non-goals).

**Rejecting means one of three statuses on the `READ_ANDX` or `WRITE_ANDX`
itself**: `STATUS_INVALID_SMB`, `STATUS_INVALID_PARAMETER` or
`STATUS_INSUFF_SERVER_RESOURCES`. Nothing else downgrades anything — a trigger
left as "any error" would spend a connection's throughput on an unrelated
failure. The third of those is ambiguous by this design's own admission: excess
multiplexing earns the same status with nothing beside it to tell the two apart
(see The request table), so a lapse can cost a connection its chunk size for the
rest of that connection's life. That is accepted in the direction it errs, which
is working slowly rather than failing at all. The same status answering a
*transaction* is not a downgrade trigger and keeps the mapping above: the
downgrade belongs to the two large-I/O commands and to nothing else.

**The client advertises its own receive capability, not the server's value
echoed back, and the value it advertises is 65,535.** The `MaxBufferSize` the
client sends in SESSION_SETUP_ANDX tells the server the largest SMB message the
client will accept, and a server splits a larger reply to fit it — so that
field, not anything the server advertises, is the threshold at which a reply
arrives in several messages at all. The crate can receive any frame the NetBIOS
length permits, so there is no reason to ask for less than the field can carry.
65,535 is what it can carry and no proposal can raise it: SESSION_SETUP_ANDX's
`MaxBufferSize` is a `USHORT` on the wire
(`internal/smb1/session_setup.go:20,35,96`), unlike the *negotiate response*
field of the same name, which is 32 bits
(`internal/smb1/negotiate.go:34,50,122`). Go echoes the server's number straight
back (`internal/client/session.go:74,136`), casting it to that `USHORT` — the
cast is the field width and not a defect, but the echo is why the value has
never been visible as a choice. Here it is one, and since that field is the
threshold above, what the port advertises is also what decides how often the
reassembly path is reached at all. Fixture obligations owns that consequence and
the live coverage it obliges. Advertising 65,535 and then requiring read replies
of 130,048 reads as a contradiction and is not one: `MaxBufferSize` bounds a
single message only where `CAP_LARGE_READX` / `CAP_LARGE_WRITEX` are absent, and
where they are present the bound is the NetBIOS frame instead, as above. It
needs saying because the two numbers sit paragraphs apart and the larger is the
legal one.

**A transaction request that does not itself fit is an error, not a secondary
exchange.** The ceiling above governs what a request may ask the server to
*return*; a TRANS2 or `SMB_COM_TRANSACTION` request's own parameter and data
bytes are a separate question, and **every transaction request must fit in one
message within the negotiated `MaxBufferSize`**. That is the transaction paths'
rule and no other's: a `READ_ANDX` or `WRITE_ANDX` is bounded by the chunk size
instead, which where the large-I/O capabilities are present comes from the
NetBIOS frame and not from `MaxBufferSize` at all (see above), so applying this
check to a 130,048-byte write would break large writes against precisely the
servers the chunk rule exists for. SMB1 splits an
oversized transaction with `TRANS2_SECONDARY` / `SMB_COM_TRANSACTION_SECONDARY`,
which this design does not implement: the port assumes every transaction it
builds fits, and long paths — a deep Unicode path in
`TRANS2_QUERY_PATH_INFORMATION` or
a long search pattern in `TRANS2_FIND_FIRST2` — are the realistic way that
assumption breaks. A request that would not fit fails locally, with an error
naming the limit and the request that exceeded it, before anything reaches the
wire. It is not truncated, and it is not silently split.

**Both limits are enforced centrally**, in the one place that builds a
transaction request, not at each call site — the same reason admission is
enforced in the actor rather than by whoever issues a request (see Connection
architecture). A size rule applied per call site is a rule the next call site
added will not apply, and both failures here are silent until a server
complains about them.

**Three more fields of that request are fixed there and reach no caller**:
`MaxSetupCount`, `Flags` and `Timeout` are all `0`, on every TRANS2 subcommand
and on `SMB_COM_TRANSACTION` alike, matching the reference
(`internal/smb1/trans2.go:286-289`, `internal/smb1/rap.go:306-309,366-369`). The
zero `MaxSetupCount` says the port accepts no setup words back, which none of
the replies it asks for carries; the zero `Flags` is what makes the exchange an
ordinary two-way transaction that leaves the tree connection in place, those
being the two behaviours that field can ask for and neither being wanted here;
and the zero `Timeout` asks the server to block for as
long as it needs, the client's own bound being the per-request timeout (see
Configuration and timeouts) rather than anything the server is told.

### Public API

The vocabulary follows the `smb` crate (smb-rs) where SMB1 has the concept:
`Client`, `ClientConfig`, `UncPath`, `Tree`, `File`.
Names are free and the familiarity is worth having. Behaviour diverges wherever
smb-rs's own is defective or SMB2-shaped, and each divergence is listed in
Alternatives with its reason. There is no `Directory` type: SMB1 reaches both
metadata and enumeration by path, nothing would return such a handle, and a
listing comes from `Tree::read_dir(path)` instead (see Directory listing). There
is no `Connection` or `Session` type either, though smb-rs has both: here they
would be names with no methods, no purpose and no construction path, the
connection and the session being what `Client` dials and caches behind a `Tree`
(see Connection caching and reconnection). Removing them from the vocabulary is
smaller than inventing a surface for them.

**`Client` is the primary path.** A caller reaches a file through
`Client` → `Tree` → `File`, and that is the whole opening sequence. smb-rs's own
examples get by without naming the two types above either, and a four-type
opening sequence is a worse first impression than it needs to be.
**`Client::tree(unc_path)` is the verb in the middle of that chain**: it takes
the UNC path naming the share and the server — with the port to dial where that
is not 445, the path being the only address anything in this API carries (see
Paths) — dials or reuses the connection and session behind it (see Connection
caching and reconnection), and is where every `Tree` in this document comes
from.

**`Client::list_shares(server)` enumerates a server's shares**, and it is the
only public entry to that path: it names no share and needs no `Tree`, since
enumerating is what a caller does before it has a share to connect to. It is
where the
RAP-then-DCE/RPC fallback, and with it the whole `rpc/` module, is reached from
(see Wire layer). Each share comes back as a **name, a kind and a comment**.
Go's public API returns bare names and discards the other two; they are kept
here, because the comment is what a user browsing shares actually reads, and
discarding it would leave the RPC decoder parsing fields it throws away.

**Operations that SMB2 has and SMB1 cannot express are absent, not present and
failing.** No change-notify, quota, security descriptors, copychunk, DFS,
multichannel or FSCTL surface. There is no `channel: Option<u32>` parameter
threaded through the I/O methods — under SMB1 it would be permanently `None`.
An API that typechecks for what the wire cannot carry is worse than one that
does not compile.

#### Reads and writes

`read_exact_at` and `write_all_at` take an absolute offset and `&self`, so
concurrent operations on one handle are possible — which matters on a
pipelining transport. The names are std's and so is the contract they name:
`std::os::unix::fs::FileExt` spells the may-transfer-fewer forms `read_at` and
`write_at`, and the fill-or-error forms `read_exact_at` and `write_all_at`.
These are the fill-or-error forms, so they take those names; borrowing the
shorter ones for the stronger contract would mislead every reader who knows std,
silently, in the direction of the truncation hazard this section exists to
prevent.

**`read_exact_at` returns `Result<()>`, and a span it cannot fill is an
error.** The contract is std's, the one the name carries, and not Go's
`io.ReaderAt`, which this design followed while the method was named `read_at`
and returned a count. The signature carries no count, so end of file is not an
outcome a caller reads off a return value: it is the error that a request for
bytes the file does not hold produces. A caller that wants the count reads
through the adapter below, whose `AsyncRead` reports end of file as `AsyncRead`
does everywhere, or asks for a span whose length it already knows. A short
return the caller must notice is the same silent-truncation hazard invariant 1
exists to prevent, merely relocated from library code into every consumer's read
loop. **That adapter reads end of file off the wire rather than off a count**:
it is inside the crate and drives the same chunk loop, so it observes the
terminal condition itself — a short far end, a zero-length reply, or
`STATUS_END_OF_FILE` — and no public count-returning method has to exist for it
to have one. Filling the caller's buffer means looping over READ_ANDX replies, and the
loop pipelines, so those replies land out of order and a short one in the middle
is not the end of anything. **The fill loop tracks which ranges of the requested
span have arrived**, the same coverage rule reassembly uses and for the same
reason (see Routing and reassembly). Three rules govern the loop, and they are
one rule seen from three sides rather than three that compete:

- a chunk answered short is re-issued for the bytes it did not return, which is
  how the span comes to be covered;
- a chunk answered with zero bytes is never re-issued — that is the loop's
  no-progress guard, and it reads off those same ranges rather than off the
  cached size, which nothing may gate a read on. A chunk answered
  `STATUS_END_OF_FILE` is that same answer under a status rather than a count:
  it is not an error, it returns the bytes already covered and nothing more, and
  it is not re-issued either;
- once every issued chunk has been answered, any range of the span still
  uncovered fails the call, a hole in the middle and a short far end alike; the
  two are the same outcome to the caller and only the error's own text
  distinguishes them.

Without them a short middle chunk with later chunks full is undefined.

`write_all_at` carries the symmetric rule, and it needs one because short writes
happen: a `WRITE_ANDX` reply may acknowledge fewer bytes than its chunk asked to
write. The remainder of a short-acknowledged chunk is re-issued from the first
unacknowledged byte; a chunk acknowledged with zero bytes is an error rather
than another attempt, by the same no-progress reasoning as the read; and the
call returns nothing on success, which it reaches only when every byte of the
caller's slice has been acknowledged. When it fails instead, the error carries
`written`, the contiguous acknowledged prefix and a lower bound on what reached
the server (see Cancelling a write).
`write_all_at` takes one further argument, an optional `WriteProgress`, which is
how a caller that drops the write future learns how much of it reached the
server (see Cancelling a write).

**`WRITE_ANDX`'s `WriteMode` is `0` on every write the port sends**, matching
the reference (`internal/client/file.go:866,958`). It asks for no write-through,
so an acknowledgement says the server accepted the bytes and not that they
reached its disk — which is what makes an acknowledged prefix the right thing to
resume from and the wrong thing to call durable.

**One operation pipelines to at most four chunks.** The inherited 128 KiB read
and 256 KiB write thresholds decide whether a one-shot call pipelines at all
(see Constants inherited without derivation), and they are measured against the
buffer that call was handed — `read_exact_at`, `write_all_at`, and the
`Tree::read` and `Tree::write` built on them; four is how deep it goes once it
does. **The adapters are the same rule's other case and those thresholds do not
govern them**: an adapter pipelines its fill unconditionally, at this same depth
of four, because its unit of work is that four-chunk fill and not the size of
the caller's `read()`. Measuring a threshold against what `tokio::io::copy`
hands it 8 KiB at a time would make the read-ahead below dead code on precisely
the case it exists for, a 10 GB file streamed through the adapter. Four is
also the reader adapter's read-ahead default below, and for the same
reason: the admission limit bounds what the whole connection carries, and this
bounds one call's share of it, so a single `read_exact_at` over a large buffer
cannot take a connection's entire capacity, or hold the admission limit's worth
of 130 KB reply frames, while every other task on it waits. It is chosen rather
than measured, as the read-ahead is; Go's own ladder up to the negotiated
`MaxMpxCount` is not carried (see The request table).

`File::into_reader()` and `into_writer()` produce cursor-carrying adapters that
implement `tokio::io::AsyncRead` and `AsyncWrite`. Without them the crate cannot
be used with `tokio::io::copy`, `BufReader`, `read_to_end`, `ReaderStream`, or
anything else that accepts `impl AsyncRead` — an isolation that would cost more
than the cursor saves. Both adapters buffer internally, because
`tokio::io::copy`'s default 8 KiB buffer would otherwise reach the transport one
8 KiB read at a time and be slower than a hand-written loop. **The reader's
read-ahead is a number of outstanding chunks, four by default, and not a byte
size**: a byte figure barely clears one chunk against a server taking
130,048-byte reads, so it would pipeline to a depth of about one and defeat the
reason the adapter buffers at all. Four is the depth whatever the chunk size
turns out to be against a given server, and it is reached on every adapter: the
128 KiB and 256 KiB thresholds gate a one-shot call's own buffer and not an
adapter's fill (see above), so an adapter read 8 KiB at a time still pipelines
four chunks deep. The writer buffers by the same count and for the same reason.
**The count is configurable on `ClientConfig`** and four is
its default: it is a memory-versus-throughput trade, and a consumer holding many
adapters at once is the one with a reason to make that trade differently (see
Configuration and timeouts). Both are a per-adapter memory cost worth stating:
four chunks each at that default, which is 508 KiB where
the large-read capability is present and four times
`min(65,520, MaxBufferSize − 1024)` where it is not (see Sizing transactions),
held for as long as the adapter lives — so a consumer holding adapters over many files at once pays
it per file.

`AsyncSeek` is not implemented. `into_writer()` takes the optional
`WriteProgress` at construction, because `AsyncWrite`'s per-call signature has
nowhere to put one and an adapter is built once — and it **returns a `Result`**
for that argument's sake, a handle that already serves a write being refused
here as it is at `write_all_at` (see Cancelling a write). `into_reader()` takes
no handle and is infallible.

**`into_inner()` gives the `File` back, and it is `async` and fallible.** Both
adapters consume the handle, so without a way back the only release path for an
adapter-owned handle is `Drop` —
the limitation documented for a `File` behind an `Arc` under Configuration and
timeouts, but arriving silently on the ordinary path, since `into_reader()` is
how a caller reaches `tokio::io::copy`. `into_inner()` consumes the adapter and
returns the `File`, so the handle can still be closed explicitly and its failure
still reported. It awaits and it can fail because the writer holds buffered
bytes that have not reached the server: an infallible synchronous `into_inner()`
would discard them with nothing returned to say so, which is the silent-loss
shape invariant 2 forbids a layer down. It flushes what it holds, and a flush
that fails is an error the caller gets rather than one nobody sees.

**Length is not a round trip.** `NT_CREATE_ANDX`'s response already carries
`EndOfFile`, so the size is known at open. It is tracked locally and updated on
write and on `set_len` — a `File` method rather than one of the `Tree` verbs,
since it acts on an open handle — and `len()` is infallible and synchronous, as
`len()` is everywhere else in Rust. It is a hint, never a gate: reads are never
short-circuited against it — that is precisely the bug that makes smb-rs return
`Ok(0)` for a read past a stale cached size. `metadata()` goes to the server for
callers who need fresh data, and pays the round trips that takes (see Filesystem
verbs).

#### Whole-file and whole-tree operations

`Tree::read(path) -> Vec<u8>` and `Tree::write(path, &[u8])` exist, the latter
creating the file or truncating an existing one exactly as `std::fs::write`
does. They are not a convenience layer to be trimmed for tidiness: they are where the fill-or-error
loop lives once, tested, instead of in every consumer. They also hand the
transport the whole payload at once rather than a caller's loop of small ones,
which is what lets pipelining engage: `read` sizes its buffer from the open-time
`EndOfFile`, and `write` presents the caller's whole slice. Lets, not
guarantees — the inherited 128 KiB read and 256 KiB write thresholds still
decide whether a one-shot call like these pipelines at all (see Reads and
writes, and Constants inherited without derivation), so a `Tree::write` of
100 KiB pipelines nothing. What the helpers
remove is the other way a transfer fails to reach those thresholds: a consumer
looping in 64 KiB chunks stays under both however large the file is.

That buffer is the one allocation in the crate a server-supplied number decides,
and `EndOfFile` is 64-bit where the reassembly totals are 16-bit — so the rule
that refuses to let a server size a buffer (see Routing and reassembly) does not
hold here, and the contract is stated instead of the exception being left to be
noticed. Asking for a whole file in memory is asking for an allocation the size
of that file, and the library has no better number than the one the server
reports; `Tree::read` is therefore for files the caller knows are small enough,
and a caller who cannot vouch for the size reads through `File::read_exact_at`,
which allocates what the caller hands it and nothing more, or the reader
adapter, which adds its own read-ahead — four chunks by default — to that and
nothing that scales with the file (see Reads and writes).

**`Tree::read` is also the one place the fill-or-error rule does not apply.** It
sizes its buffer from the length the open reported and fills it, so a file
another writer truncates in between answers short at the far end — and that is
end of file here rather than the error `read_exact_at` would raise (see Reads
and writes). What comes back is what was there. This needs saying precisely
because `read_exact_at`'s contract makes the opposite the default everywhere
else.

`Tree::remove_dir_all` likewise exists for a correctness reason rather than an
ergonomic one — see Handle lifetime.

#### Directory listing

**`Tree::read_dir(path)` starts a listing and returns the iterator**, matching
the `std::fs` naming the filesystem verbs use. It is the only entry point to
enumeration, and the iterator it returns owns the server-side search from there
on — closing it is closing that search.

Listing is lazily paged, and the iterator exposes an inherent
`next_entry().await` returning `Result<Option<DirEntry>>` — the shape of
`tokio::fs::ReadDir`. It deliberately does **not** return `impl Stream`:
`Stream` is not in `std`, so returning one puts the pre-1.0 `futures-core` in
this crate's public signature and forces every consumer to add a dependency to
perform the most common SMB operation. That is the churn guiding principle 4
rejects, arriving through the API rather than the dependency graph. A `Stream`
implementation can be added later without breaking anything.

**The pattern `Tree::read_dir(path)` searches on is the path with `\*`
appended.** For a path inside the share it is the normalized path, a trailing
backslash if it has not got one already, and an asterisk — `dir\sub` searches on
`dir\sub\*` — and for the share root, where there is no path, it is `\*` with
the leading backslash. That asymmetry is the reference's
(`session.go:864-873`) and is inherited deliberately rather than tidied away:
every listing this campaign observed was made with these patterns, and no
evidence says what a server that refused the root form's leading backslash
would do instead — so a neater spelling would be a change with nothing behind
it.

**The iterator carries the search's continuation state**, which is the search
ID, that pattern, and whether the search has reached its end by either of
the two terminators below. A
`TRANS2_FIND_NEXT2` is not self-contained: it repeats the search ID the
`TRANS2_FIND_FIRST2` reply returned, re-sends the pattern, and asks the server
to continue from its own position — `Flags = SMB_FIND_CONTINUE_FROM_LAST` with
`ResumeKey = 0`. Both requests ask for information level `0x104`,
`SMB_FIND_FILE_BOTH_DIRECTORY_INFO`, which is the level every rule about entries
in this design is written against: the chain walk and its two terminators (see
Wire layer), and the symlink a recursive delete cannot distinguish from a
directory (see Handle lifetime). Continuation is therefore server-side, and the
client keeps no resume point of its own; that is what the Go library sends
(`session.go:922-930`, `internal/client/file.go:1431-1438`) and the port adopts
it, with one addition — the port sets `SMB_FIND_CLOSE_AT_EOS` in those flags as
well, which Go sets only on the FIND_FIRST2, so that the request reaching
end-of-stream is the one that closes the search (see Handle lifetime).

**The FIND_FIRST2 asks for `SearchAttributes = 0x16`** — directory, hidden and
system — matching the reference. It is not a cosmetic choice: it decides whether
hidden and system entries appear in a listing at all, and with that whether
`Tree::remove_dir_all` can empty a directory that holds them.

**Two things end a listing, and `STATUS_NO_MORE_FILES` is the second.**
`EndOfSearch` in a reply is one. The other is a FIND request answered with
`STATUS_NO_MORE_FILES` (`0x80000006`), which is warning severity rather than
the `0xC` error class, carries no entries, and says the search is exhausted: the
listing ends normally there, exactly as it does on `EndOfSearch`, and
`next_entry()` returns `Ok(None)` rather than an error. Go's own error check
allows the status explicitly (`internal/smb1/packet.go:172-186`).

**The paging loop has a no-progress guard** as reassembly and the read fill loop
do: a page that yields no entries and neither sets `EndOfSearch` nor carries
`STATUS_NO_MORE_FILES` is an error, not another round. Without it a server
answering `SearchCount = 0` with `EndOfSearch = 0` pages forever. **The guard
counts the entries the server returned, before `.` and `..` are removed**, and
the ordering is the rule rather than an implementation detail: an empty
directory's first page is `.` and `..` and nothing else, and on a server that
does not set `EndOfSearch` on it the post-filter reading turns listing an empty
directory — the ordinary case — into an error. That the two are in the server's
count at all is measured rather than assumed: in finding C5's control capture
the server reports six entries where the client hands back four. The guard does
not apply to either terminator: a terminating reply is entitled to carry no
entries, and failing it would turn the ordinary end of a listing into an error
on every server that ends one that way. It costs nothing to compute, because the
walker already cross-checks the entries it walked against the `SearchCount` the
reply reports (see Wire layer).

The batch size is what each round *asks* for and nothing more: `SearchCount` is
advisory, and a server returns whatever fits — Windows answers a request for
100 with 22, because what bounds a page is `MaxDataCount`, not the count asked
for. The 100 is still load-bearing, but for one reason and in one place: it is
what makes a Samba reply large enough to fragment (see Fixture obligations).
The values observed in `spikes/capture-frag/0010` are `SID = 256`,
`SearchCount = 100`, `EndOfSearch = 0` and `LastNameOffset = 17656` — the last
of those recorded because the reply carries it, not because anything reads it
back into a request.

An earlier position in this design had the iterator carrying that offset as its
resume point, and made the offset pointing past the end of the first message the
reason reassembly must complete before the entries are parsed. The offset is
unused, but the conclusion holds for a plainer reason the corpus does show: an
entry straddles the fragment boundary — the 93rd entry of the page in
`capture-frag/0010` begins 176 bytes before that message's data ends and
continues in `0011` — so the chain is walked over the reassembled data buffer
and never over a single message — which is what the
actor delivers in any case, the unit of routing being a completed transaction
(see Routing and reassembly).

Most `next_entry()` calls are answered out of the page already in hand and send
nothing; the call that exhausts a page issues the FIND_NEXT2 from the search ID
and pattern the iterator has held since the FIND_FIRST2.

**`.` and `..` are filtered by the listing API, not by the parser.** The chain
parser returns every entry the server sent, so a chain that is short because the
server truncated it stays distinguishable from one that is short because two
entries were dropped. The listing API then omits `.` and `..`, matching
`std::fs::read_dir`; the Go library filters them too, and does so correctly.
That filter sits above the parser, above the search state and above the
no-progress guard: it changes neither
what a FIND_NEXT2 carries nor where the server continues from nor what counts as
progress, so a page whose
entries are all filtered still resumes exactly where the server left off.

**A filename that is not valid UTF-16 fails the listing.** The entry is not
handed back with a lossily decoded name: the error names the entry's position in
the directory and carries the raw bytes, so the caller can see what actually
arrived. Paths are `&str`-shaped (see Configuration and timeouts), so a lossily
decoded name is not usable as a path — returning one produces an entry that
looks usable and fails at the moment the caller acts on it, which is the
delete-what-you-listed path. Failing the listing is louder and it is rarer: a
real server sending such a name is vanishingly unlikely, and the loudness is the
point of spending an error on it. The consequence is owned rather than hidden: a
directory holding such a name cannot be enumerated through this crate, so
`Tree::remove_dir_all` cannot delete it either.

**The iterator closes like any other handle, except when there is nothing left
to close.** Alongside `next_entry()` it
exposes an inherent `close().await`, which reports the failure of the release
round-trip and is what `Tree::remove_dir_all` awaits before deleting a level
(see Handle lifetime); dropping the iterator instead enqueues the same close
best-effort. A listing drained to end-of-stream has already been closed by the
server: the request that ended it — the one that returned `EndOfSearch`, or the
one answered `STATUS_NO_MORE_FILES` — carried `SMB_FIND_CLOSE_AT_EOS`, and the
server released the search when it processed it. So on a drained listing
`close()` sends no `SMB_COM_FIND_CLOSE2`, and returns success rather than a
round-trip's error; dropping one enqueues nothing. Whether the search reached
its end is already part of the continuation state the iterator carries, so it
knows which case it is in.

**Entry order is the server's.** Samba returns a directory's entries unsorted
and Windows returns them sorted, and nothing in SMB1 obliges either. The listing
yields entries in the order the server sent them and sorts nothing, so an
acceptance test that asserts an order must either name the server it asserts
against or sort before comparing.

#### Filesystem verbs

**A `File` comes from `Tree`, and opening follows `std::fs`.** `Tree::open(path)`
opens an existing file for reading; `Tree::create(path)` creates one, or
truncates what is already there; `Tree::open_with(path, OpenOptions)` is
everything else. `OpenOptions` carries the `std::fs::OpenOptions` set — `read`,
`write`, `append`, `truncate`, `create`, `create_new` — plus one field that has
no local analogue.

**`append` exists, it is not atomic, and it reaches the writer adapter alone.**
It positions that adapter's writes at the file's length as observed when the
handle was opened, and they advance from there — cursor semantics, which
`into_writer()` is the only thing that has (see Reads and writes).
`write_all_at` is untouched by it: an absolute-offset write has no cursor to
append to, so on an append-opened handle it writes at the offset it was given,
exactly as on any other handle. Both halves need saying, because the name
invites the other reading. `FILE_APPEND_DATA` is requested either way, so that
the server permits the adapter's writes. What `append` is
not is `std::fs`'s `append`, which maps to `O_APPEND` and is atomic against
concurrent writers on the same file: SMB1 offers no equivalent, no
append-at-end-of-file a server resolves per write, so two writers appending to
one file through this crate can overwrite each other. The name is kept because the operation is the one callers want and
the alternative is making them compute offsets by hand; the caveat is stated
because the name promises something the protocol cannot deliver.

**The field with no local analogue is `share`, and it is permissive unless the
caller narrows it**: readers, writers and deleters alike are admitted, which on
the wire is `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`, `0x7`.
Delete sharing is part of the default and not an omission from it — permissive
means permissive, and it is what decides whether `remove_file` succeeds on a file
another opener still holds rather than returning a sharing violation. Windows'
own default is exclusive, which surprises a caller porting from local filesystem
code and produces sharing violations on files nothing else is writing. Narrowing what other openers are
allowed is the deliberate act, and `OpenOptions::share` is how it is asked for.
That `0x7` is a departure from the reference, which sends `0x3` on every
non-delete open (`session.go:487,546`) and so denies a deleter what this port
admits: it is a client-side value no server has been sent, on the conformance
script with the others (see Acceptance Criteria) and among the deliberate
departures that make the client-to-server assertions decode-then-re-encode
rather than byte-identity.

**`NT_CREATE_ANDX`'s `Flags` field is not reachable through `OpenOptions`, and
stays 0 whatever the options say.** It is a fixed property of what this design
sends and not a default a caller may change: no oplock is requested, and what
that forecloses is decided where it is relied on (see Frames that are not
replies).

**The options reach the wire as `NT_CREATE_ANDX` fields, and the mapping is
fixed here rather than at each call site.** The table is every field the request
carries apart from the AndX header, the reserved byte and the `NameLength` the
name itself fixes; only the first four carry anything the caller chose, and the
rest are constants of this design:

| Field | What it carries |
|---|---|
| `DesiredAccess` | The union of what the options asked for: `FILE_READ_DATA \| FILE_READ_ATTRIBUTES` for `read`, `FILE_WRITE_DATA \| FILE_WRITE_ATTRIBUTES` for `write`, `FILE_APPEND_DATA` additionally for `append`, `FILE_WRITE_ATTRIBUTES` alone for `create_dir`, which carries none of the caller's options, and `DELETE` alone on the delete path below. `SYNCHRONIZE` is not set on any of them — see below. |
| `CreateDisposition` | `FILE_OPEN` for a plain open, and on the delete path below, which opens what it is deleting; `FILE_CREATE` for `create_new`, and for `create_dir`; `FILE_OPEN_IF` for `create` without `truncate`; `FILE_OVERWRITE` for `truncate` without `create`; and `FILE_OVERWRITE_IF` for the two together, which is what `Tree::create` asks for. |
| `CreateOptions` | `FILE_NON_DIRECTORY_FILE` for a file open and `FILE_DIRECTORY_FILE` for a directory open, plus `FILE_DELETE_ON_CLOSE` on the delete path below. |
| `ShareAccess` | `0x7` unless the caller narrows it, as above. |
| `FileAttributes` | `FILE_ATTRIBUTE_NORMAL` (`0x80`) on a create, matching the reference, which sends `0x80` even when what it is creating is a directory. |
| `ImpersonationLevel` | `SEC_IMPERSONATE` (2). No option reaches it. |
| `Flags` | `0`, as above. No option reaches it either. |
| `AllocationSize` | `0`, matching the reference (`internal/client/file.go:93-107`). It is a hint about a file being created and nothing depends on it; a caller wanting space reserved sets the length afterwards. |
| `RootDirectoryFID` | `0`, matching the reference. Every path this port sends is relative to the tree, so there is no directory handle to resolve it against. |
| `SecurityFlags` | `0`, matching the reference. It qualifies the impersonation above, and this port asks for no qualification. |

**`DesiredAccess` asks for specific rights and never for `SYNCHRONIZE`, and
both halves are deliberate.** The reference asks for the `GENERIC_*` groups on
its file opens — `GENERIC_READ | SYNCHRONIZE`, `GENERIC_WRITE | SYNCHRONIZE`,
or both plus `SYNCHRONIZE` (`session.go:470-484`) — which claims a good deal
more than the operations behind them exercise. The port asks for the rights it
will use, which is narrower and says on the wire what the handle is for.
`SYNCHRONIZE` follows from that: it is the right to wait on the handle itself,
and nothing in this crate waits on one — reads and writes carry absolute
offsets and the actor waits on replies (see Reads and writes). The reference does not
treat it as a floor either: its directory create sends `FILE_WRITE_ATTRIBUTES`
alone (`session.go:545`) and its delete open sends `DELETE` alone
(`session.go:613`), both without it. What the reference does send on a file open
is fixture-pinned: `spikes/capture/0015-c2s-cmda2.bin` carries
`DesiredAccess = 0x80100000` — `GENERIC_READ | SYNCHRONIZE` — so this departure,
like the `ShareAccess` one beside it, is a client-side value no server has been
sent, and the two travel together on the conformance script (see Acceptance
Criteria). **`append` is where the port diverges
furthest, and it has to.** The reference clears `GENERIC_WRITE` when it sets
`FILE_APPEND_DATA` (`session.go:481-484`), which would leave an append-opened
handle unable to serve the absolute-offset `write_all_at` that this API keeps
working on one (see Reads and writes), so `FILE_WRITE_DATA` stays alongside
`FILE_APPEND_DATA` here.

`remove_file`, `remove_dir`, `remove_dir_all`, `rename`, `create_dir`, `read_dir`,
`metadata` and `exists` are named methods on `Tree` too, taking paths, matching
the same `std::fs` naming. smb-rs instead expresses deletion and renaming as typed
info-class writes — `set_info(FileDispositionInformation::default())` — which is
unteachable, and whose generic surface typechecks for info classes SMB1 cannot
carry. Renaming is a path-based command on the wire as well as a path-taking
method here — `SMB_COM_RENAME` — so `Tree` is where it belongs on both.

**Deleting is not, and an earlier position in this design had it as one.**
`SMB_COM_DELETE_DIRECTORY` and `SMB_COM_DELETE` are declared in the Go source
(`internal/smb1/constants.go:17,22`, in that order) and sent nowhere: `Share.Remove`
(`session.go:598-668`) opens the path with `DELETE` access and
`FILE_DELETE_ON_CLOSE` under disposition `FILE_OPEN`, then closes the handle,
and the server unlinks the entry on that close. The port deletes the same way,
and `remove_file`, `remove_dir` and every level of `remove_dir_all` are that one
mechanism, with the create option saying which kind of object the open expects:
`FILE_NON_DIRECTORY_FILE` from `remove_file`, `FILE_DIRECTORY_FILE` from
`remove_dir`.
Three things follow. It costs one round trip more than a path-based
delete would, being an open and a close where `SMB_COM_DELETE` is a single
request. It works for files and directories alike, where `SMB_COM_DELETE` cannot
delete a directory at all — so there is no second command to get right and no
`SMB_COM_DELETE_DIRECTORY` path to write. And the delete is share-mode bound at
both ends: the open asks for `DELETE` access, which the share mode of any handle
somebody else already holds has to permit, and it offers the same permissive
`0x7` in its own share mode, so it denies nothing to anyone opening after it.
That is the field `OpenOptions::share` exposes, and it is why the default admits
deleters and not only readers and writers.

**No stat precedes that choice, and the divergence is deliberate.** Go stats the
path to learn whether it is a directory
and sets `FILE_DIRECTORY_FILE` or `FILE_NON_DIRECTORY_FILE` from the answer —
three round trips where the port sends two. The port's caller has already said
which it meant by choosing the method, so a `remove_file` aimed at a directory
is refused by the *server*, with `STATUS_FILE_IS_A_DIRECTORY` (see Errors),
rather than by a client-side check that spends a round trip to reach the same
refusal.

**`create_dir` is that same `NT_CREATE_ANDX`** — `FILE_CREATE` with
`FILE_DIRECTORY_FILE`, then a close — and not `SMB_COM_CREATE_DIRECTORY`. It is
the field mapping above with nothing of the caller's in it, so creating a
directory, deleting one and opening a file all reach the path through the one
command.

`rename` does **not** overwrite an existing destination: `SMB_COM_RENAME`
returns `STATUS_OBJECT_NAME_COLLISION`, which surfaces as
`ErrorKind::AlreadyExists`. This differs from `std::fs::rename` and is
documented on the method, because the name invites the wrong assumption. **The
request's `SearchAttributes` is `0x16`** — directory, hidden and system, the
same set the FIND requests carry (see Directory listing) — matching the
reference (`internal/client/session.go:369-372`). It says which kinds of entry
the server may rename, so a narrower value would leave a hidden or system file,
or a directory, unrenameable — the same reason the FIND requests carry it.

**Both of rename's names go on the wire with a leading backslash**, and this is
the one command whose path on the wire is not the normalized share-relative
form Paths describes. The reference prepends `\` to the old name and the new
name alike wherever the caller's string has not got one
(`internal/smb1/rename.go:49-57`) and the port does the same. Nothing else about
them changes: they are the normalized paths the caller gave, refused by the
same three checks as every other path before the prefix is applied (see Paths).

`Tree::metadata(path)` uses `TRANS2_QUERY_PATH_INFORMATION` and requires no
handle, so nothing needs an open directory merely to stat a path. **It issues
two queries rather than one**: `SMB_QUERY_FILE_BASIC_INFO` (`0x0101`) for the
timestamps and the attributes, then `SMB_QUERY_FILE_STANDARD_INFO` (`0x0102`)
for the size and the allocation size, neither level carrying both.
`SMB_QUERY_FILE_ALL_INFO` (`0x0107`) would do it in one, and it is not taken: no
server in this campaign was tested with it, and a stat is not hot enough to
spend an untested information level on. It is recorded here as available and
untested rather than left unnamed.

**`Metadata` carries the four timestamps, the size, the allocation size and the
attributes**; `DirEntry` carries everything `Metadata` does — those four
timestamps, the size, the allocation size and the attributes — plus the entry's
name, which is
what `SMB_FIND_FILE_BOTH_DIRECTORY_INFO` returns per entry in any case (see
Directory listing). Both expose `is_dir()` derived from the attributes rather
than from a query of their own.

**The rest of the Go library's file surface is disposed of here**, in or out,
because a document that names every surface it drops makes silence on the rest
read as an omission.

In, because SMB1 expresses them and they are what a file client is for:
`Chtimes` and `Chmod` become `Tree::set_times` and `Tree::set_attributes`, both
sending `TRANS2_SET_PATH_INFORMATION` at `SMB_SET_FILE_BASIC_INFO` (`0x0101`),
the level that sets times and attributes together and needs no open handle;
`Statfs` and `VolumeInfo` become one `Tree::statistics`, sending
`TRANS2_QUERY_FS_INFORMATION` at `SMB_QUERY_FS_SIZE_INFO` (`0x0103`), whose unit
counts are 64-bit, and falling back to `SMB_INFO_ALLOCATION` (`0x0001`) on **any
error from the modern level** — the wide trigger the transact-to-write/read
fall-through already takes (see Wire layer), and for the same reason: Go accepts
five distinct statuses there (`fsinfo.go:248-252`), so a narrower trigger would
rest on guessing which of them a given server picks. It is the fallback the Go
library also carries, kept because the legacy level's counts are 32-bit and a
large volume overflows them;
and path `Truncate` is `File::set_len` on an opened handle, which already exists
(see Reads and writes) and which sends `TRANS2_SET_FILE_INFORMATION` at
`FILE_END_OF_FILE_INFORMATION` (`0x0104`), its data being the new length as
eight little-endian bytes and nothing else (`internal/smb1/constants.go:314`,
`internal/client/file.go:1076-1097`). It is a handle-based set and not a
path-based one — there is no `Tree` verb for it — and the handle it acts on has
to have been opened for writing, the level altering the file's length.
**None of those three carries a `std::fs` name**, and
they sit outside the naming rule the path-taking verbs above follow rather than
breaking it: `std::fs` has no verb for setting a path's times or attributes and
none for asking a volume its size, so each is named for what it does.

**`Tree::statistics` returns a named struct that says which level answered.**
`FsStatistics` carries three fields: `total_bytes: u64`, `available_bytes: u64`
and `level: FsInfoLevel`, an enum whose two variants name the two levels above.
Both levels report allocation units rather than bytes — units, sectors per unit
and bytes per sector — and the verb multiplies them out once so that every
caller does not. The level field is not decoration: the fallback is otherwise
silent, and the legacy level's unit counts are 32-bit, so on a volume large
enough to overflow them a caller has no other way to tell a real number from a
wrapped one.

**A zero field on `SMB_SET_FILE_BASIC_INFO` means "do not change", and splitting
that level into two verbs makes it the API's problem.** The level carries four FILETIMEs and
an attribute word (`internal/smb1/trans2.go:199-206`), and a zero in any of them
tells the server to leave that field alone — which the reference records in its
own comments for both halves (`setinfo.go:16-18`, `:94-96`, `:143-145`). Since
`set_times` and `set_attributes` are one wire level between them, each sends
zeros for the other's fields, and two rules follow:

- **`set_times` takes an `Option` per timestamp**, one for each of the four the
  level carries, and `None` encodes as the zero that leaves that timestamp as it
  was. Without that a caller could not set a modification time without also
  asserting a creation time it does not know.
- **`set_attributes(0)` is a silent no-op on the wire, so the port translates
  it.** A caller asking to clear every attribute gets `FILE_ATTRIBUTE_NORMAL`
  (`0x80`) sent instead, which is what actually clears them; sending the zero
  would return success and change nothing. This is the silent-no-op class
  guiding principle 1 exists to catch, and it is a case where the port does for
  every caller what Go's caller has to know to do for itself — the reference
  applies the substitution inside `chmodAttributes` (`setinfo.go:98-108`), on
  the one path that happens to go through it.

**Information-level numbers repeat across TRANS2 subcommands, and pooling them
into one constant table conflates them.** The `0x0104` above is a *set-file*
level; `0x0104` is also `SMB_FIND_FILE_BOTH_DIRECTORY_INFO`, the level every
FIND request in this design carries (see Directory listing), and `0x0101` is a
query-file level, a set-file level, a find level and a query-fs level at once. A
level means nothing except beside the subcommand that carries it, which is why
the reference names the sets separately rather than sharing them
(`internal/smb1/constants.go:290-335`), and the port groups its constants by
subcommand for the same reason.

**The Go library's second set-path fallback is deliberately not inherited.** A
server rejecting that basic level with `STATUS_NOT_SUPPORTED` gets the
core-protocol `SMB_COM_SET_INFORMATION` from Go instead
(`internal/client/session.go:442-456` on the path form, and
`internal/client/file.go:1162-1180` on the handle form; the top-level `Chmod`
that reaches the first of them documents the fallback at `setinfo.go:47-50`);
the port sends no such request and reports the rejection. The capability floor
is the reason: it refuses any server not advertising `CAP_NT_SMBS` (see Security
posture), and a server that clears that floor and still cannot answer a TRANS2
set-path at the basic level is not one this port targets. The Go library
predates that floor being enforced, so what its second fallback serves is a
class of server this port has already declined at the handshake.

Out, each for its own reason. `Symlink` and `Readlink` need the UNIX extensions
this port does not implement — which is also why `remove_dir_all`'s symlink
caveat is about what a *server* may resolve rather than about anything this
crate creates (see Handle lifetime). `Lstat`, with no symlinks to distinguish,
is `metadata`. `IsDir` is `metadata().is_dir()`. `Sync` is a documented no-op
in Go and a named non-goal here (see Non-goals). `ServerTime` serves a
clock-skew workaround this port does not have. And `Glob`, `Match`, `Walk`,
`CopyFile`, `CopyFrom` and `CopyTo` are composed by the caller from `read_dir`,
`read`, `write` and the adapters: none of them touches the wire in a way the
crate would do better.

#### Errors

One `thiserror` enum. NT status codes are carried as a typed variant holding the
raw code plus a name lookup, and **the status table is generated afresh from
[MS-ERREF] rather than transformed from the Go source's 3,598 generated
lines (`internal/erref/ntstatus.go`).** That is the more expensive answer and it is chosen anyway. The Go
generator's MSDN URL still
resolves — it redirects to the current MS-Learn [MS-ERREF] page, table intact —
but the generator scrapes a DOM shape that page no longer has, and its `goquery`
dependency is not in `go.mod`, so generating from the specification means
writing a new scraper first, where transforming the table already in hand would
be a mechanical rewrite. What buys the difference is attribution: that generator
is go-smb2-derived, so a table transformed from its output inherits whatever
obligation that material carries, while a table generated from a published
specification carries none. This is the same answer already settled for NTLM and
SPNEGO and settled for the same reason (see Licensing) — generating from the
spec removes the obligation rather than documenting it.

**A second specification stands behind that table, and the two overlap rather
than abutting.** [MS-ERREF] defines the NTSTATUS space and nothing beyond it,
and the generator hard-fails rather than invent a name that specification does
not define — which is what it correctly does with `STATUS_INVALID_SMB`, one of
the three statuses Sizing transactions names as a large-I/O downgrade trigger.
That name belongs to the SMB-specific statuses [MS-CIFS] defines for servers
returning NT status, and they are hand-written beside the 1,796 generated
entries, each carrying its own [MS-CIFS] citation.

**Their values are not a reserved range, and one of them collides.** The family
is `(SMB error code << 16) | error class`, the class being `0x0001` for ERRDOS
or `0x0002` for ERRSRV, so the eighteen span `0x00060001` to `0xFFFF0002` rather
than sitting in a block of their own. `STATUS_INVALID_SMB` is `0x00010002`
because its code is `ERRerror` and its class is ERRSRV — a coincidence of shape
and not a range. That value **is** in the generated table, under the unrelated
name `DBG_CONTINUE`: what [MS-ERREF] lacks is the name, not the number.

**Where they collide the [MS-CIFS] name wins, and only for those eighteen.** A
server that sends `0x00010002` in answer to an SMB command cannot have meant a
debugger continuation, so reporting one would be actively misleading. Every
other value in the table keeps its [MS-ERREF] name, and the generated file is
not edited — the preference is applied where the name is rendered, so
regenerating from the specification cannot silently undo it.

The licensing argument above is untouched: [MS-CIFS] is a published
specification exactly as [MS-ERREF] is, so neither generating nor hand-writing
from it carries an attribution obligation. No behaviour moves with any of this;
the downgrade trigger stays exactly as Sizing transactions specifies it.

**`Error::kind() -> std::io::ErrorKind`, plus `impl From<Error> for
std::io::Error`.** This replaces Go's seven error predicates — six named
`IsXxxError`, the seventh `IsTemporary` — with one method, and it is the piece
without which nothing composes: every function in a consumer's codebase
returning `io::Result` would otherwise need a hand-written conversion. It also
keeps status classification in one tested place. "Did this fail because the file
does not exist?" is answered by four different NT statuses depending on which
server answered — `STATUS_NO_SUCH_FILE`, `STATUS_OBJECT_NAME_NOT_FOUND`,
`STATUS_OBJECT_PATH_NOT_FOUND` and `STATUS_NOT_FOUND` (`errors.go:280-283`),
all four of which map to `NotFound` here — so a caller matching only
`STATUS_OBJECT_NAME_NOT_FOUND` writes a bug that appears against one server
family and not another. Dropping the taxonomy without replacing it would not
delete that problem, only relocate it to everyone.

**Five statuses the filesystem verbs turn on are mapped here**, one of them
against the Go library: `STATUS_DIRECTORY_NOT_EMPTY` to `DirectoryNotEmpty`,
`STATUS_NOT_A_DIRECTORY` to `NotADirectory`, `STATUS_FILE_IS_A_DIRECTORY` to
`IsADirectory`, `STATUS_INVALID_HANDLE` to `InvalidInput`, and
`STATUS_SHARING_VIOLATION` to `ResourceBusy` — **not** to `PermissionDenied`,
which is where Go groups it. A sharing violation is a transient conflict with
another handle rather than an authorization failure, and a caller that retries
on busy and gives up on denied needs the two apart. Two more mappings the verbs
turn on are decided where the behaviour is:
`STATUS_OBJECT_NAME_COLLISION` to `AlreadyExists` with `rename`, the one verb it
answers, and `STATUS_INSUFF_SERVER_RESOURCES` under Sizing transactions.
`STATUS_BUFFER_OVERFLOW` is deliberately absent from all of that: it arises only
on the named-pipe paths, where the pipe-read loop consumes it and reads again
until the response is whole (see Wire layer), so no caller of this crate ever
sees it and there is nothing for it to map to.

**Eleven statuses is the whole of what this document classifies** — the four
not-found statuses above, the five here, and the two decided where their
behaviour is, the second of those reaching a named error rather than a kind.
Classifying the rest of the table is the implementer's, and the root-level
`errors.go` is where the remaining groupings are read off: authentication
(`errors.go:208-224`, seventeen statuses), permission (`:325-328`),
already-exists (`:370-371`) and temporary (`:441-445`). Each is a boolean
predicate over a list of statuses rather than a mapping, so what transfers is
which statuses a real server actually returns for a given condition, not the
shape Go puts them in.

**A status outside every one of those groups maps to `ErrorKind::Other`, and the
error keeps the raw `NTSTATUS` regardless.** The generated table alone is 1,796
entries and this design classifies eleven, so the unclassified case is the
common one,
not the exception — leaving it undefined would put the most frequently taken
branch in the implementer's hands. `Other` is what `std` reserves for exactly
this, and the raw status stays reachable through `Error::status() ->
Option<NtStatus>` — `None` on an error that never carried one, a transport
failure or a decode failure — so a caller can match a status the crate never
anticipated. That accessor is not optional surface: the argument above for
replacing Go's taxonomy turns on a caller being *able* to match
`STATUS_OBJECT_NAME_NOT_FOUND` and being wrong to, which presumes it is
reachable. Without it the eleven classifications would be the only thing a
caller could ever see, and the classification would be lossy rather than narrow.
`kind()` answers the question a caller can act on generically; `status()`
answers the one it cannot.

Not carried over: the go-smb2 error taxonomy, the `os.PathError`/`os.LinkError`
wrapping, and the `io/fs` and go-smb2 compatibility surfaces (`dirfs.go`,
`compat.go`) in their entirety.

#### Configuration and timeouts

`ClientConfig` carries three timing bounds: a connect timeout, a per-request
timeout, and the overall deadline that caps how far a request's own progress may
extend it (see Frames that are not replies). The
first is not optional to have — `tokio::net::TcpStream::connect` imposes none of
its own, so a dead host otherwise hangs for the OS SYN timeout, around two
minutes on Linux — and it bounds the handshake as well as the dial, the
handshake being complete before the actor exists (see Connection architecture).

**The connect timeout defaults to 10 seconds, the per-request timeout to 30 and
the overall deadline to 300**, all configurable. Unlike the wire constants this
design pins to the digit, these three are chosen rather than measured: nothing
in the evidence campaign fixes them. Ten seconds is comfortably inside the
two-minute SYN timeout it exists to cut short and longer than any dial and
handshake a server that is there at all needs; 30 seconds is longer than
any silence a working server on a local network puts between messages, while 300
seconds is a bound on one request's whole life that ordinary work does not reach
and a server answering forever without finishing does.
Everything derived from them follows: a five-minute silence window, a
forty-minute give-up on a Lapsed request, and a hundred-minute idle eviction
swept for every twenty-five minutes.

The overall deadline carries four duties beyond the single request it bounds:
it is the span of silence that fails a connection, the idle time after which a
cached connection is probed before it is reused, the idle time — at twenty
times its value — after which a cached connection is evicted instead (see
Connection caching and reconnection), and — at eight times its value — how long
a Lapsed request waits before it is given up on and its multiplex ID retired
(see The request table). One knob therefore does five jobs, and
raising it for a slow single-board server lengthens all five. Three of those are
benign: a longer silence window, a later probe and a later eviction all cost
only that a dead connection is noticed later. Two are not. A server that
answers nothing holds capacity for longer before its requests lapse; and a
longer give-up means every request that will never be answered holds its
multiplex ID eight times longer, so more IDs sit reserved at once, while the
1,024-retirement bound that fails such a connection is reached that much later.

It carries five things besides, each decided in the section that owns it: the
credentials — username, password and the NTLM domain, which is credential
material and not a name the crate chooses (see Security posture) — which are the
one identity every connection a `Client` dials
authenticates with (see Connection caching and reconnection); whether a guest
logon is acceptable, which is what the guest
check tests against (see Security posture); the byte-level dump toggle, off
unless the operator turns it on for a run (see Security posture); the
`MaxBufferSize` the client advertises, which is 65,535 (see Sizing
transactions); and the adapters' read-ahead, four chunks by default (see Reads
and writes).

Two shapes in that surface are settled here because no other section owns them.
Paths are `&str`-shaped rather than `std::path::Path`: a remote path is not a
local one, and `Path` would carry the host platform's separator and
normalization semantics onto a wire that wants backslashes whatever the client
runs on; what the crate accepts in such a string, and what it normalizes it to,
is settled under Paths. And timestamps are `time::OffsetDateTime`, a type that
represents the whole FILETIME range rather than clamping it: SMB1's times are 100-nanosecond
ticks from 1601, which `std::time::SystemTime` can neither represent in full nor
give any defined calendar behaviour over, and a server is free to return a time
a narrower type would have to fabricate a value for rather than report. The
crate is pre-1.0 and is taken on the same judgment as the other pre-1.0
dependencies (see Wire layer).

**The per-request timeout bounds one request on the wire, not one public API
call.** That is the level the request table works at — a request outliving it
lapses — and it is the only level at which a fixed figure means anything: a
`Tree::read` of a large file and a pipelined `write_all_at` are many requests
each, and a bound on the whole call would have to scale with the file. So a
public call is bounded by that timeout applying to each request it issues, and
a caller who wants one figure for the whole call wraps it in
`tokio::time::timeout` — the ordinary Rust answer, and the same
drop-cancellation the progress handle exists
to report against (see Cancelling a write).

Handles own what they were opened on, by reference count: a `File` or a listing
iterator holds its `Tree` alive and a `Tree` holds its session and connection
alive, so nothing releases a tree connect while a file opened on it is still
live. Handles are `Send + Sync`, and `Client` is usable from many tasks behind an
`Arc` without an external lock. A handle behind an `Arc` cannot be closed
explicitly at all, because `close()` consumes it: a `File` shared that way is
released by the `Drop` path and by nothing else. A `Tree` has more than one owner
without any `Arc` of the caller's, the cache being an owner of every tree it
hands out:
**`Tree::close()` on a tree the cache still holds returns `Ok` having sent
nothing**, because disconnecting a tree other callers hold would invalidate
handles they still own. `TREE_DISCONNECT` goes out when the cache's own entry is
evicted or the client is closed, which is where the teardown rule already puts
it (see Handle lifetime). Both are documented rather than designed around.

### Connection caching and reconnection

`Client` caches connections and sessions internally. **Connections are keyed by
the dial address alone** — host *and port*, which is what a UNC path's server
component carries (see Paths): two paths naming different ports on one host are
two different servers, which is the exact shape of the capture
relay and the acceptance container this campaign runs against, and a host-only
key collides them. **The host half of the key is the literal string the caller
wrote, lowercased and otherwise untouched** — not the address it resolves to.
Two spellings of one server are therefore two cache entries, two connections and
two `MaxMpxCount` budgets, and that is the cost of the alternative being worse:
resolving first would make the cache's identity depend on DNS state at the
moment of the lookup, and would collapse two genuinely different servers behind
one rotating name onto a single connection and session. Lowercasing is the one
normalisation, hostnames being case-insensitive, and it belongs to the key
alone: what the server-name component carries on the wire is untouched by it
(see Paths).
Credentials are no part of that key and need not be, because
**one `Client` is one identity**: they live on `ClientConfig`, so every
connection a `Client` dials is authenticated with the same material, and a
caller needing two identities builds two `Client`s, each with a cache of its
own. That is also what makes a connection carry exactly one session, so trees
are keyed by the **connection** — which is the session identity, there being
only the one — and the share, with no third component for a distinction that
cannot arise. There is no user-facing connection pool: Go's `ConnectionPool` and
its `MaxActive`, `IdleTimeout` and `HealthCheck` knobs are not carried over.

What the pool did that is not optional is carried into the cache:

**Liveness, with transparent re-dial.** A cached entry whose connection actor
has terminated is evicted and re-dialled on the next use. Without this, a
long-running server is permanently broken after its first idle disconnect —
Windows reaps idle SMB sessions after fifteen minutes by default, so this needs
no NAT and no network fault to occur. Go's own transport reaches the same place
far sooner and from the client side: its 30-second NetBIOS deadline is armed
before the header read and covers, in its own source comment, "the entire packet
read (header + data)" (`internal/netbios/session.go:115-122`), so it kills any
connection idle that long — an idle-connection killer rather than a request
timeout, and one that sits oddly against its pool holding entries idle for five
minutes (`IdleTimeout`, `pool.go:68`). The port has no such
transport-level deadline — an idle connection with nothing outstanding is not
failed by the silence rule below — so its cached entries live until the server
or the network ends them, which is what makes eviction and re-dial load-bearing
here rather than incidental. smb-rs is the cautionary example: it has
no liveness probe, no eviction and no re-dial anywhere, its `Connection::connect`
refuses to reconnect outright, and calling `share_connect` again on a dead
connection returns `Ok(())`. Recovery there requires discarding the whole client.

Termination is not the only way a connection stops working, so eviction cannot
be defined by it alone. Two further routes reach the same permanent breakage. A
silent drop with no FIN leaves the actor alive, reading a socket that will
never speak again: every later call would spend a full per-request timeout and
charge capacity for the whole of it, and the entry would never be re-dialled.
**A connection fails once one overall deadline's worth of silence has passed
*while a caller was waiting through it*** — the same bound `ClientConfig`
carries, applied to the connection rather than to one request. Live or Orphaned
is what "outstanding" means here, and it is the condition that says a caller is
still waiting for something. A Lapsed request does not hold the clock open:
nobody is waiting on it, and letting it keep the window running would fail a
connection nothing was being asked of.

**The window accumulates rather than running from a fixed instant, and that is
load-bearing rather than a detail of measurement.** It advances only while at
least one request is Live or Orphaned, it stops when none is, and any arriving
message resets it to zero. The two simpler readings are each wrong in a way that
shows up at the defaults:

- **Timing from the last message received** fails a connection on its *first*
  use after any idle stretch longer than the deadline — the condition is
  satisfied the instant a request goes on the wire, because nothing has arrived
  for an hour. That would fail every long-idle cached connection at the moment
  it is reused, the `SMB_COM_ECHO` probe below included, so the probe would
  evict every connection it exists to vouch for.
- **Restarting the window at each dispatch** puts the rule out of reach
  entirely. At the default 30-second per-request timeout against a 300-second
  deadline, a request to a wholly silent server lapses ten times inside one
  deadline, and between each lapse and the next dispatch nothing is outstanding,
  so the window never survives to run out. That is precisely the server the rule
  exists to disconnect from.

Accumulating satisfies both: an idle connection accrues nothing however long it
sits, and a server answering nothing accrues across the successive lapses of
whatever is asked of it until the deadline is reached.
The measure is silence rather than a count of failures: what trips it is that
nothing arrived, not which clock noticed, so a request lapsing meanwhile — by
its per-request timeout or by the overall deadline — is that same evidence seen
one request at a time rather than a second trigger. A merely slow server never
trips it, because it is still answering: a reply counts, complete or still
continuing a reassembly, and so does an interim `STATUS_PENDING` response — the
same arrivals that reset a per-request timeout (see Frames that are not
replies) — and the silence window starts over at each. A server that answers
nothing trips it one deadline into the first stretch of silence a caller spends
waiting; a connection nobody is waiting on is not failed there but probed before
its next use, below. A NetBIOS
keep-alive is not an answer and does not count: it is evidence that the TCP
path is alive, not that the server is progressing on anything, and admitting it
would let a server hold a connection open indefinitely by keeping the socket
warm and doing nothing else.

The other route is a server that discards the session or the tree while keeping
TCP alive: it answers every later request promptly, so the actor stays healthy,
no timeout ever fires, and nothing above would evict anything. Two statuses say
so, they are not the same scope, and they are not treated alike.

**`STATUS_USER_SESSION_DELETED` fails the connection.** It is session-scoped,
and because credentials are per-`Client` a connection carries exactly one
session, so session and connection are the same object here: the actor shuts
down, which evicts the cache entry, and the next call re-dials.

**`STATUS_NETWORK_NAME_DELETED` does not.** It says one tree is gone and nothing
more, so it evicts that tree's cache entry and returns an error distinguishable
from a lost connection — the caller re-opens that tree, and only handles opened
on it are invalid. The connection, the other trees keyed under it, their open
handles and every in-flight request are left alone; failing the connection on a
tree-scoped status would tear down work that is still good.

Neither route is visible on a connection the cache is holding idle: the silence
rule needs a request outstanding to measure, and both statuses arrive only in
answer to one. **A cached connection idle for longer than one overall deadline
is therefore probed before it is reused** — the client sends `SMB_COM_ECHO` and
waits for the reply, and a failure evicts the entry so that the call re-dials.
That costs one cheap round-trip on the first use of a long-idle connection, and
it removes the case where a connection dropped silently while idle charges the
next caller a full deadline before anything is evicted.

**What the probe closes is the silent TCP drop, and only that.** `SMB_COM_ECHO`
is neither session- nor tree-scoped on most implementations, so it will answer
perfectly well on a connection whose session the server has discarded: the
probe cannot be claimed to cover that route, and the discarded session is still
caught where it always was, by `STATUS_USER_SESSION_DELETED` on the next real
request. Whether a given server answers an echo after discarding the session is
one of the checks the conformance script carries (see Acceptance Criteria). The
probe is what replaces the pool's `HealthCheck`, and it is the only place the
port sends `SMB_COM_ECHO`, which the Go library sends nowhere at all: its
`HealthCheck` is an optional callback, nil by default, and the Echo example in
its documentation (`pool.go:48-54`) calls a `sendEcho` that the library does
not define. So the encoder is written from the specification with no reference
and nothing to check it against — the same position `SMB_COM_FIND_CLOSE2` is in
(see Handle lifetime), and for the same reason: the Go constant and that doc
comment are evidence the command was never sent, not a shape to copy, and no
fixture in the corpus carries one. **The probe's header carries `UID = 0` and
`TID = 0xFFFF`**, which say no session and no tree: the probe asks whether the
transport and the server's SMB layer are alive, not whether any session or tree
still is, which is exactly the scope stated below. `0xFFFF` is SMB1's "no tree"
TID — the reference sends it on the tree connect that has yet to obtain one
(`internal/client/session.go:251`) — and `0` claims no session. That is reasoned
from the protocol's shape rather than inherited or measured, since the reference
sends no echo at all, so it is on the conformance script with the other untested
wire choices (see Acceptance Criteria). **`EchoCount` is 1**, and that is forced
rather than chosen. The server answers with as many replies as the count asks
for, all on the one multiplex ID; this design routes a completed transaction per
ID and fails the connection on a frame that routes to no request (see Frames
that are not replies), so at any count above one every reply after the first
would kill the connection the probe exists to vouch for. **The byte area is
empty**, `ByteCount = 0`: that field carries the bytes the server is being asked
to echo, and the probe has nothing to say — it treats any successful reply as
the signal it wanted and reads nothing out of what comes back. Nothing catches those
extra replies: the first one completes the probe, and a completed reply returns
its ID to the pool rather than retiring it, so they arrive on an ID the table
neither holds nor remembers as retired.

**A distinguishable error.** `Error::ConnectionLost` means "this connection had
already died; the next call will re-dial." It exists because transparent re-dial
cannot cover the mid-flight case: an operation that fails partway cannot be
safely retried, since writes are not idempotent. The honest contract is that the
*next* call re-dials, not the failed one, and the caller needs to be able to
tell that case apart from a genuine failure in order to act on it.

**A re-dial carries no handles across.** A `File`, a listing iterator or a
`Tree` holds a file ID, search ID, tree ID and user ID that mean nothing outside
the connection they were opened on, so when that connection is evicted every
handle on it is permanently invalid — and the tree cache entries go with the
connection they were keyed under. Re-dialling authenticates afresh and gets new
IDs; it does not revive the old ones. An operation on a stale handle is
`Error::ConnectionLost`, with the same contract as everywhere else: this call
fails, the next call through `Client` re-dials, and the caller re-opens what it
needs from there. This is the
first thing a consumer meets after an idle disconnect, so it is stated rather
than left to be discovered.

The cache must dial **single-flight**: several tasks meeting a cold cache for
the same key must produce one dial, not one each. smb-rs carries a
`// TODO: This is a bit racy` at exactly this point. **A dial in flight runs to
completion when its last waiter drops**, rather than being cancelled with them:
the dial is expensive, another caller is likely, and a connection dialled with
nobody left to want it is exactly what the cache exists to hold — it is cached
like any other and evicted like any other if nobody does come back (below). A
dial that fails is not cached, so finishing one nobody claimed creates nothing
durable. Cache state is behind interior mutability so that every method takes
`&self` — a cache that needs
`&mut self` forces every consumer to wrap the client in a mutex, which turns
"caches internally" into a process-wide lock.

**A cached connection idle far longer than that is evicted, not merely probed.**
The probe answers the connection a caller is about to reuse; eviction is for one
nobody comes back to. The window is a fixed multiple of the overall deadline —
twenty times it — rather than a knob of its own, so the two thresholds cannot be
configured into contradiction: the probe fires on reuse after one deadline of
idleness, and eviction closes the connection after twenty without any. Evicting
is what releases the cache's own reference; a handle still holding that
connection keeps it alive regardless, and the connection closes when that handle
drops. Without it the cache holds a strong reference for the process lifetime
and nothing is ever released.

**Eviction needs a component of its own, and this is the one place the design
adds one.** A connection nobody comes back to is by construction never reached
by a check performed on access, so a lazy sweep at cache lookup would leave
exactly the entries eviction exists for untouched. A per-`Client` timer task
drives it instead: it wakes every quarter of the eviction window — five overall
deadlines, twenty-five minutes at the defaults — drops the cache's reference to
every entry idle past twenty deadlines, and ends when
the `Client` does — `Client::close()` stops it along with everything else the
cache owns. That is a task the `Client` spawns and not something `Drop` does:
the guarantee that dropping a handle neither spawns a task nor requires a
running runtime (see Handle lifetime) is untouched by it.

**`Client::close()` is the shutdown**, and its signature is
`async fn close(self) -> Result<()>`, the same shape `close()` has on a `File`
and on a listing iterator (see Handle lifetime). It drops every reference the
cache holds — connections, sessions and trees alike. A connection whose last
handle has gone with it is closed there and then; a connection some live handle
still holds is closed when that handle drops. That is what makes shutdown
deterministic without invalidating handles a caller still owns: all the method
does is stop the cache being an owner. **The goodbye each closing connection
sends is awaited rather than raced against the socket close** — the
`TREE_DISCONNECT` per tree and the `LOGOFF_ANDX` for the session that a
deliberate teardown carries (see Handle lifetime) — because reporting that
release is the whole reason the method is fallible, and a fire-and-forget close
reports nothing. On failure the socket closes regardless and the error is
returned: there is nothing to retry, and TCP teardown releases what the server
still holds.

One consequence to state plainly: the pool bought parallelism *across*
connections, and a single cached connection per key is bounded by that
connection's negotiated `MaxMpxCount`. For this crate's workload that
ceiling is not binding; it is a real difference from the Go library nonetheless.

### Wire layer

Message structures use `binrw` derives. A plain derive round-trips the 32-byte
SMB1 header byte-identically against captured bytes, which is why a parsing
crate is worth taking over hand-rolled byte pushing at all.

`binrw` does not meet guiding principle 4's definition of established: it is at
0.15.2, pre-1.0, across 35 published versions. The risk is accepted as a
judgment with a reason rather than waved through as a category. It is
load-bearing for the entire wire layer and has no 1.0 alternative, so the choice
is `binrw` or hand-rolled bytes and nothing in between. And its release history
is maintenance of old lines rather than a forced march: 0.11.3, 0.12.1, 0.13.4
and 0.14.2 were all published after 0.15.1, which is backporting, not churn.
That is a materially different cadence from the smb-rs leaf crates, whose
rejection turned on a different balance — eight breaking minors in a year,
`=`-pinned so the family moves as a unit, to displace 2% of the code — under 3%
even with the generated status table set aside (see Alternatives).

The other pre-1.0 dependencies the crate takes are the RustCrypto primitives
NTLMv2 needs — `md4`, `md-5`, `hmac` and `digest` — plus `rc4` for the encrypted
session key, and they take the same judgment for a different reason. They do
move as a coordinated set, on every `digest`/`crypto-common` bump, which is the
churn shape that rejected the smb-rs leaf crates. What differs is the
alternative: there is no 1.0 RustCrypto line to take instead, and the only other
option is hand-rolling MD4, MD5, HMAC and RC4, which principle 4 prefers not to
do. The accepted cost is occasional manual triage: a `0.x` minor is held for a
human whatever the build says (see Self-maintenance). `des` is not among them:
it is needed only for LM and NTLMv1 responses, and this design is NTLMv2-only.

**A CSPRNG is a dependency too, and two things need it**: the NTLMv2 client
challenge and the session key exported under `NTLMSSP_NEGOTIATE_KEY_EXCH`. It is
`getrandom` rather than `rand`: what is wanted
is operating-system entropy and not a pseudo-random generator, and `rand`
depends on `getrandom` for exactly that, so taking `rand` would add a generator
this crate never draws from. `getrandom` is pre-1.0 like the primitives above
and takes the same judgment for the same reason: there is no 1.0 line to prefer,
and the alternative is reading the platform's entropy source by hand, which
principle 4 prefers not to do.
Two further pre-1.0 dependencies are taken on the same judgment, both because
every alternative is pre-1.0 too. The logging facade `tracing` is at 0.1 and its
only alternative `log` is at 0.4 — there is no 1.0 line to prefer either way
(see Security posture for what the crate emits through it). And `time`, at 0.3,
carries the crate's timestamps (see Configuration and timeouts) against `chrono`
at 0.4 and `jiff` at 0.2, so again there is no 1.0 line to prefer and the risk
is accepted rather than avoidable; what settles it among the three is that
`time` is what the smb-rs family uses, so a consumer holding both crates
converts between no date types at all — ecosystem agreement with the crate this
API's vocabulary follows.

**The header's `Flags` and `Flags2` are client-chosen fields like any other, and
the port sends `Flags = 0x18` and `Flags2 = 0xC801`.** The `Flags` byte is Go's
unchanged — `SMB_FLAGS_CASE_INSENSITIVE | SMB_FLAGS_CANONICALIZED_PATHS`, and
there is no reason to send anything else. `Flags2` is Go's `0xC803` less
`SMB_FLAGS2_KNOWS_EAS` (`0x0002`), leaving the four bits this port actually
relies on: `SMB_FLAGS2_UNICODE` (`0x8000`), `SMB_FLAGS2_NT_STATUS` (`0x4000`),
`SMB_FLAGS2_EXTENDED_SECURITY` (`0x0800`) and `SMB_FLAGS2_KNOWS_LONG_NAMES`
(`0x0001`) — Unicode strings, 32-bit NT statuses, extended security negotiation
and long names known (`internal/smb1/constants.go:134,142,145,146`, where the
`0x0001` bit carries the reference's own shorter name). The third of those is
the request-side half of the
`CAP_EXTENDED_SECURITY` floor (see Security posture): it is what says the
`SESSION_SETUP_ANDX` this port sends carries a SPNEGO blob rather than the
pre-extended-security fields, so a word built without it breaks the whole auth
path. `SMB_FLAGS2_IS_LONG_NAME` (`0x0040`, `constants.go:140`) is a different
bit: it is *not* among the four and it is *not* set. The
bit dropped claims the client understands extended
attributes, and this port implements none: it is the same false claim, removed
for the same reason, as `NTLMSSP_NEGOTIATE_ALWAYS_SIGN` and
`NTLMSSP_NEGOTIATE_VERSION` (see Security posture). Like those two it is an
untested wire change against all three servers — the Go client took every
capture, so every committed request carries `SMB_FLAGS2_KNOWS_EAS` — and it
joins them on the conformance script (see Acceptance Criteria).

**One dialect is offered, and the response is parsed by `WordCount` rather than
by the dialect.** The negotiate request offers `NT LM 0.12` and nothing else.
Go offers three — `NT LM 0.12`, `NT LANMAN 1.0`, `LANMAN1.0` — and the extra two
are what create the disagreement the evidence shows: against that three-entry
list Windows 11 24H2 answers `DialectIndex = 0` while both Samba-family servers
answer `1`, which is literally `NT LANMAN 1.0`, so the selection does not name
the dialect the server then speaks — all three return the same 17-word NT LM
0.12 response body regardless. A port that validated the selection by index, or
mapped the index back to a dialect name, would pass against Windows and fail
against the acceptance container. Offering one dialect removes the question: the
only index a conforming server may return is 0, and `DialectIndex = 0xFFFF` —
the server saying it accepted nothing on offer — is the single diagnosable
failure, refused with an error naming the absent common dialect rather than
parsed further. Any other index is refused the same way, since a server may only
choose from the list it was offered. The response shape is still keyed off
`WordCount` alone: 17 words is the NT LM 0.12 negotiate response this design
parses, and any other word count is refused as a dialect the port does not
implement.

**The two servers that agree are one implementation, not two.** The embedded
device's negotiate response is byte-identical to Samba's in every field that
matters — the same `Capabilities` of `0x8080F3FD`, `CAP_UNIX` included, the same
`MaxBufferSize`, the same dialect index — and the device says so in words as
well: its `IPC$` share comment reads `IPC Service (Samba 4.9.5-Debian)`. So the
family is the device's own claim rather than an inference from a matching
capability word, and the evidence covers two implementations rather than three.
Neither piece is checkable from a clone: the comment was read from the
git-excluded `spikes/device-asiair/` and the negotiate response from the equally
excluded `capture-vm/`. Every wire convention
below splits the same way, Samba-family versus Windows, with one implementation
on each side; where the device differs from the container it varies a size or a
supported command, never the convention.

**A response whose status is an error carries no words for most commands, and
the decoder branches on `WordCount` rather than assuming it.** SMB1 usually
answers a failed command with `WordCount = 0` and an empty byte area rather than
with a zeroed version of that command's successful response. Four committed
frames show it — the three `STATUS_DUPLICATE_NAME` tree-connect responses in
`capture-win-{a,b,frag}/0008-s2c-cmd75.bin`, and the
`STATUS_INSUFF_SERVER_RESOURCES` TRANS2 response in
`capture-win-a/0012-s2c-cmd32.bin` — each 39 bytes on the wire, header and
`ByteCount` and nothing else. A derive that reads
`TREE_CONNECT_ANDX_RESPONSE`'s words unconditionally fails on the first three of
those frames. The negotiate response above is this same branch applied to a
command whose *successful* shapes differ, not a rule of its own.

**A server may also answer outside NT status altogether, and the header says
so.** `SMB_FLAGS2_NT_STATUS` is a *per-message* flag, and a response may clear
it however the request was flagged: Windows answers a malformed RAP request in
DOS error format, `ERRSRV`/`ERRerror` under `Flags2 = 0x8803`, where those four
header bytes are an error class, a reserved byte and a 16-bit code rather than a
32-bit `NTSTATUS`. The port cannot provoke this — it is the reference's
`SetupCount` defect that earns it (see Where the Go library is the oracle, and
where it is not) — but reading the flag costs one branch, and not reading it
means reporting a status number that means nothing. So the decoder checks the
flag before it reads the status, and a response that clears it surfaces as a
named error saying the server answered outside NT status rather than as a
fabricated `NTSTATUS`. Mapping the DOS class and code onto NT statuses is **not**
done: the capability floor requires `CAP_STATUS32`, so a server doing this is
outside what this port targets, and the honest report is that it happened.
`spikes/capture-win-rapsetup/0010-s2c-cmd25.bin` is the frame.

**The rule is not universal, and reading it as universal breaks
authentication.** `STATUS_MORE_PROCESSING_REQUIRED` (`0xC0000016`) sits inside
the `0xC` class the port otherwise classifies as error, and the
`SESSION_SETUP_ANDX` response carrying it has `WordCount = 4` and a 297-byte
byte area — that frame is the NTLM challenge, so a decoder that reads no words
from an error-class response cannot authenticate at all. It is not an error: it
is the middle leg of the session setup, classified as continuation before
anything branches on the status class, which is how the Go library survives it
too — `Header.IsError()` special-cases exactly this status
(`internal/smb1/packet.go`). Decoding therefore branches on the status *and* on
the `WordCount` the frame actually carries, never on the status alone. The
counterexample is in `capture-vm/`, which the corpus rules exclude, and the
four committed frames are all the corpus has — a second-order effect of the
privacy rule worth recording: it removed the frames that would have falsified
the wider claim (see Fixture obligations).

**Absolute offsets need back-patching, and there are four such sites in two
shapes**: `TRANS2` and `SMB_COM_TRANSACTION` (the RAP and named-pipe paths) both
carry `ParameterOffset`/`DataOffset` computed from the start of the SMB message,
and `WRITE_ANDX` and `READ_ANDX` each carry a `DataOffset` that must be written
on encode and honoured on decode. A derive cannot express these, so a small
offset helper is written for them. It is far smaller than the 658-line
`PosMarker<T>` smb-rs needs, because SMB2 carries offsets nearly everywhere and
SMB1 does not — but it serves four sites in two shapes, not one, and is sized
accordingly.

**Alignment is a separate mechanism from offsets, and neither side infers it.**
Directory entries are padded — Samba to 4 bytes, Windows mostly to 8 — and the
walk never computes an entry's size for itself; it follows `NextEntryOffset`,
which carries the padding already. "Mostly" is load-bearing: one server is not
even internally consistent about its own stride. The `.` entry in
`capture-win-b/0012` has a 96-byte body under a `NextEntryOffset` of 100 — four
gratuitous bytes past a size that needs no padding at all — while
`capture-win-frag/0012` gives that same entry 96 and none. The same server emits
different offsets for identical content, which is the thing to take from it. So the
walk is bounded by the declared counts and by `NextEntryOffset` and never by an
assumed stride: a decoder that derives an entry's end from a padding rule is
already wrong against frames in the corpus.

On encode, the pad bytes between the SMB header, the parameter block and the
data block are part of what the offset helper is computing over, and getting
them wrong moves every offset with them: this campaign lost time to a
4-versus-2-byte parameter-block alignment mistake. The encoders' padding is
therefore pinned by fixture bytes rather than reasoned about, which is what
build order step 1 is for.

A third alignment site belongs to neither mechanism and is a classic SMB1 bug:
a UTF-16 name in a command's byte area has to begin on a 2-byte boundary
measured from the start of the SMB header. It is not block padding and the
offset helper does not compute it; what lands the name on that boundary is
written and expected per command, and getting it wrong — omitting it, or adding
one where the reference adds none — shifts every character of the name by a
byte and produces a frame the server cannot parse. **Five commands carry the
problem and no two solve it the same way** — and the fifth is the reason the pad
is computed from a running offset rather than written as a per-command constant.
The first four sit at fixed offsets, so their pads could in principle be
constants; `SESSION_SETUP_ANDX`'s cannot, because a variable-length field
precedes the strings. One rule covers all five: parity is a property of the
offset from the start of the SMB header, and anything of variable length ahead
of a string moves it.

- **`NT_CREATE_ANDX`.** The byte area begins at offset 83 — header 32,
  `WordCount` 1, parameters 48, `ByteCount` 2 — which is odd, so a single pad
  byte precedes the name (`internal/smb1/file_ops.go:312-321`).
- **`TREE_CONNECT_ANDX`.** The byte area begins at 43, also odd, but what
  precedes the path is not padding: the reference declares `PasswordLength = 1`
  and sends one null password byte, and that is what puts the path on an even
  offset (`internal/client/session.go:236-237`,
  `internal/smb1/tree_connect.go:119-132`). Writing that byte as a pad while
  leaving `PasswordLength` at 0 mis-declares the field, and the server reads
  the path a byte early.
- **`SMB_COM_RENAME`.** Two names, and only the second is padded. The data
  section is `0x04`, the old name, its terminator, `0x04`, **one pad byte**, the
  new name, its terminator (`internal/smb1/rename.go:68-90`). The byte area
  begins at 37, so the first `0x04` already lands the old name on 38; after an
  even-length name and its two-byte terminator the second `0x04` lands on an
  even offset, which is what makes the pad necessary there and only there. The
  encoder says both halves in its own comments — "No padding needed -
  OldFileName is already aligned at even offset" (`:69-70`) and "Always add
  padding byte to align NewFileName to word boundary" (`:83-84`). Padding the
  old name as well shifts every character of it.
- **`SMB_COM_TRANSACTION`.** The two pipe paths carry different `SetupCount`s
  and so begin their byte areas at different offsets, both of them odd. On
  `TRANS_TRANSACT_NMPIPE` the setup words are the subcommand (`0x0026`) and the
  pipe's FID, so `SetupCount = 2`, sixteen words, and the byte area begins at
  67 — header 32, the `WordCount` byte 1, sixteen words 32, `ByteCount` 2. On
  the RAP path [MS-RAP] 2.1 sends `SetupCount = 0`, so there are fourteen words
  and the byte area begins at 63. Odd either way, so a single pad byte precedes
  the `Name`, as on `NT_CREATE_ANDX`. This site is the port's and not the
  reference's: an 8-bit name needs no boundary and the reference writes no pad,
  which is the other half of the spelling defect recorded with the named-pipe
  paths below. `spikes/capture-win-rap/0009-c2s-cmd25.bin` carries the port's
  RAP shape exactly — `SetupCount = 0`, one pad byte, `\PIPE\LANMAN` as UTF-16LE
  from 64, `ParameterOffset = 90` twenty-six bytes after it — while
  `spikes/capture-rap/0009-c2s-cmd25.bin` is the same request with the
  reference's two setup words still in it, which puts those at 68 and 94.
  `spikes/capture-nmpipe/0011-c2s-cmd25.bin` is the transact-mode shape:
  `\PIPE\` from 68 and `DataOffset = 82` fourteen bytes after it.

- **`SESSION_SETUP_ANDX`.** The byte area begins at 59 — odd — and the
  `NativeOS` and `NativeLanMan` strings sit *after* the security blob, whose
  length varies with the SPNEGO token. So the pad depends on that length and
  cannot be written as a constant: with the reference's 376-byte blob the
  strings land at 435, odd, and a server honouring the alignment reads every
  character of both a byte late. That is measurable rather than theoretical —
  Samba logs `NativeOS=[渀椀砀]` for bytes that decode as `Unix` from even
  parity — and it is the one site where the reference is wrong in this way
  rather than in its spelling (see Where the Go library is the oracle, and where
  it is not). The port sends its own crate-identifying strings here (see
  Security posture), behind its own variable-length blob, so it meets the same
  arithmetic and must compute the pad.

Deleting adds no sixth: it sends no
`SMB_COM_DELETE`, reaching the path through `NT_CREATE_ANDX` instead (see Public
API → Filesystem verbs), which is already the first of the five.

**`ByteCount` is 16 bits and wraps, and must never be used as the length.**
Measured against the live Samba container during the design session and
committed since: a 130,048-byte write carries `ByteCount = 64512` with
`DataLengthHigh = 1`, and a 130,048-byte read reply carries
`ByteCount = 64513`. Both frames are in `spikes/capture-large/` —
`0027-c2s-cmd2f.bin` and `0018-s2c-cmd2e.bin` — and neither is in a logged
finding. A derive written the obvious way —
`#[br(count = byte_count)]` — yields 64,513 of 130,048 bytes: a silent short
read of exactly the class invariant 1 forbids. Lengths come instead from the
fields that carry them at full width: the NetBIOS frame length bounds the
message, and `READ_ANDX`'s `DataLength | DataLengthHigh << 16` together with its
`DataOffset` locate the payload inside it, which is what the Go library does
(`internal/smb1/file_ops.go:441-447`). The frame length alone is not the rule —
deriving the payload length from it silently absorbs whatever trailing padding a
server appends. Note also that the NetBIOS length field is read as **17 bits**,
not 16: the byte following the message type contributes its low bit as the
length's high bit, which is what allows the 130,108-byte frames this design
cites. Seventeen is a choice rather than a fact about the wire — direct TCP
framing on port 445 reads that byte and the two after it as a 24-bit length,
where the NetBIOS session service treats the other seven bits as reserved. The
client reads 17 and requires those seven to be zero, which is what bounds the
largest inbound frame it will allocate for at 131,071 bytes; reading 24 would
raise that bound to 16,777,215 bytes for no message this design sends or
expects. The fixtures large enough to catch any of this are committed:
`spikes/capture-large/` carries frames of 130,112 and 130,115 bytes on the wire
(see Fixture obligations).

**No AndX chaining.** Across the twenty committed capture directories, 242
frames carry an AndX-family command byte and 237 of those carry AndX words; none
chains — every `AndXCommand` is `0xFF`. The other five are the zero-word error
responses above, which carry no AndX fields to chain. The port needs no chaining
machinery, and what it does with a response that chains anyway is decided with
the other two connection-fatal frame conditions (see Frames that are not
replies). `AndXOffset` is a separate field and must **not** be asserted zero
alongside that sentinel: thirteen committed frames — tree-connect, logoff and
`NT_CREATE_ANDX` responses, all from Windows — carry a non-zero `AndXOffset`
with `AndXCommand = 0xFF`. In all thirteen the offset equals the SMB message
length exactly: 54 and 48 bytes in the tree connects, 39 in the logoffs, 103 in
the creates. The sample grew from five with the live Windows runs and the rule
held across every one, over a third command and a second tree-connect size — so
a parser that seeks to it before checking the sentinel lands precisely on the
buffer boundary:
the bug surfaces as an empty read at the end of the message rather than as an
out-of-range seek that would be caught. The sentinel is what says there is no
next command; the offset beside it is read and ignored.

**Directory chains are bounded by `DataCount` and stop on a zero
`NextEntryOffset`.** Windows zero-terminates and leaves six bytes of trailing
padding. Samba's last entry instead points just past itself: its
`NextEntryOffset` is that entry's own padded size, so the chain lands exactly on
the `DataCount` boundary, which is why bounding the walk by `DataCount`
terminates correctly there. That property is one of a *complete* reply and not
of every message: in `spikes/capture/0010` the terminal entry begins at 552 and
measures 112, landing on `DataCount` = 664, and `spikes/capture-frag/0028` does
the same with 180 + 180 = 360, while a fragment does not — the trailing entry of
`spikes/capture-frag/0010` begins at 16,396 and measures 180, four bytes past
that message's `DataCount` of 16,572. It is one more reason the walk runs over
the reassembled buffer and never over a single message (see Routing and
reassembly). The terminal entry's size tracks the filename length and is no
fixed number: 112 bytes in `capture/0010`, whose last name is 8 characters,
against 180 bytes where the names are 42 characters — both Samba — and 132 bytes
on the embedded device, which being Samba-family varies the size rather than the
convention. That 132 is finding W2's in `notes/01-rust-port-spike.md`, not W8's:
W8 collects the numbers and decodes the other two from committed fixtures, while
the 132 was read from the git-excluded `capture-vm/` and is not checkable from a
clone. Each convention
defeats a walker that honours only the other. Reading Windows with a
`DataCount` bound alone recognises no terminator at all: the zero that ends the
chain is not one to it, and the walk hard-errors on that zero rather than
returning a wrong count. Walking Samba with the zero terminator
alone never meets a terminator: the terminal entry's `NextEntryOffset` sends the
walk past the end of the data. Both terminators are therefore kept. The walker
additionally rejects a `NextEntryOffset` below the minimum entry size, so a
malformed reply cannot re-parse overlapping bytes into fabricated entries — but
the order of those two checks is part of the rule and not an implementation
detail: **the zero terminator is tested first**. Reversed, `0 < 94` rejects
every Windows listing as malformed; and a walker that skipped the check and
simply advanced by a zero `NextEntryOffset` would sit on one entry forever
rather than erroring. It also cross-checks the walked count against the count
the reply itself reports having returned in `SearchCount`, and a mismatch is an
error rather than a logged oddity: the chain and the count are two statements
about the same reply, and a reply that disagrees with itself is the same class
of defect as a chain that ends short.

**Share enumeration keeps both paths.** RAP over `\PIPE\LANMAN` is tried first
and DCE/RPC `srvsvc` is the fallback. smb-rs's `smb-rpc` is NDR64-only and
salvages nothing, so this is hand-ported. Both paths ask for information level
1, which is what carries a share's name, kind and comment — the three
`Client::list_shares` hands back (see Public API).
Two response classifications matter
here and both are wrong in the Go library, but they are wrong in different ways
and the port does not treat them alike. `STATUS_BUFFER_OVERFLOW` is not in the
`0xC0000000` class and so reads to Go as success. It says the response did not
fit the request that asked for it, and it belongs to the pipe-read loop here
rather than to the actor's reassembler (see Routing and reassembly): in the
write/read mode it arrives on the `READ_ANDX`, which is not a transaction at
all, and in the transact mode it arrives on a *completed* `SMB_COM_TRANSACTION`
reply whose pipe payload was truncated. Either way the remedy is another
`READ_ANDX` on the pipe until the response is whole, never more transaction
fragments. Go
issues a single 64 KiB read and never loops, so the read loop is something the
port has and the Go library does not. RAP's `ERROR_MORE_DATA` is a different
answer: it says the share list did not fit the RAP reply. The port does **not**
retry it with a larger receive buffer — the transaction ceiling may not permit
a larger one (see Sizing transactions), and the machinery for a RAP that cannot
deliver already exists. It is treated as RAP being unable to produce the list,
and share enumeration falls through to the DCE/RPC path exactly as
`STATUS_NOT_SUPPORTED` does. Go treats `ERROR_MORE_DATA` as a hard failure and
enumerates nothing. That is RAP's condition alone: srvsvc answers with the same
name for a list that pages, and there it is a loop rather than a fall-through
(see `NetrShareEnum` pages, below).

**Windows does not serve RAP at all, so the fall-through to DCE/RPC is required
rather than defensive.** A `NetShareEnum` request with nothing wrong with it —
`Transaction Name: \PIPE\LANMAN` in UTF-16LE, `MaxParameterCount = 64`,
`MaxDataCount = 65472`, `MaxSetupCount = 0`, `SetupCount = 0`, under
`Flags2 = 0xC803` — is answered `STATUS_NOT_SUPPORTED` (`0xC00000BB`) by
Windows 11 24H2 (`spikes/capture-win-rap/`), and the same request with the name
8-bit and `SMB_FLAGS2_UNICODE` cleared is refused identically
(`spikes/capture-win-rap-ascii/`). Unlike both Samba-family servers, where the
spelling is the whole cause and either spelling is answered once it is corrected,
the spelling is not the cause here: the server does not implement the transport.
What that costs is nothing, because the client falls through — the same corpus
enumerates four shares over `srvsvc` — and it is what a port carrying only RAP
would lose entirely.

**The named-pipe transport has two modes, and the port implements both.** A
DCE/RPC exchange on `\PIPE\srvsvc` is carried either by `TRANS_TRANSACT_NMPIPE`
— one `SMB_COM_TRANSACTION` carrying the request and returning the response — or
by writing the request to the pipe's file ID with `WRITE_ANDX` and reading the
response back with `READ_ANDX`. In the capture the reference library took
against the embedded device, **every** `SMB_COM_TRANSACTION` was refused, RAP
and DCE/RPC alike, with `STATUS_NOT_SUPPORTED`: the sequence is TRANSACTION bind
refused, `WRITE_ANDX` bind accepted, `READ_ANDX` returning `bind_ack`,
TRANSACTION request refused, `WRITE_ANDX` request accepted, `READ_ANDX`
returning the share list. Go's fallback is what makes enumeration work for that
client (`internal/client/file.go:1337-1384`).

**That capture recorded a defect in the client that took it, not a property of
the device.** An earlier position here had the device forcing RPC over the
write/read mode, so that a port implementing only the transact mode would
enumerate nothing against it. The capture was taken with the reference library,
which mis-spells the RAP transaction's `Name` and omits the transact mode's
altogether (see Where the Go library is the oracle, and where it is not) — and
**a stock, healthy Samba returns exactly `STATUS_NOT_SUPPORTED` for both of
those defects**, then answers both subcommands as soon as the name is supplied.
A corrected harness pointed at the device gets exactly that: RAP answered under
either spelling and `TRANS_TRANSACT_NMPIPE` answered under either, every one
`STATUS_SUCCESS` (`spikes/device-asiair/`, git-excluded because those frames
carry the device's real share names). The device is an ordinary Samba-family
server that met a defective client, and the refusal was the client's.

**The write/read mode is kept as a hedge with no tested server behind it, and
the RAP fall-through beside it is the opposite.** All three servers answer
`TRANS_TRANSACT_NMPIPE` once the `Name` is supplied: the container
(`spikes/capture-nmpipe/`), the embedded device (`spikes/device-asiair/`), and
Windows, whose whole `srvsvc` exchange rides on `SMB_COM_TRANSACTION` — both
calls `STATUS_SUCCESS`, no `WRITE_ANDX` or `READ_ANDX` anywhere
(`spikes/capture-win-nmpipe/`). The transact-to-write/read fallback is therefore
exercised by no server this campaign has tested: what was once a measured
requirement, and then a hedge against one device, is now a hedge against servers
nobody has seen. It is kept because the two costs are not comparable — a port
carrying only the transact mode enumerates nothing against a server that refuses
one, while carrying the second mode costs code that never runs — and because RAP
shows that a server refusing a transaction two others answer is not
hypothetical. That is what separates the two fall-throughs, and this document
does not blur them: the RAP-to-DCE/RPC one has a tested server that requires it,
and the transact-to-write/read one has none.

**The transaction `Name` the port sends agrees with its own header, and both
modes carry one.** An `SMB_COM_TRANSACTION`'s `Name` is a string in the byte
area like any other, so under the `Flags2` this port sends — which sets
`SMB_FLAGS2_UNICODE` on every request, as above — it is UTF-16LE:
`\PIPE\LANMAN` on the RAP path, and `\PIPE\` on `TRANS_TRANSACT_NMPIPE`, which
is the name [MS-CIFS] requires there. Neither half is inherited. The reference
writes that name as 8-bit ASCII under its own `0xC803`, and sends the
transact-mode request with no name at all, and both are recorded as known-wrong
(see Acceptance Criteria → Where the Go library is the oracle, and where it is
not). The first is what `spikes/capture-trans/` captures, and it is worth not
mistaking for the device capture above: the Samba container refuses every
`SMB_COM_TRANSACTION` the reference sends it with that same
`STATUS_NOT_SUPPORTED`, and the enumeration completes over the write/read
fallback there too — but for a client-side reason and not because the container
lacks the command, since correcting the spelling makes that same container
answer RAP (`spikes/capture-rap/`).

**The transact fall-through's trigger stays wide, and the Windows evidence
closes that question rather than licensing a narrowing.** Go falls back from
transact to write/read on *any* error. That is sloppy — it turns an unrelated
failure into a second full attempt — but it never fails to enumerate, and the
port keeps it. An earlier position here held that narrowing the trigger to
`STATUS_NOT_SUPPORTED` would rest on the embedded device alone, and that the
narrowing was a change to make once there was Windows evidence for it. There is
now, and it runs the other way on both fall-throughs. On the RAP one, Windows
answers a well-formed `NetShareEnum` with exactly that status (above), which
makes `STATUS_NOT_SUPPORTED` the one condition that fall-through cannot stop
triggering on: excluding it breaks share enumeration against Windows outright.
On the transact one, Windows contributes no error at all, since it answers the
subcommand — so narrowing that trigger to `STATUS_NOT_SUPPORTED` would cost
nothing measurable, and there is still no server-side evidence for choosing any
narrower set than "any error", the only `STATUS_NOT_SUPPORTED` ever recorded
there being the one a defective client earned. So the port falls back on any
error from the transact attempt too, and it keeps the first error rather than
discarding it, so a failure of both attempts still says why the transact attempt
failed. **Read "there is Windows evidence now" as closing this question, not as
reopening it**: the evidence is what makes the wide trigger the tested choice,
and the status it would have been narrowed to is the one the other fall-through
depends on.

**A DCE/RPC response arrives in one or more PDUs, and assembling them is a
second layer of fragmentation sitting above the SMB one.** The two are
independent and the port keeps them so. Underneath, the SMB layer delivers one
complete `SMB_COM_TRANSACTION` reply, or a pipe read looped until the response
is whole; what those carry is a byte stream of DCE/RPC PDUs, and `rpc/`
assembles it for itself. A response is complete when a PDU carries
`PFC_LAST_FRAG`: stub data accumulates from each PDU until then, and only the
assembled stub is parsed — never a single PDU, exactly as the entry walk runs
over a reassembled transaction and never over one message. A stream that ends
without `PFC_LAST_FRAG` is an error and not a short result, the same
complete-or-error rule invariant 1 states one layer down. This is the port's own
code with nothing behind it: Go never inspects the flag inbound —
`internal/dcerpc/request.go:52` sets it outbound only, and `:89`'s
`DecodeResponse` never reads it back — and `Tree.RPCRequest`
never loops — and the only fixture this path has is a single-PDU
response from a device with few shares (see Fixture obligations), so a server
with many shares is where the loop first matters and where a port without it
truncates silently.

**`NetrShareEnum` pages, and its own `ERROR_MORE_DATA` is not RAP's.** srvsvc
returns `ERROR_MORE_DATA` together with a **resume handle** when the share list
does not fit the response it can return, and unlike the RAP case there is no
further path to fall through to — DCE/RPC is already the fallback. The port
loops: it re-issues `NetrShareEnum` carrying the resume handle the previous
reply returned, accumulating entries, until a reply comes back successful. A
list handed to the caller with `ERROR_MORE_DATA` unresolved is an error and
never a short answer — the silent-truncation class invariant 1 forbids, reached
through the one module with no oracle. The loop carries the no-progress guard
the listing and read-fill loops carry: a reply that adds no entries and does not
end the enumeration is an error rather than another round.

**That guard does not bound the loop, so a round cap does.** A server adding one
entry per round makes progress by the guard's measure and pages for ever, while
the accumulating list grows without limit — which contradicts the crate's own
claim that allocation from untrusted input is bounded wherever it happens (see
Security posture). The loop therefore gives up after **64 rounds**, which is the
fragment cap from Routing and reassembly used for the same purpose and with the
same reasoning: a liveness bound against a server that never finishes, chosen
far above what any real answer needs rather than derived from the reply size.
Four shares came back in one round from Windows and two from the container, so
nothing observed approaches it.

**RAP's receive buffer is not spelled that way, and the two numbers have to
agree.** A RAP `NetShareEnum` request carries its own 16-bit receive-buffer
size, and every capture in the corpus sets it to `0xFFFF` because the reference
asks the SMB layer for `MaxDataCount = 65535` to match. This port asks for
65,472 (see Sizing transactions), so it sends **65,472 there too**. Telling RAP
it may build a larger reply than the transaction is willing to return would earn
a reply the connection layer then refuses for exceeding what the request asked
for — a self-inflicted failure the reference never meets, because its two
numbers happen to agree. Whatever the transaction asks for is what RAP is told.

**The srvsvc request asks for `PreferedMaximumLength = 0xFFFFFFFF`**, the value
the reference sends (`internal/srvsvc/netshareenum.go:76-77`) and the value this
port sends. The asymmetry with RAP above is real and follows from the field: this
one is 32-bit and advisory, so declining to cap costs nothing and the SMB layer
beneath still bounds any single reply. It is the "no limit of my own" spelling: the client declines to cap
the reply, so what decides whether the loop above is entered at all is the
server's own idea of how much it will return, and nothing the client picked. A
smaller figure would only page more often, since the SMB layer beneath already
bounds any single reply — by the transaction ceiling in the transact mode (see
Sizing transactions) and by the pipe read that collects it in the other.

**SPNEGO** encodes as DER and decodes as lenient BER, because real servers emit
indefinite-length encodings. The token shapes are hand-rolled rather than
decoded through a general ASN.1 crate: the grammar the client exchanges is
closed and tiny, and a general decoder is a larger attack surface for a
security-adjacent parser reached before authentication. Three shapes cover the
exchange at its longest:

- **encoded** — the `NegTokenInit` the client sends in SESSION_SETUP_ANDX,
  inside its GSS-API `initialContextToken` wrapper (`[APPLICATION 0]`, SPNEGO
  OID), carrying `mechTypes` of NTLMSSP alone and the NTLM NEGOTIATE message as
  `mechToken`;
- **decoded** — the `NegTokenResp` (`[1]`) the server returns, carrying
  `negState`, `supportedMech` and the NTLM CHALLENGE as `responseToken`;
- **encoded** — the `NegTokenResp` the client sends back, carrying the NTLM
  AUTHENTICATE message as `responseToken` and the `mechListMIC`, with the
  GSS-API wrapper stripped rather than emitted.

The `NegTokenInit2` a server puts in its negotiate response is not among them:
nothing in the exchange depends on it and the Go library does not parse it
either.

**The exchange can also end after the first leg, and the second and third shapes
are then never exchanged.** A server that answers the client's
SESSION_SETUP_ANDX with `STATUS_SUCCESS` rather than
`STATUS_MORE_PROCESSING_REQUIRED` has issued no challenge and wants no
AUTHENTICATE message: the session is set up, and the client sends nothing
further (`internal/client/session.go:98-111`). This is not a curiosity to
tolerate — it is precisely the shape a guest downgrade takes, a server declining
to challenge credentials it has decided not to check. So the guest check runs on
this path exactly as it does on the longer one: the `Action` bit of that same
response is read before the session is handed back, and a guest logon the caller
did not ask for fails there (see Security posture).

### Paths

`UncPath` is validated on construction and on parsing, unlike smb-rs's, whose
`FromStr` bypasses even the checks its own constructor performs and accepts
`\\\\` as an empty server and empty share. Share names containing spaces are
valid and are carried verbatim; no escaping or quoting is applied, because none
belongs on the wire.

**The path carries a port for dialling and never carries one on the wire.**
`UncPath`'s server component is a host and an optional port:
`\\127.0.0.1:10445\testshare` says where to connect, and the tree connect it
produces says `\\127.0.0.1\testshare`. An earlier position in this design had
the path carrying no port at all, on the ground that the transport address is
configuration rather than identity, and that was wrong in a way nothing else
covered: no other part of the API carries an address — `Client::tree` takes a
UNC path, `Client::list_shares` takes that same server component on its own, and
`ClientConfig` carries none — so the rule left every server not listening on 445
unreachable, the acceptance container this campaign runs against among them.

**Server-name components are built from the host alone, never the dial
address**, and one construction path serves every use so they cannot drift apart
again. That is the half of the rule the Go library gets wrong: it builds share
paths without the port and the IPC$ path
*with* it, producing `\\host:445\IPC$`, which Windows rejects with
`STATUS_DUPLICATE_NAME` on the `TREE_CONNECT_ANDX` — so share enumeration fails
against Windows for that reason alone, while Samba and the embedded device
tolerate it. That is reproduced live and twice over rather than inferred:
`spikes/capture-win-control/` is the unpatched reference library meeting
Windows 11 24H2, and `spikes/capture-win-ipcport/` is the same client with every
*other* known defect corrected and the port alone left in, earning the same
refusal — which is what makes the port, and nothing else in the frame, the thing
the status answers. It leaks into a
third place besides: the `ServerName` the srvsvc RPC call carries
(`session.go:368`). **The host goes on the wire as the caller wrote it**, case
included: the lowercasing under Connection caching and reconnection normalises
the cache key and nothing else, and no request carries that key.

**A server is reachable over IPv6 only by a name, and that is the stated cost of
one address surface.** SMB1's UNC syntax has no IPv6 literal form — Microsoft's
workaround is a separate `ipv6-literal.net` name transform, which this design
does not implement — so the host a server-name component is built from must be a
hostname or an IPv4 literal. Because the path is the only address anything in
this API carries, that limit reaches the dial address too: a UNC path can name
no IPv6 address to connect to, and reaching such a server means naming it by a
hostname that resolves to one, which dials like any other hostname and puts the
hostname on the wire. A literal offered in a path is refused with an error
saying exactly that, rather than being carried onto the wire mangled — and the
parser accepts the bracketed form IPv6 requires, `[2001:db8::1]:445`, precisely
so that it recognises one and refuses it instead of splitting on the last colon
and mangling it into a host and a port. The limitation is accepted rather than
designed around, because both alternatives are worse for a case the operator's
targets do not present: a second address parameter beside the path would give
the API two address surfaces where the port rule above settled on one, and the
`ipv6-literal.net` transform is a name mangling this design declines.

**A path inside a share is accepted on a stated policy, not on whatever the
server makes of it.** Every path a `Tree` verb takes is normalized and checked
before it reaches the wire, in one place, and the rules are these.
**Normalization does two things and nothing else**: it rewrites `/` to `\`, so
that a caller writing `dir/file.txt` is not made to know that the wire wants
backslashes, and it trims Unicode whitespace from both ends — not just ASCII
spaces, since a legacy server can hold a name with a non-breaking space in it —
which is what the reference does too (`session.go:1575-1577`). What comes out of
that is the form the request carries, with one exception: `SMB_COM_RENAME`
puts a leading backslash in front of each of its two names on the wire,
matching the reference (see Public API → Filesystem verbs). What a caller may
hand in is unaffected by that. An absolute path is rejected: a path is
relative to
the share root, and there is nothing for a leading separator to mean. A path
containing a null byte is rejected, since it can only be a truncation waiting to
happen in whatever reads it at the other end. And a path that escapes the share
root is rejected: `..\..\etc\passwd` is
refused here rather than sent for the server to have an opinion about, because a
caller joining a user-supplied name onto a prefix should not be able to reach
outside the share it connected to.

**That last check resolves `.` and `..` to reach its verdict, and resolving them
is all it does with them.** The check walks the components and tracks depth, so
an escape cannot be evaded by spelling it differently; the path that goes on the
wire is the normalized one the caller gave, components and all. `a\..\b.txt`
passes the check and is sent as `a\..\b.txt`, not as `b.txt` — the port does not
rewrite a path it has decided is safe, which is what the reference does as well
(`session.go:1491-1549`). Go applies the same three refusals, and its own
normalization does the same two things: the trimming unconditionally and the
separator rewrite behind a flag (`session.go:1491-1600`). Here both are
unconditional, because a path policy a caller can turn off is one no caller can
rely on.

### Security posture

The crate does not sign messages and cannot encrypt — SMB1 has no encryption.
**This is stated in the crate's own user-facing documentation**, not only in a
contributors' file, because a published crate that does not sign should say so
where its users will read it. Signing itself is deferred — see Non-goals.

**The client advertises `NTLMSSP_NEGOTIATE_SIGN` and does not advertise
`NTLMSSP_NEGOTIATE_ALWAYS_SIGN`.** Advertising a signing capability that is
never exercised looks like a defect worth removing, and removing it breaks
Windows outright. Measured against Windows 11 24H2 and the Samba container
(finding W7 in `notes/01-rust-port-spike.md`):

| Flags advertised | Windows | Samba |
|---|---|---|
| `SIGN` + `ALWAYS_SIGN` (as Go sends) | authenticates | authenticates |
| `SIGN` only | authenticates | authenticates |
| `ALWAYS_SIGN` only | `STATUS_INVALID_PARAMETER` | authenticates |
| neither | `STATUS_INVALID_PARAMETER` | authenticates |

Windows requires `SIGN` and is indifferent to `ALWAYS_SIGN`. The embedded device
was not in that sweep, so dropping `ALWAYS_SIGN` is untested against it; the
conformance script carries the check (see Acceptance Criteria). The likely
mechanism is the key exchange: `NTLMSSP_NEGOTIATE_KEY_EXCH` is set, and the
encrypted session key it carries is only meaningful when signing or sealing is
negotiated, so dropping `SIGN` produces an AUTHENTICATE message Windows reads as
malformed. Whatever the cause, the flag stays and the reason is recorded here so
it is not "cleaned up" later.

**`NTLMSSP_NEGOTIATE_VERSION` is dropped as well, and for the same reason
`ALWAYS_SIGN` was.** The Version flag carries a structure claiming a Windows major,
minor and build, and Go claims Windows 10. It is informational, nothing in the
exchange depends on it, and asserting a Windows version this crate is not is the
same class of false claim as advertising a signing capability it does not
perform. Both removals are untested wire changes, and both are on the
conformance script (see Acceptance Criteria).

**The NEGOTIATE message carries these nine flags and no others**, and they are
taken from [MS-NLMP] section 2.2.2.5, which gives both the names and the bit
values:

  `NTLMSSP_NEGOTIATE_UNICODE`, `NTLMSSP_REQUEST_TARGET`,
  `NTLMSSP_NEGOTIATE_NTLM`, `NTLMSSP_NEGOTIATE_SIGN`,
  `NTLMSSP_NEGOTIATE_EXTENDED_SESSIONSECURITY`,
  `NTLMSSP_NEGOTIATE_TARGET_INFO`, `NTLMSSP_NEGOTIATE_128`,
  `NTLMSSP_NEGOTIATE_KEY_EXCH`, `NTLMSSP_NEGOTIATE_56`.

Nine is Go's eleven less the two dropped above: its set is exactly these plus
`ALWAYS_SIGN` plus `VERSION`. The set is nevertheless enumerated from the
specification rather than read out of Go's constant, which is what keeps `auth/`
clean of the go-smb2 lineage the write-from-spec decision exists to avoid (see
Licensing) — that constant lives in a package documented as adapted from
go-smb2, so citing it as the source of the port's flags would reintroduce
exactly the derivation the decision forecloses. The bits are load-bearing and
not a formality: without `SIGN`, Windows answers `STATUS_INVALID_PARAMETER` and
authentication never happens at all, as the table above measures.

**The server's advertised signing requirement is checked and reported**, and it
is documented as necessary but not sufficient. A server that honestly sets
`NEGOTIATE_SECURITY_SIGNATURES_REQUIRED` gets a distinct error naming signing as
the cause, which removes a class of failure that otherwise surfaces as
access-denied and sends the operator looking at credentials. It cannot be the
detection mechanism in general: Windows 11 24H2 with `RequireSecuritySignature`
set to true reports `SecurityMode = 0x03`, with neither signature bit set. That
same `0x03` is what all three tested servers report, so the check has no fixture
coverage at all — no committed negotiate response carries a server that admits
to requiring signing, and only the manual conformance script can ever exercise
it (see Acceptance Criteria).

**Logging goes through `tracing`, and the crate emits without configuring it.**
It is what an async Rust library is expected to use, its spans survive across
await points, and a consumer that prefers `log` bridges the two in one line. No
subscriber is installed — where diagnostics go is the binary's decision, not a
library's. Two rules bound what the crate emits.

**Credentials never reach a log.** The pass-the-hash-equivalent NT hash and the
password have redacted `Debug` implementations, with a test asserting the secret
does not appear in their formatted output — a redacted `Debug` is exactly what a
later `#[derive(Debug)]` silently undoes. More importantly the same material
travels in the SESSION_SETUP_ANDX request bytes, so the wire tracer redacts that
message's byte section and the NTLMSSP token inside it **unconditionally**,
never behind a feature flag. A hex dump added while debugging a wire problem is
otherwise a complete, offline-crackable handshake written to a log file.

Credentials are not the only sensitive bytes that tracer sees. A dump of a
listing reply or a read reply carries filenames and file contents, which this
campaign's own corpus rules treat as sensitive enough to keep out of the
repository entirely (see Fixture obligations). Byte-level dumping is therefore
off unless the operator turns it on for a run, and the SESSION_SETUP_ANDX bytes
stay redacted even when it is on.

**The capability floor is a decision, not an inheritance.** The client requires
the following capabilities and refuses a server lacking any of them; the port
targets nothing that predates them.

| Capability | Underpins |
|---|---|
| `CAP_NT_SMBS` | NT-style creates |
| `CAP_UNICODE` | Unicode paths |
| `CAP_LARGE_FILES` | 64-bit offsets |
| `CAP_STATUS32` | NT status codes |
| `CAP_NT_FIND` | The TRANS2 FIND listing path |
| `CAP_EXTENDED_SECURITY` | The SPNEGO session setup the whole auth path assumes |

The last of those is the one the design would otherwise assume silently. All
three tested servers set it (`0x80000000`), and all three answer with
`EncryptionKeyLength = 0` and a SPNEGO blob in the negotiate response's byte
area, which is why the `NegTokenInit` path works at all. A server without it
sends an 8-byte challenge and expects a raw NTLM response in
SESSION_SETUP_ANDX; a floor that omitted it would admit such a server and then
fail it somewhere inside the SPNEGO decoder, which is the least diagnosable
place in the crate to fail.

The client additionally checks `NEGOTIATE_USER_SECURITY` and refuses
share-level-security servers, which the Go library does not: it declares
`NEGOTIATE_USER_SECURITY` (`internal/smb1/negotiate.go:64`) and never tests it,
reading the negotiate response's `SecurityMode` for the encrypt-passwords bit
alone (`internal/client/negotiate.go:63,73`). Proceeding against
one sends a password where a share key is expected.

**The negotiated `MaxBufferSize` is checked at the same moment, and a value
below 4,356 fails the connection at negotiate.** That figure is the SMB1
minimum — Windows 11 24H2 advertises exactly it — and a server negotiating below
it is one this campaign never tested and this port declines, with an error
naming the field rather than a failure further in. **The check's location is
load-bearing**: the field is 32 bits and server-supplied, and the chunk-size
rules subtract 1,024 from it (see Sizing transactions), which in Rust is a debug
panic or a release wrap on any value under 1,024. Validating once, on arrival,
makes every one of those subtractions safe by construction, so they are written
as plain arithmetic; scattering saturating arithmetic through them instead would
leave a nonsense buffer size in play and no place that said so.

**The client advertises the capability word it implements, not the server's
echoed back.** It sends `CAP_EXTENDED_SECURITY | CAP_NT_SMBS | CAP_UNICODE |
CAP_LARGE_FILES | CAP_STATUS32`, and `CAP_LARGE_READX` and `CAP_LARGE_WRITEX`
besides **when the server advertised them**. The first five are capabilities the
port implements and the floor above already requires of the server; the last two
are what the chunk-size rule turns on (see Sizing transactions), so claiming them
to a server that did not offer them would assert a capability against a peer that
cannot honour it. Go echoes the server's word back verbatim, so this is a
divergence, and — like the two client-chosen numbers beside it in the same
request — a word no server had been sent when this was written (see Acceptance
Criteria).

**`CAP_EXTENDED_SECURITY` is in that list because Windows refuses the session
setup without it, and an earlier position here omitted it.** Curating the word
down to what the port implements is right; dropping this bit was not, and the
mistake was invisible from the corpus because Go echoes the server's word and
every tested server sets it — the reference therefore sends `0x8080F3FD` and
satisfies the requirement by accident. Built without it, Windows 11 24H2 answers
the *first* `SESSION_SETUP_ANDX` with `ERRSRV`/`ERRerror` in DOS error format,
`Flags2 = 0x8801`, `WordCount = 0`, no NT status at all, and authentication never
begins. Both Samba-family servers accept the word either way, so the acceptance
container cannot catch this. It is the fifth defect in this campaign to surface
only against Windows, and the first found by the port's own code rather than by
a capture — and the `SMB_FLAGS2_NT_STATUS` rule recorded above (see Wire layer)
paid for itself on its first contact with a real server: without it the refusal
would have surfaced as a fabricated `NTSTATUS` of `0x00010002`. **`NativeOS` and
`NativeLanMan` identify the crate**, by name and version, rather than a host
operating system: Go sends `"Unix"` and `"smb1client"`. They are wire-visible
identity strings and there is no reason to misreport them.

**NTLM's `Domain` and `Workstation` are two different kinds of field and are
decided apart.** An unset `Domain` is sent as the empty string rather than omitted, and it is
the empty string that NTLMv2 mixes into the response — so an unset domain is a
value, not an absence, and two callers who leave it unset compute the same
response. `Domain` is otherwise not the crate's to choose: NTLMv2 mixes it into the
response, so it is credential material and it sits on `ClientConfig` beside the
username and the password (see Configuration and timeouts). `Workstation` the
crate does choose, and **it is sent empty** — which is not the `NativeOS`
reasoning above transplanted: there the argument is against *misreporting* an
identity string, here it is against *reporting at all*. Shipping the operator's
hostname to a legacy SMB1 server on an untrusted network is the same exposure
the redaction rules above refuse in the crate's own logs, and no server needs
the field.

**A session setup that succeeds is checked for a guest logon.** Bit 0 of the
SESSION_SETUP_ANDX response's `Action` field says the server logged the client
on as guest, which on many servers is exactly what a wrong password produces:
authentication reports success and every later operation runs as an anonymous
user with whatever rights guests have. The client reads that bit and fails with
an error naming guest access, unless guest access is what the caller asked for.

**The pre-authentication parsers are hardened, not merely small.** The case for
a hand-rolled SPNEGO decoder is that it is a smaller attack surface than a
general ASN.1 crate, which is worth something only if the small surface is
treated as one: the crate is `#![forbid(unsafe_code)]`, and every parser an
unauthenticated peer can reach carries a fuzz target — the frame decoder, the
negotiate-response parser, the SPNEGO decoder, and the NTLM challenge parser,
which consumes server-supplied AV pairs before authentication has completed.
Those four are where hardening starts, and they are not a trust boundary,
because the crate has none to draw: it does not sign, so it never authenticates
the server at any point (see Non-goals), and a hostile or intermediary peer is
exactly as present after the session setup as before it. Every parser above the
session — the reassembler, the entry walk, the RPC decoders — faces that same
peer, and which of them carry targets beyond these four is the
implementation's call rather than a decision made here.
Allocation from untrusted input is bounded wherever it happens — the NetBIOS
frame length bounds a frame and is read as 17 bits for that reason, and a
reassembly buffer is bounded by what the request asked for (see Wire layer and
Routing and reassembly). The one place a server-supplied number sizes an
allocation is `Tree::read`, which says so (see Whole-file and whole-tree
operations).
Input travelling the other way is checked as well: a caller's path is refused
before it reaches the wire if it is absolute, carries a null byte, or escapes the
share root when `.` and `..` are resolved for the purpose of that check — the
path itself is sent as the caller wrote it (see Paths). That last refusal is the
one path rule with a security consequence — a consumer joining a user-supplied
name onto a prefix gets it without having to ask for it — which is why it is
named here as well as decided there.

**Those four fuzz targets have an owner.** A scheduled weekly CI job runs them on
the nightly toolchain, from a small committed seed corpus; they are not a
pull-request check, because fuzzing on a pull request either finds nothing
within the budget it is given or blocks a merge on a run nobody sized for it.
The job is named here rather than left implied because a fuzz target nobody runs
is decoration — it compiles, it is never exercised, and the hardening claim
above is the thing that rests on it.

### Non-goals

Stated so they are decisions rather than gaps. None of these is a capability
SMB1 lacks; each is something this crate does not do.

- **Message signing.** Deferred by the operator to follow-up work rather than
  implemented here. No tested server requires it: Windows 11 24H2 with
  `RequireSecuritySignature=True` accepted NTLMv2 authentication and a tree
  connect from an entirely unsigned client. The crate states the absence in its
  own user-facing documentation (see Security posture).
- **Byte-range locking and oplocks.** `SMB_COM_LOCKING_ANDX` and the oplock
  request flag exist in SMB1; nothing here uses them.
- **Port 139 NetBIOS session transport.** TCP/445 only. No target requires 139,
  and the Go library never implemented it either.
- **Reaching a server by an IPv6 literal address.** Microsoft's
  `ipv6-literal.net` name transform is what would carry one through a UNC
  syntax that admits no literal, and this crate does not implement it; nor does
  it take a second address parameter beside the path. So a server is reachable
  over IPv6 only by a hostname that resolves to one, and a literal offered in a
  path is refused with an error saying so — Paths states what that costs and
  why it is accepted.
- **Splitting an oversized request with `TRANS2_SECONDARY` /
  `SMB_COM_TRANSACTION_SECONDARY`.** See Sizing transactions.
- **Automatic retry of failed operations.** A dead cached connection is
  re-dialled on the next call, but a failed operation is reported rather than
  retried — see Connection caching and reconnection. One narrow exception is
  stated where it is decided: a large read or write a server rejects with one of
  three named statuses is retried once at a chunk of `MaxBufferSize − 1024`,
  because that chunk size is measured on two implementations and asserted of
  every other server (see Sizing transactions).
- **A sync or flush verb.** The crate offers none and never sends
  `SMB_COM_FLUSH`. The command is not widely supported; the reference declares
  it as a constant (`internal/smb1/constants.go:21`) and sends it nowhere, and
  its own `File.Sync()` is a documented no-op — "SMB1 doesn't have a direct
  flush/sync command… For now, this is a no-op" (`file.go:262-267`). A `sync()`
  that silently guarantees nothing is worse than its absence in a crate whose
  principle 1 is that a silent no-op is a defect. Nothing else here promises
  durability either: `WRITE_ANDX` asks for no write-through, so an
  acknowledgement says the server took the bytes and not that they reached its
  disk (see Public API → Reads and writes).

### Constants inherited without derivation

The Go library's 128 KiB read and 256 KiB write pipelining thresholds have no
recorded rationale and no test pinning them. They are carried over as-is and
marked in the source as inherited rather than re-derived from first principles,
because re-deriving them silently changes behaviour with nothing to catch the
difference.

Eight related values are **not** carried that way. Each is decided in the
section that owns it, and this table is an index rather than a second home for
the reasoning.

| Go value | Carried? | Decided in |
|---|---|---|
| Pipeline depth cap of 50 | yes, but with a derivation | The request table |
| `maxPipeline` of 30 | no | The request table |
| `MaxParameterCount` of 1024 | no — right-sized instead | Sizing transactions |
| FIND batch size of 100 entries | yes, as a load-bearing value | Fixture obligations |

### Self-maintenance

This section follows from the self-maintenance priority stated in the guiding
principles: the crate should need as little attention as the Go library does.
The Go repo's automation is translated rather than reinvented.

**Releases are unattended.** `release-plz` computes the version from
Conventional Commits, maintains the changelog, bumps `Cargo.toml` and tags.
Publishing is the one thing it does not do here, the registry step being
withheld deliberately (below). Its normal model is a release pull request a human merges, which
would trade the Go repo's zero-touch property for a click per release. Two
things close that gap: the workflow runs as a GitHub App so its pull request
triggers CI at all — a pull request opened with the default token fires no
workflows, so with branch protection copied over from the Go repo it could never
satisfy its own required checks and releases would deadlock silently — and
auto-merge is enabled on it, the same trust model already used for dependency
updates. The App's credential is long-lived; that is accepted in exchange for
unattended operation.

**The crate starts at `0.1.0` and stays pre-1.0** until its API has been
exercised by a real consumer. Version discipline therefore lives in the commit
messages rather than in a review step: `release-plz` computes the bump from
Conventional Commits, so a commit marked breaking produces a breaking release
with nobody approving it. That is the same trust model already accepted for
dependency automerge, and the alternative is the per-release human merge
rejected above. The pre-1.0 consequence is worth stating for consumers: a
breaking change is a minor bump, and Cargo treats every `0.x` minor as
incompatible, so what protects a consumer from an unreviewed breaking release is
the resolver rather than review.

**Nothing publishes to crates.io, and the repository is configured so that
nothing can.** `package.publish = false` in `Cargo.toml` makes `cargo publish`
refuse outright, and the release workflow's jobs are additionally gated on a
repository variable that is unset. Two guards rather than one, because they fail
differently: the manifest stops a publish attempted by hand from any checkout,
while the gate stops the workflow from running at all — and `release-plz release`
would otherwise try to publish the unpublished `0.1.0` on the first push to the
default branch, which is a live hazard rather than a hypothetical one.

**The registry path is nevertheless specified, because turning it on must not
mean designing it.** Should the operator decide to publish, the mechanism is
crates.io Trusted Publishing over OIDC, so that no registry token is stored.
Three properties of it are worth having recorded before that day rather than
discovered on it:

- Trusted Publishing **cannot bootstrap a crate that does not exist**, so the
  very first publish needs a token. That token is removed afterwards and
  per-crate token publishing is disabled, leaving the OIDC path as the only one.
- The name has to be free at that moment. `smb1client` was confirmed
  unregistered while this design was implemented; nothing reserves it, so the
  check is repeated rather than trusted.
- crates.io matches a Trusted Publishing configuration by workflow **filename**,
  so renaming that file later breaks publishing silently. Support outside GitHub
  is gitlab.com-only, which does not bind here: the crate lives on GitHub, and
  this design depends on that.

**Dependency updates** are Dependabot with automerge, matching the Go repo, with
two carve-outs. Majors wait for a human, and so do `0.x` minors, on the
incompatibility the resolver already assumes above. Dependabot has no setting
that treats a pre-1.0 minor as a major, so that carve-out is mechanism rather
than configuration: the automerge workflow itself withholds automerge from any
update whose dependency is pre-1.0, rather than a list of per-dependency
`ignore` rules — a list is silently incomplete the moment a new `0.x`
dependency is added. The cost is one piece of workflow logic to keep working
against Dependabot's metadata, and it is the cheaper of the two to maintain
correctly. A green build is not evidence that a breaking change was harmless; it
only proves the crate still compiles. The other carve-out is the acceptance
container, excluded from updates entirely (see Acceptance Criteria).

**MSRV** is the higher of what the dependency graph requires and what this
crate's own code requires, raised only when something forces it, never raised
merely because development uses a newer toolchain. The second half is not
redundant: `DirectoryNotEmpty`, `NotADirectory` and `IsADirectory` are
`io::ErrorKind` variants stabilized in Rust 1.83, so the status mapping puts a
floor under the crate that no dependency accounts for (see Public API → Errors).
The 2024 edition the crate is written in carries a higher floor still, so
nothing turns on the
1.83 today; what the rule has to say is that the crate's own code can raise the
floor at all, which a purely dependency-driven reading did not cover. The
policy needs one mechanism to be honest: a CI matrix leg that runs
`cargo check --all-targets` against the declared minimum. Edition 2024's
resolver is MSRV-aware for dependency *selection* only — it does not check that
this crate's own code compiles on its declared floor, so without that leg the
declared version is an unverified claim and a consumer discovers the lie.
The Go repo's two floor-raising workflows are not translated; with a
dependency-driven floor the raise is rare and doing it by hand is right.

**`Cargo.lock` is committed**, so CI resolves reproducibly and an unrelated pull
request does not turn red because a transitive dependency published or yanked.
The crate repository's `.gitignore` therefore must not carry the library-crate
default that excludes it — the evidence repository's does, and it is the file
most likely to be copied across.

**Supply chain** is `cargo-deny` for advisories and licenses. Development
dependencies need no configuration to be covered: they are in the graph
already, `[graph] exclude-dev` defaulting to false. `include-dev` is not a
`cargo-deny` key at all — it is a hard config error that stops the tool
starting. No advisory exceptions are needed: neither `md4` nor `rc4` carries
one.

**No test-oracle dependency.** `smb-fscc` would serve as a dev-dependency for
its independently validated MS-FSCC struct layouts; it is not taken. Pinning
does not stop Dependabot raising pull requests, and every `0.x` minor is held
for a human and triaged roughly monthly — precisely the cost that rejected
smb-rs as a runtime dependency, re-entering through the development door. That
cost is not what distinguishes it from `binrw` and the RustCrypto primitives,
which are held the same way and accepted: those are load-bearing and have no
1.0 alternative, while this one's value can be taken once and kept. The
cross-validation is run once during implementation and its results committed as
plain expected-value test vectors beside the fixture bytes, which keeps the
evidence and drops the subscription. It is also only a partial oracle: its
chained-list container assumes SMB2's zero terminator and its info-class enum
uses SMB2 codes, both of which would need special-casing anyway.

### Licensing

The crate is `MIT OR Apache-2.0`.

**The NTLM and SPNEGO implementations are written from their specifications** —
[MS-NLMP] and RFC 4178 — with the Go library consulted only as a **behavioural**
cross-check: same inputs, compare the bytes that go on the wire. Never as a
structural reference. Fixture obligations says where that cross-check runs and
what stands in for it in CI. The go-smb2-inherited material is exactly what
these two implementations would otherwise be derived from, so reading that code for its
shape rather than its output would propagate the derivation into Rust and
defeat the reason for writing from specification at all.
The operator holds the copyright in the Go library, which is MIT, so translating
their own code into Rust carries no third-party obligation and nothing here turns
on it. What could carry one is the material that library inherited from go-smb2
under BSD-2-Clause. The NTLM and SPNEGO implementations are where that
inheritance is documented — `ARCHITECTURE.md:76` records the package as
"NTLM v2 authentication (adapted from go-smb2)", `CLAUDE.md:47` names
`internal/ntlm` and `internal/spnego` together against BSD-2-Clause, and the
only trace in the SPNEGO source itself is a test comment linking a go-smb2
pull request (`internal/spnego/spnego_test.go:66`). They are not established to
be the whole of it.
Writing those two from specification is a decision made before the code is
written rather than an audit afterwards, and what it buys is bounded by what it
covers: `auth/` carries no derivation from that material, and the question is
closed for `auth/`. **`status.rs` is closed the same way and by the same
decision**: its table is generated from [MS-ERREF] — with the handful of
SMB-specific statuses [MS-CIFS] defines hand-written from that specification,
which is published on the same footing and carries no obligation either — rather
than transformed from the output of the Go repository's go-smb2-derived
generator, which costs a scraper and removes an attribution question instead of
leaving one to be answered (see Public API → Errors). The question stays open
everywhere else. The
rest of the port is
translated from the operator's own MIT-licensed code, and where any of that
turns out to be go-smb2-derived the obligation below is what carries it.

Narrowing it that far was worth the trouble because the Go repository had the
question open and unanswered when this was written: its inherited go-smb2
material was traceable but unattributed — no copyright notice, no licence text,
no notice file, no per-file headers — and a third-party notice file cannot be
written correctly without first establishing what it covers.

**That has since changed there, and it changes nothing here.** A
`LICENSE-THIRD-PARTY` reproducing the go-smb2 licence has been added to that
repository after the pinned commit. It is the right fix for that library and it
does not reach this one: writing `auth/` and `status.rs` from their
specifications means neither carries the derivation at all, so there is nothing
for a notice to cover. The decision was made before the code was written rather
than audited afterwards, which is exactly what makes it robust to the upstream
answer arriving later. That diagnosis belongs to that repository and is recorded in
its issue notes, which are git-excluded and unreachable from a clone (see
Detailed Implementation).

If any implementation does end up derived from that go-smb2-inherited material,
the obligation is carried by per-file headers naming the upstream and its licence
**and** a `LICENSE-THIRD-PARTY` file — not the file alone. Downstream binary
attribution in Rust is generated by tooling that reads the SPDX `license` field,
so a notice file nothing parses would be omitted from every downstream binary's
notices.

## Acceptance Criteria

### What gates a release automatically

CI runs against the dockerized Samba NT1 container and against the committed
wire-fixture corpus. **`spikes/capture-frag/` is a mandatory fixture**: it is
28 captured frames of a listing of a 600-entry directory, whose TRANS2 replies
split across messages, and it is the
only thing in the corpus that fails a port which reads one message per multiplex
ID; every other fixture passes such a port. What that port loses is measured on
the fragmentation corpus itself, and nowhere else: six of its seven TRANS2
replies split in two, so a reader that takes only the first message of each
returns 92.3% of the bytes and reports no error at all. (The 213-of-285 figure
from the pre-`cfe08eb` Go defect, which was that same
one-message-per-multiplex-ID behaviour, is a different directory and a different
measure, entries rather than bytes; neither number is the other's
contradiction.)

The live half of the gate needs the container seeded, not merely running:
invariant 1's end-to-end check asserts that a listing of the 600-entry directory
returns 600. That check is end-to-end coverage and not the invariant's
reassembly evidence, and the 42-character names the directory is built from are
what the committed fragmentation corpus depends on; Fixture obligations owns
both points. Creating that directory is a setup step of the
acceptance job, so the oracle cannot quietly degrade to an empty share.

**Listing an empty directory is a second named live check**, and the seeding
step creates one for it: `read_dir` on a directory holding nothing returns no
entries and no error. It is named because it is a plausible regression no
committed fixture would catch — the corpus has no empty directory in it — and
because the way to fail it is a one-line ordering mistake: a first page carrying
`.` and `..` alone, with `EndOfSearch` unset, is an error to a no-progress guard
that counts entries after the filter rather than before it (see Public API →
Directory listing).

The corpus and the crate live in different repositories, and they meet by
copying. The fixtures are captured and kept in the evidence repository, which remains the
evidence trail and the home of this design; the crate is built in its own
repository. The fixtures the test suite needs are copied into the
crate repository as test data and ship in the published package, so `cargo test`
passes from a fresh clone and from the published tarball without reaching this
repository at all. Only credential-free frames are copied, which the corpus
already guarantees (see Fixture obligations). The copy is checked rather than
trusted, and the check has to be the right one. A digest manifest is committed
beside the fixtures in both repositories, and each test suite verifies its own
fixtures against its own manifest — which catches a fixture edited without its
manifest, and nothing else: a fixture and its manifest edited together pass on
both sides while the two corpora have silently diverged. What says the corpora
agree is the two manifests agreeing, so the manifest travels with the fixtures
and the comparison is a step of the copy. **The copy itself owns that
comparison** — an obligation nobody owns is decoration, and whatever performs
the copy, a person or a script, holds both manifests at that moment by
construction, which nothing later does. A mismatch stops the copy rather than
producing a corpus to be caught afterwards. Neither CI job can perform it — the
crate's checks out only the crate.

### What cannot gate a release, and what covers it instead

**There is no Windows VM in CI.** This is a real gap, not an oversight: every
finding made late in the evidence campaign — the transaction-size ceiling, the
two directory-chain terminators, the fact that a page is bounded by
`MaxDataCount` and not by the `SearchCount` a request asked for, the port in the
IPC$ UNC path — surfaced *only* against Windows, and a Samba-only gate would
pass a library that cannot list a directory on a stock Windows SMB1 server.

It is covered two ways:

1. **Windows behaviour is committed as captured fixtures** and asserted in CI, so
   the specific defects the campaign found stay closed without a live server.
2. **The crate ships a conformance script a user can point at their own SMB1
   server** — the operator's Windows VM, an embedded device, anything — run by
   hand before a release. It is not a CI job and does not gate automatically.
   It carries the checks no committed evidence can settle, and nine are named
   explicitly — one of them since discharged against a live Windows server and
   kept for the next server nobody has measured:
   - authenticating with `NTLMSSP_NEGOTIATE_SIGN` and without `ALWAYS_SIGN`,
     which finding W7 measured against Windows and Samba only and never against
     the embedded device (see Security posture);
   - authenticating without `NTLMSSP_NEGOTIATE_VERSION`, which no sweep measured
     against any server at all (see Security posture);
   - a header `Flags2` without `SMB_FLAGS2_KNOWS_EAS`, which no sweep measured
     either, every captured request having carried Go's own value (see Wire
     layer);
   - a 130,048-byte read and a 130,048-byte write against a server that sets
     `CAP_LARGE_READX` / `CAP_LARGE_WRITEX` beside a small `MaxBufferSize`.
     **This one is discharged**: run against Windows 11 24H2, which sets both
     beside a `MaxBufferSize` of 4,356, the write was accepted in full and every
     read was served `min(asked, 65536)` — so a server may cap a read reply
     below the frame limit while accepting a full-sized write, and what covers
     that is the fill loop rather than the downgrade (see Sizing transactions).
     The check stays on the script because it is still the right one to re-run
     against a server nobody has measured;
   - `SMB_FIND_CLOSE_AT_EOS` on a FIND_NEXT2, which is spec-legal but which no
     server in the corpus has been observed to accept (see Handle lifetime);
   - the idle probe, on both counts no evidence can settle: whether
     `SMB_COM_ECHO` answers at all carrying `UID = 0`, `TID = 0xFFFF` and an
     empty byte area, all of which are reasoned from the protocol's shape and
     not inherited from the reference, which sends no echo; and whether it
     answers on a connection whose session the server has discarded, which is what says how much the probe can be
     relied on (see Connection caching and reconnection);
   - an open carrying both of this port's `NT_CREATE_ANDX` departures: the
     permissive `ShareAccess` of `0x7` where the reference sends `0x3`, which is
     what decides whether a delete succeeds against a handle somebody else
     holds, and a `DesiredAccess` of specific rights without `SYNCHRONIZE` where
     the reference sends the `GENERIC_*` groups with it. The reference's side of
     both is fixture-pinned — `spikes/capture/0015-c2s-cmda2.bin` is an
     `NT_CREATE_ANDX` request carrying `DesiredAccess = 0x80100000`,
     `GENERIC_READ | SYNCHRONIZE`, beside `ShareAccess = 0x3` — and neither of
     the values the port sends instead has reached any server (see Public API →
     Filesystem verbs);
   - whether a server that requires signing says so in its negotiate response,
     which is the check that has no fixture coverage at all: all three tested
     servers report `SecurityMode = 0x03` with neither signature bit set, so
     only a live server that admits to requiring signing can exercise it (see
     Security posture);
   - the three client-side values no server has ever been told, the Go client
     that took every capture having echoed the server's own back: a
     `MaxBufferSize` advertisement of 65,535 (see Sizing transactions), a
     client-chosen `MaxMpxCount` (see Flow control) and a client-chosen
     capability word (see Security posture). Each is a wire change against all
     three tested servers, and none has been sent to any of them.

**The Windows fixtures are decode oracles, not encode oracles.** They were
captured from the Go library patched around finding W1, asking
`MaxDataCount = 4000` beside Go's unchanged `MaxParameterCount = 1024` — a sum
of 5,024, far under the measured 66,524-byte ceiling, which is what makes the
patched request acceptable to Windows at all. It is not the 4,356-byte buffer
that admits it, that being the bound this document shows is not one (see Sizing
transactions); what the buffer does bound is a single message, and a reply the
client has capped at 4,000 data bytes fits in one, which is why nothing in
`capture-win-frag/` fragments. `capture-win-a/` is the exception and
predates the patch: it asked for Go's own `MaxParameterCount = 1024` and
`MaxDataCount = 65535` — 66,559 as a sum, which is the ceiling's unit but not a
field on the wire — which is what makes its
`0012` the `STATUS_INSUFF_SERVER_RESOURCES` frame cited elsewhere. Finding W3's
"Windows does not fragment Trans2 replies" (both in
`notes/01-rust-port-spike.md`) is therefore a property of that request rather
than of the server, and no committed evidence says what Windows does with a
reply too large for what the client asked for. The client-to-server frames are
limited the same way: `MaxParameterCount` of 64, no port in the IPC$ path,
`ALWAYS_SIGN` and `NTLMSSP_NEGOTIATE_VERSION` dropped, a header `Flags2` without
`SMB_FLAGS2_KNOWS_EAS`, a single-dialect negotiate offer, a client-chosen
`MaxMpxCount`, a client-chosen `MaxBufferSize`, a client-chosen capability word,
a permissive `ShareAccess` of `0x7` and crate-identifying `NativeOS` /
`NativeLanMan` are all deliberate
departures, so the port re-encoding one of those messages will not reproduce
the captured bytes. Six of those eleven are moot against this corpus — the two
dropped NTLM flags, the client-chosen `MaxMpxCount`, `MaxBufferSize` and
capability word, and the `NativeOS` / `NativeLanMan` pair all travel in
SESSION_SETUP_ANDX, and session-setup frames are excluded from the corpus by
rule (see Fixture obligations), so they touch no committed frame.

**The other five are not moot, and between them they touch every committed
client-to-server frame there is.** `MaxParameterCount` is a TRANS2 field and the
corpus holds 51 committed TRANS2 requests; the absent IPC$ port is a
TREE_CONNECT_ANDX field, and there are 25; the single-dialect offer is a
NEGOTIATE field, and there are 19; `ShareAccess` is an NT_CREATE_ANDX field, and
there are 11; and `Flags2` is a header field, so it touches all 238. Those counts
are over every committed frame — the tracked ones, which is what "committed"
means here and what a clone gets. There is no
committed client-to-server frame that some departure does not reach. For them,
build order step 1 asserts that the committed
frame decodes to the fields it should and that re-encoding *those decoded
fields* reproduces the bytes exactly — the codec is still pinned, the defaults
are not. The `Flags2` departure is what makes that the rule for every
client-to-server frame rather than for a list of exceptions: it is a header
field, so no request the port builds of its own accord reproduces a captured one
byte for byte, and there is no client-to-server message left for which
byte-identity against a fresh encode could be asserted.

### Where the Go library is the oracle, and where it is not

Differential testing against the Go library is authoritative only where that
library is known-good. These are the places it is not, as this campaign found
them: for each one the suite marks the Go behaviour as known-wrong and asserts
the correct result instead. The list is what the suite asserts against, not a
guarantee that nothing else in that library is wrong.

- transaction sizing — `MaxParameterCount` left at 1024 overshoots the ceiling
  on the TRANS2 and RAP paths;
- the TCP port in the IPC$ UNC path;
- the byte count returned by a cancelled write;
- multiplex IDs freed on cancellation while the request is still outstanding —
  in `sendRecv`; the pipelined paths mark the request cancelled and keep the ID
  (see Frames that are not replies);
- `0xFFFF` allocated as a multiplex ID, which [MS-CIFS] reserves for
  server-initiated oplock-break notifications (see The request table);
- an unroutable frame skipped and the receive loop continued, with nothing
  logged (see Frames that are not replies);
- `SMB_COM_FIND_CLOSE2` never sent, and `SMB_FIND_CLOSE_AT_EOS` set only on the
  FIND_FIRST2, so no listing longer than one batch closes its search at all;
- a FIND loop that ends on `SearchCount == 0` (`session.go:913`), so a page
  carrying no entries and neither terminator ends the listing silently where
  this design's no-progress guard fails it — a short listing reported as a
  complete one, which is the silent-truncation class invariant 1 forbids (see
  Public API → Directory listing);
- a short read reported as end of file. `readAtChunk` returns `io.EOF` whenever
  `n < readSize` (`internal/client/file.go:608-609`), under its own comment that
  "a short response only happens at end of file" (`:541-543`), and `ReadAt`
  stops at the first chunk that returns one (`file.go:38-52`,
  `internal/client/file.go:524-537`). Against Windows, which serves
  `min(asked, 65536)` on every read (see Sizing transactions), a `ReadAt` of
  65,537 bytes on a 260,096-byte file returns 65,536 bytes **and** `EOF`. The
  pipelined `Share.ReadFile` path (`session.go:1041`) re-issues and returns all
  260,096, which is why the defect stayed hidden. This is the silent-truncation
  class invariant 1 forbids, on the read path, and it is what the port's fill
  loop exists to prevent: a chunk answered short is re-issued for the bytes it
  did not return, never mistaken for the end (see Public API → Reads and
  writes);
- `STATUS_BUFFER_OVERFLOW` classified as success;
- RAP's `ERROR_MORE_DATA` treated as fatal to share enumeration rather than as
  a fall-through to the DCE/RPC path (see Wire layer);
- the single unlooped 64 KiB named-pipe read, which cannot collect a response
  that did not fit the read asking for it (see Wire layer);
- the `SMB_COM_TRANSACTION` `Name` written as 8-bit ASCII under a header that
  sets `SMB_FLAGS2_UNICODE`. `EncodeTransactionRequest`
  (`internal/smb1/rap.go:277-278`) writes `[]byte(name + "\x00")` under its own
  comment "Name should be null-terminated ASCII string for pipe name", while the
  header carries `Flags2 = 0xC803`; a server that honours the flag decodes
  `\PIPE\LANMAN` as `䥐䕐䱜乁䅍N` and matches nothing. Samba 4.23.8 answers every
  `SMB_COM_TRANSACTION` from that client with `STATUS_NOT_SUPPORTED` — RAP and
  the DCE/RPC transact-mode bind and request alike — so the reference library
  reaches share enumeration against the container only through its write/read
  fallback. `spikes/capture-trans/` is the refusal and
  `spikes/capture-rap/` and `spikes/capture-rap-ascii/` are the same container
  answering `NetShareEnum` once the spelling is corrected either way (see Wire
  layer);
- `TRANS_TRANSACT_NMPIPE` requests sent with no `Name` field at all, where
  [MS-CIFS] requires `\PIPE\`: the byte area of
  `spikes/capture-trans/0017-c2s-cmd25.bin` begins `05 00 0b 03`, the DCE/RPC
  bind PDU, with no name in front of it. It is invisible in practice only
  because the server refuses the request earlier, for the reason above (see
  Wire layer);
- `SetupCount = 2` on a RAP request, where [MS-RAP] 2.1 sends `0`.
  `EncodeTransactionRequest` hardcodes the count (`internal/smb1/rap.go:315`)
  and then writes two zero words for it under its own comment "For RAP/LANMAN
  pipes, setup is typically zero" (`:318-322`); its named-pipe sibling
  (`:375,382-384`) is right to send two, those being the subcommand and the FID.
  Samba ignores the difference, dispatching on the `Name`, and **Windows rejects
  the frame as malformed** — answering in *DOS error format*, `ERRSRV` /
  `ERRerror` under `Flags2 = 0x8803` with `SMB_FLAGS2_NT_STATUS` cleared against
  the request's `0xC803`, so the refusal carries no status about RAP at all.
  `spikes/capture-win-rapsetup/` is that refusal. This was on no list before,
  and it is the kind of defect that hides behind another: it became reachable
  only once the transaction `Name`, the `IPC$` UNC port and the transaction size
  were all corrected. The port sends `SetupCount = 0` on the RAP path, which
  moves that request's `Name` and `ParameterOffset` with it (see Wire layer);
- `NativeOS` and `NativeLanMan` placed at an odd offset in `SESSION_SETUP_ANDX`,
  so a server honouring the alignment reads every character of both a byte late.
  This one is not a spelling defect and reads like one: the bytes are already
  UTF-16LE, and it is the *offset* that is wrong, the strings sitting behind a
  security blob whose length the pad has to be computed from. Samba logs
  `NativeOS=[渀椀砀]` for bytes that decode as `Unix` from even parity. Nothing
  breaks, because the server ignores both values — it is listed because the port
  sends its own strings at that same site behind its own variable-length blob
  (see Wire layer);
- `CAP_LARGE_WRITEX` never checked: 130,048-byte chunks are written whatever the
  server advertised;
- no protocol-level `STATUS_PENDING` handling: `errors.go` classifies the
  status as temporary and nothing else acts on it, so an interim response is
  delivered to the caller as the answer;
- reassembly totals latched from the first message, so a downward revision is
  never honoured (see Routing and reassembly);
- the guest-logon bit in the SESSION_SETUP_ANDX response never checked —
  `IsGuest()` exists at `session_setup.go:264` and its only caller is the
  `String()` at `session_setup.go:277`, so no decision path reads the bit — and
  a wrong password a server downgrades to a guest logon reports success (see
  Security posture);
- `NEGOTIATE_USER_SECURITY` never checked, so a share-level-security server is
  authenticated against as though it were user-level (see Security posture).

**A third case exists that the list above cannot hold: the Go library
disagreeing with itself.** Where two of its own paths answer the same question
differently there is no single Go behaviour to compare against — neither
answer is the reference, and the differential run cannot adjudicate between
them. The port decides such a case on its own terms and says where it did, and
the run is then expected to disagree with whichever Go path the port did not
follow. That disagreement is evidence of the inconsistency and not of a port
defect, so it is neither reproduced as reference behaviour nor asserted against
as a known-wrong one; what the suite pins is the port's answer. Build order
step 4 carries the one instance this campaign found.

**Every oracle the port keeps could be wrong the same way, and the independent
dissector that would catch it is deferred.** The campaign had a check this port
does not carry forward: `tshark`'s SMB1 dissector, authored independently of
both this project and the Go library, agreeing field for field with the Go parse
and with a seeded ground truth (finding C5 in `notes/01-rust-port-spike.md`),
which is what made the fixture corpus usable as an oracle at all. What validates
the port's decoder instead is the committed fixtures, the Go library
differentially, and the published [MS-NLMP] vectors for `auth/`. The residual is
the limit the campaign itself recorded: a misreading of the wire format shared
by the fixtures, the Go library and this port would pass every one of those
checks. The tested servers reduce that risk and do not remove it — and there are
two implementations behind the three of them, the embedded device being
Samba-family (see Wire layer). Adopting a second independent dissector is
deferred rather than rejected, and this is the paragraph to re-read before
trusting a differential pass.

**What becomes of the Go test suite.** Roughly 24,000 lines of it exist, and the
port takes it selectively rather than wholesale. The behaviour-pinning tests for
the wire layer and the client are ported: they pin the wire behaviour this port
has to reproduce, minus the twenty-one places above where the correct result is
asserted instead. The go-smb2 parity suites are dropped, since that contract
does not exist here. The `io/fs` suites are dropped, having no Rust equivalent.
The `synctest` suites are translated, because the virtual-clock technique does
transfer. The invariant tests are new work and a port of nothing — the
Invariants section names each one and the test that proves it.

### What fixtures cannot prove, and what covers it

Captured fixtures are static bytes, so they can prove parsing and nothing about
timing. Three of the four invariants are timing properties, and every capture in
the corpus has exactly one request outstanding at a time — so a replay harness
alone cannot distinguish a correct implementation from several broken ones.

Two facts make this sharper. All three tested servers — the Samba container, the
embedded device and Windows 11 24H2 — negotiate `MaxMpxCount = 50`, which is
also the Go library's hardcoded pipeline cap, so a port that ignores the
negotiated value entirely behaves identically against everything we can test,
and the inherited ceiling of 50 binds nothing observed. The figure is 50 on all
three, but only two of the three are checkable from a clone: the Samba and
Windows negotiate responses are in the committed corpus, where the value decodes
with no live server needed, while the embedded device's negotiate lives in the
git-excluded `capture-vm/` and is evidence no clone can check. And reassembly
happens inside the connection actor, so the fragmented-reply fixture carries
invariant 1's reassembly path but not its coverage rule — no capture holds an
overlapping or gapped fragment — and it is structurally incapable of
proving invariant 2, continuations never reaching a waiter at all.

The design therefore requires a **test seam, and this is a design constraint
rather than an implementation detail**: the connection actor must be
constructible over an arbitrary `AsyncRead + AsyncWrite`, with negotiated
parameters injectable rather than reachable only through a real handshake.
Invariants 2, 3 and 4 are proven through it, as is invariant 1's coverage rule,
and the Invariants section names the test for each. **That constructor is public
surface, in a `transport` module, and it is not behind a feature flag** — a flag
would add a second build configuration for CI to test, when the point of the
seam is that the deterministic tests drive the same code path a consumer gets.

**The seam covers the handshake as well as the actor.** Negotiate and session
setup run on a stream handed to them (see Connection architecture), so they are
constructible over the same `AsyncRead + AsyncWrite` with a scripted negotiate
response and a scripted session-setup response — and that is the test for the
four refusals the handshake decides, none of which is reachable any other way:
the capability floor, the `NEGOTIATE_USER_SECURITY` refusal and the
`MaxBufferSize` floor all need a negotiate
response no tested server sends, and the guest-logon refusal needs an `Action`
bit the acceptance container is configured never to set (`map to guest =
never`). **A real server does set it**: the embedded device returns it for its
`guest` account, and the refusal fired against it on the first live run — so the
rule has one live confirmation beside its scripted test, from a server that is
not in CI and cannot be. No fixture can stand in, because session-setup frames are excluded from
the corpus by rule (see Fixture obligations), and two of the four are among the
behaviours the suite is required to assert. Extending the seam changes no
ordering: the handshake still completes before the actor takes the stream, and
what the test replaces is the stream, not the sequence.

The timing tests among those run under a virtual-clock harness, the direct
equivalent of Go's `testing/synctest` and the reason those suites translate
rather than drop
(see Where the Go library is the oracle, and where it is not). It is what the
timing rules need: the per-request timeout, the overall deadline that caps its
resets, and the connection-silence rule, none of which a test can reach in real
time. The two reassembly guards are not in that category — both are counts, and
a test reaches them by feeding fragments, the cap with a 65th fragment and the
empty-fragment tolerance with a second contribution-free message — but they are
proven in the same place.

### Fixture obligations

- **The fragmented-reply corpus is mandatory** and must stay reachable. It was
  captured from a client requesting `MaxDataCount = 65535` and advertising the
  16,644-byte `MaxBufferSize` Samba had just offered it, and that pair is why it
  fragments: fragmentation occurs when the whole reply exceeds `max_xmit`, the
  server's per-message transmit limit, which is itself bounded by the buffer the
  client advertised (see Sizing transactions) — 16,644 advertised against 65,535
  asked for. **The split point is two values and not one**, and a test asserting
  a single one fails against the corpus it was written from: the FIND_FIRST2
  reply's first message carries `DataCount = 16,572` (`capture-frag/0010`,
  `TotalDataCount` 17,836) and each of the five FIND_NEXT2 replies carries
  16,576 (`0013`, `0016`, `0019`, `0022`, `0025`, `TotalDataCount` 18,000).
  `max_xmit` bounds the whole message and not its data half — headers,
  parameters and their padding come out of the same 16,640 bytes — and the two
  subcommands' reply parameter blocks differ in size: 10 bytes padded to 12 for
  FIND_FIRST2 against 8 needing no padding for FIND_NEXT2, which is the four
  bytes by which the data halves differ. The port advertises 65,535, which
  lifts that bound
  above anything an ordinary listing produces, so Samba will rarely fragment for
  it live: the committed corpus is the captured evidence, and **one live test
  that advertises a small `MaxBufferSize` while asking for a large
  `MaxDataCount` is the live coverage** rather than a hedge against some future
  default. The knob is the advertisement and not the request: a small
  `MaxDataCount` bounds the total the server may return, so the reply fits in
  one message and the server pages with FIND_NEXT2 instead — a test written that
  way exercises paging and would pass a port with no reassembly at all. The
  port's default advertisement of 65,535 is unchanged; the test overrides it for
  its own connection. Relatedly, the fragmentation the corpus captured
  depends on three values jointly and all three are **load-bearing** rather than
  untuned inheritances: the FIND batch size of 100 entries, the 42-character
  filenames the captured directory uses, **and** the `MaxBufferSize` the
  capturing client advertised. The entries measured in
  `capture-frag/0010` are 96 bytes for `.`, 100 for `..` and 180 for each
  42-character name, and it is that 180 that pushes a 100-entry Samba reply
  past `max_xmit`; with ordinary 8-character names the
  same 100 entries are about 11 KB and Samba would not fragment at all.
  Lowering either of the first two, or raising the third, silently deletes the
  coverage, so any re-capture pins the name length as deliberately as the batch
  size. **`spikes/regenerate-fixtures.sh` meets that obligation.** It pins the
  42-character name length and the 600-entry directory size in its own source,
  and it pins the other two — the FIND batch size of 100 and the advertised
  `MaxBufferSize` of 16,644 — by *asserting them against the captured frames*
  rather than setting them, those two being resolved inside the Go library and
  reachable no other way; an assertion fails just as loudly as a setting that
  will not take. The fragmentation check is an executed step and no longer
  instructions to run by hand: `spikes/check-fixtures.py` runs at the end of the
  script and aborts it on any drift, and it was verified to fire by pointing it
  at corpora that had lost each property. A re-capture that silently stops
  fragmenting therefore fails instead of passing.
- **The large-read and large-write fixtures exist, and what they are for is what
  a re-capture has to preserve.** `spikes/capture-large/` holds a `READ_ANDX`
  reply at `ByteCount = 64513` and a `WRITE_ANDX` request at
  `ByteCount = 64512`, both carrying 130,048 bytes of payload, so a codec that
  trusts that 16-bit field fails against the fixture instead of against a
  server. Before it, the largest frame in the corpus was 16,644 bytes on the
  wire (16,640 bytes of SMB message plus the four-byte NetBIOS header) — exactly
  Samba's negotiated `MaxBufferSize`, which is not a coincidence: Samba counts
  the NetBIOS header inside the buffer it advertised and so never emits a
  message larger than `MaxBufferSize` less four. So the corpus had a hole
  exactly where the parser is most likely to be wrong, and on the write side not
  a hole but an absence, no `WRITE_ANDX` frame having been committed at all —
  and `WRITE_ANDX` is both one of the four offset back-patching sites and the
  encode side of the `ByteCount` wrap, so build order step 1, which validates
  the wire layer against committed fixtures offline, could not discharge the
  write path without it. The frames that establish the hazard were measured
  against the live Samba container during this design and lived in no capture;
  this corpus is what commits them. **It is captured the way the two older
  corpora are** — through the same relay, against the same container — and
  `spikes/regenerate-fixtures.sh` carries the seeding step and the harness
  client that reads the seeded file back and writes one of its own. The seeded
  file has to stay larger than the 256 KiB write threshold: below it the Go
  harness takes its sequential path and clamps the chunk to
  `MaxBufferSize − 1024`, and only above it does the pipelined path emit the
  full 130,048-byte chunks that carry a `ByteCount` past 65,535 in both
  directions (see Sizing transactions).
- **The `SMB_COM_TRANSACTION` fixture exists, and a second pair beside it gives
  RAP an offline oracle on both sides.** Before `spikes/capture-trans/` every
  transaction in the corpus was a TRANS2 and no `SMB_COM_TRANSACTION` (`0x25`)
  frame was committed at all, so two of the four offset back-patching sites had
  no offline oracle, `WRITE_ANDX` and `SMB_COM_TRANSACTION` alike (see Wire
  layer), and the RAP encoder that rides on the second had none whatever — the
  RAP path was pinned only by a live Samba run. `capture-trans/` is the
  reference library's own share enumeration against the container, taken through
  the same relay by the step `spikes/regenerate-fixtures.sh` carries for it: the
  RAP `SMB_COM_TRANSACTION` and the RAP parameter block on it, the two
  transact-mode DCE/RPC attempts, and the write/read fallback that answers where
  those are refused. What it pins is the request side, the mis-spelled `Name`
  that earns the refusal included, which is what makes it evidence of that
  defect rather than of the container (see Acceptance Criteria → Where the Go
  library is the oracle, and where it is not). **The answered RAP exchange is
  `spikes/capture-rap/` and `spikes/capture-rap-ascii/`**, one corpus per
  spelling that works — UTF-16LE under the flag, and 8-bit with the flag cleared
  on that one request. Both were taken by a harness **corrected for the `Name`**
  (`spikes/rapname/`) rather than by the reference library, and both directories
  are labelled that way, because that makes them evidence about the server
  rather than about what the reference sends. Corrected for the `Name` and not
  for the setup words: their requests still carry the reference's
  `SetupCount = 2`, so what pins the port's own RAP request shape is
  `spikes/capture-win-rap/` instead (see Wire layer). What they add is the reply
  the other corpora cannot carry — `STATUS_SUCCESS`, `WordCount = 10`, RAP
  status 0, `Converter = 0x0000`, `EntryCount = 2`, `Available = 2`,
  `DataCount = 68`,
  entries `testshare` (type `0x0000`) and `IPC$` (type `0x0003`, comment
  "IPC Service (Samba 4.23.8)") — and that reply is the only thing that can pin
  a RAP decoder's converted-pointer arithmetic offline.
- **The DCE/RPC `srvsvc` fixture exists, and it is synthesised rather than
  captured.** `spikes/srvsvc-synthesised/` is eight frames carrying the path
  that **works** on a server refusing the transact mode — the `WRITE_ANDX` bind,
  the `READ_ANDX` carrying `bind_ack`, the `WRITE_ANDX` request and the
  `READ_ANDX` carrying the share list — with session-setup frames left out. The
  exchange it was built from exists in exactly one capture directory,
  `capture-vm/`, which is git-excluded because it was taken against the
  operator's own device and names that device's real shares, which the corpus
  rule below forbids. So the frames were rebuilt with those names replaced, and
  **the scrub is length-preserving, which any later edit of it has to stay**:
  NDR conformant-varying strings carry a maximum count, an offset and an actual
  count, so a replacement name of a different length corrupts the frame and
  everything after it in the same stub. Replacement names match the originals
  character for character in length, and the generator reproduces the originals
  byte for byte when it is fed the unscrubbed strings. What results is a
  synthesised fixture rather than captured evidence, and it is labelled as one,
  because it proves the port's own decoder and not what the device sent.

  **Re-capturing that exchange against the container is open**, and an earlier
  position in this design had it closed. The premise was right and the
  conclusion wrong: stock Samba has no setting that refuses
  `SMB_COM_TRANSACTION` while still serving the share, but the trigger is
  client-side rather than server-side. A deliberately mis-spelled transaction
  `Name` produces exactly that behaviour, which is what `spikes/capture-trans/`
  is — the container refusing every transaction while serving the share over
  `WRITE_ANDX`/`READ_ANDX` regardless. A session that wants captured frames for
  this path therefore takes that route rather than performing a scrub it does
  not need. The synthesised fixture stays either way: it carries a second
  server's shape, which the container cannot produce. That is worth keeping
  because the RPC share enumeration is the largest piece of hand-written work in
  the port, and no tested server forces the write/read fallback in ordinary use
  at all: all three answer the transact mode (see Wire layer), so a fixture is
  the only thing that can exercise it.
- **The live coverage of that work is the reverse of what the corpus suggests,
  and the fixtures are load-bearing because of it.** The captures were taken by
  a client the container refuses, so every one of them exercises the write/read
  fallback — which reads as though the fallback were the well-trodden path. A
  correct client inverts it completely: the container answers RAP, so share
  enumeration stops there and **neither DCE/RPC transport runs at all**, nor the
  fallback between them. Measured, not inferred: with RAP bypassed the container
  also answers the transact mode outright (`spikes/capture-nmpipe/`), so even
  the second transport never yields to the third. Everything below
  `Client::list_shares`'s first attempt is therefore unreached in CI, and
  `spikes/capture-trans/`, `spikes/capture-nmpipe/` and
  `spikes/srvsvc-synthesised/` are the whole of what stands behind it.
- **Fixtures carry no credential material and no real content.** Session-setup
  frames are excluded from the corpus; the evidentiary value lives in the
  negotiate and transaction frames. Captures are **not** templated for host and
  port: the committed frames carry the capture relay's own loopback address and
  ephemeral port literally — the tree connects read `\\127.0.0.1:10451\IPC$`,
  `:10452` and `:10453`, and `\\127.0.0.1\TESTSHARE` — so a test comparing
  request bytes has to substitute them before it compares, which is one more
  reason the client-to-server assertions are decode-then-re-encode rather than
  byte-identity (see What cannot gate a release, and what covers it instead).
  The rule covers content as well as secrets, which is what `.gitignore` already
  assumes in excluding captures "taken against real devices rather than the
  synthetic container" because "they carry that device's actual directory
  contents": a frame carrying real share names, filenames or file bytes off
  someone's device is not committed, whatever else it would prove.
- **Four corpora regenerate through the Go harness; the rest are preserved
  rather than re-made.** `spikes/regenerate-fixtures.sh` rebuilds the container,
  seeds it and re-captures `capture/`, `capture-frag/`, `capture-large/` and
  `capture-trans/`, and those only. `capture-rap/` and `capture-rap-ascii/` sit
  outside it deliberately: they are taken by the corrected harness in
  `spikes/rapname/`, whereas this script captures what the reference library as
  it stands puts on the wire, which is the refusal. `srvsvc-synthesised/` is
  built by its own generator and captured from nothing. And there is no Windows
  section: `capture-win-a/`, `capture-win-b/` and `capture-win-frag/` cannot be
  reproduced without the Windows VM and the patched client that took them, so
  they are evidence to be preserved rather than regenerated — which is
  why the digest manifest guarding the copy into the crate repository matters
  more for them than for the four that can be re-made.

  The Go harness is not
  incidental for `capture-frag/`, though not because it chose anything:
  `spikes/fragclient/main.go` builds a bare `smb1.Dialer` carrying only an
  initiator, and the Go client echoes back whatever `MaxBufferSize` the server
  advertised — 16,644 — which is what makes Samba split the replies, as the
  first bullet above sets out. The fragmentation came from that echo. So the
  corpus cannot be re-captured with the port's own defaults at all: a client
  advertising 65,535 has to override the advertisement to reproduce it.
  Regenerating means running that script and its Go client, and the
  port's live coverage of the path is the small-`MaxBufferSize` test named above
  rather than a re-capture.

  **`capture/` does not come back byte-identical, and never did.** The committed
  `capture/0010-s2c-cmd32.bin` is a root listing holding `alpha.txt`,
  `gamma-longer-name.dat`, `subdir` and `beta.bin` and **no** `bigdir` — its
  `client.out` agrees — so that corpus was taken before the `bigdir` seeding step
  came to run ahead of the baseline, and a run today legitimately produces a
  larger frame there. The mismatch is pre-existing and it was deliberately not
  re-baselined, because this document cites measurements read off that corpus as
  it stands. Anyone who re-runs the script and diffs is seeing that, not a
  regression.
- **`auth/` is covered by published vectors, not by captures.** Session-setup
  frames are excluded by the rule above, and they are the only place NTLM and
  SPNEGO appear on the wire, so those two modules can have no captured coverage
  of their own. The [MS-NLMP] worked examples are committed as vectors instead:
  they fix the nonce and the timestamp, so the expected bytes are reproducible
  exactly; they carry no real credential; and they come from the specification
  rather than from the Go source, which is the same independence the licensing
  rule asks of the implementation itself. They are what CI asserts for `auth/`.
  The behavioural cross-check against the Go library is not a CI job — nothing
  in CI checks out that repository — it is a development-time run performed while
  `auth/` is written, at build order step 3, and its comparisons are committed
  as expected-value vectors, the same arrangement the `smb-fscc`
  cross-validation uses (see Self-maintenance).

### Pinning the acceptance container deliberately is owed work

This is an obligation the implementation has to meet, not a property already in
place. The container definition lives in the Go repository, where the fixture
regeneration script reaches it (`integration/Dockerfile`), and it is pinned
neither way today: it floats on `alpine:3.24` and on whatever `apk add samba`
resolves to. What the port requires is a copy in the crate repository — the
crate's CI checks out the crate and nothing else, so reaching across is not
available to it — pinned by image digest, with the `samba` package pinned to an
exact version rather than floating, and with Dependabot configured **not** to
update it. That removes automation on purpose: the container is the entire
automatic acceptance gate, some distributions build Samba without the SMB1
server, and upstream is actively removing SMB1 server support. An automerged
base-image bump that silently produces a container which no longer speaks NT1
would delete the acceptance oracle rather than fail loudly. There is no consumer
exposure and no advisory pressure, so there is no reason to update it except
deliberately.

## Detailed Implementation

This is a decision record, not an interface specification. It names what is
built, in what order, and the decisions each piece carries. Choices it does not
make are deliberately the implementer's.

The `smb1client` Go library is the reference implementation for every part of
the port except `auth/`, which is written from specification and may consult it
only as a behavioural cross-check (see Licensing).

**That library is being fixed while this port is built, and the pin is what
keeps the two coherent.** Several of the defects this document lists have been
corrected upstream since `b948f59` — the NTLM signing advertisement among them,
which means the reference has adopted this port's own decision and now sends ten
flags where the pin sends eleven. So the list below describes the library **at
the pinned commit** and nothing later, and a differential run against a working
tree that has moved will disagree with it for reasons that are not the port's.
Pin the harness to `b948f59`, or update this document and the harness together. Acceptance Criteria
enumerates the twenty-one behaviours where it is not the reference at all — for
each of those the suite asserts the correct result instead.

**That library holds two client implementations, and the oracle is the
top-level one** — the `smb1.Dialer`/`Session` path in `session.go` — not
`internal/client`. Two reasons, and neither is a preference: it is what every
spike in this campaign drove (`spikes/*/main.go` all construct a bare
`smb1.Dialer`), so it is the path behind every capture in the corpus and every
measurement this design cites; and it is the only one a differential harness can
call at all, `internal/` being unimportable from outside that module. The paired
citations throughout this document are the same behaviour located on both
implementations; where they diverge, the top-level path is the one being ported
and the other is context.

**Six notes in that repository are unreachable from a clone.** They are
git-excluded, so they appear in no history. Nothing here rests on them: every
claim this design draws from one of the six also carries a `file:line` into
committed Go source, a fixture, or its own full statement in this document. The
findings note that principle 1 names is background rather than a prerequisite
even so, and
its own first finding — clamp transaction sizes to the negotiated
`MaxBufferSize` — is one this design measured wrong.

**Two committed documents in that repository are worth reading first.**
`ARCHITECTURE.md` (619 lines) maps the package tree, which is the quickest way
to find which Go file answers a given question and which package carries the
go-smb2 provenance (see Licensing). `ERRORS.md` (831 lines) sets out the
error-wrapping and classification conventions that `Error::kind()` replaces
wholesale (see Public API → Errors).

### Build order

Each step is testable before the next begins, and the order is chosen so that
the pieces most likely to be wrong are provable earliest. Which of the Go
library's own tests a step can draw on, and which are dropped, is settled under
Where the Go library is the oracle, and where it is not.

**One piece precedes the numbered steps and belongs to none of them: the
[MS-ERREF] scraper that generates `status.rs`.** Generating the status table
from the specification rather than transforming the Go source's is a licensing
decision, and what it costs is a scraper written against the shape the MS-Learn
page actually has, the Go generator's own DOM assumptions no longer holding
(see Public API → Errors). Nothing that names a status can be written until the
table exists, so it is written first. It is owed work in the same register as
the unpinned acceptance container, and it is not
a small task: a scraper, the generator behind it, and the committed table they
produce, all before `status.rs` compiles.

1. **`wire/` against the committed fixtures**, offline, no network. Header,
   negotiate, and the transaction encoders including the offset helper, whose
   padding is pinned here against fixture bytes (see Wire layer). The
   large-read, large-write and `SMB_COM_TRANSACTION` fixtures are what this step
   turns on: a codec trusting `ByteCount` must fail before anything is built on
   it, and without them the step could exercise neither `WRITE_ANDX` nor
   `SMB_COM_TRANSACTION` and the RAP request on it (see Fixture obligations).
   For client-to-server
   messages the assertion is decode-then-re-encode rather than byte-identity
   against a fresh encode, the header's own `Flags2` being one of the deliberate
   departures (see What cannot gate a release, and what covers it instead).
2. **`connection/` over the test seam**, still offline. Reassembly, admission —
   which is where the backpressure is — and the request states, including a
   multiplex ID held through Orphaned and Lapsed and returned to the pool on
   Done — or retired instead, when a Lapsed request is given up on and whenever
   an arrival ends a request in any state without completing it — are proven
   against a fake transport. Invariants 1, 2 and 3 are
   discharged here — they cannot be discharged later, because no live server
   exercises them. The Invariants section names the test each one needs.
3. **`auth/`**, then a live connect to the Samba container: negotiate and
   session setup run to completion on the dialled socket, and the result is
   handed to the actor built in step 2 (see Connection architecture). First
   point at which anything talks to a real server. The handshake's four
   refusals — the capability floor, `NEGOTIATE_USER_SECURITY`, the
   `MaxBufferSize` floor and the guest
   logon — are proven here over scripted responses on the seam rather than
   against the container, which can produce none of them (see What fixtures
   cannot prove, and what covers it).
4. **`session.rs` / `tree.rs` / `resource/`**, differentially tested against the
   Go library on the container. That differential run is development-time, not a
   CI job — nothing in CI checks out the Go repository — so its comparisons are
   committed as expected-value vectors and those are what CI asserts, the same
   arrangement `auth/` uses at step 3 (see Fixture obligations).
   **Chunk size is where that run will disagree with Go without either side
   being the reference.** Go's sequential paths clamp to `MaxBufferSize − 1024`
   (`internal/client/file.go:233`, `:662`) while neither of its pipelined paths
   consults the negotiated buffer at all: `writePipelined` hardcodes 130,048
   (`internal/client/file.go:700`), and `readPipelined` starts from the same
   flat 65,520 the sequential read does and raises it to 130,048 only under
   `CAP_LARGE_READX` (`:274`, `:275-277`). So Go's chunk size turns on which
   side of its own 128 KiB / 256 KiB pipelining threshold a request falls. The port
   sizes chunks by one rule whatever the size of the transfer (see Sizing
   transactions), so it necessarily differs from Go on one side of that
   threshold: the disagreement is the Go library's inconsistency, and it is
   read that way rather than as a finding against the port (see Where the Go
   library is the oracle, and where it is not).
   Invariant 4 is discharged here rather than at step 2: its test needs the
   same fake transport, but `write_all_at` does not exist until this step.
5. **`rpc/`**, whose only fixture is the synthesised one (see Fixture
   obligations).
6. **`client.rs`**, the caching and reconnection layer, last: it is the only part
   whose failure mode needs a connection that can already work.

### Ported deliberately, not rediscovered

- Transaction sizing per the measured ceiling, with `MaxParameterCount`
  right-sized (see Sizing transactions). This is the difference between working
  and not working on Windows.
- Multi-message transaction reassembly, in the actor from the start.
- Both directory-chain terminators; and both ways a large listing arrives — one
  reply split across messages (see Routing and reassembly) and one page per
  round with FIND_NEXT2 continuing it (see Public API → Directory listing). The
  second is not a Windows trait: the patched client that took the Windows
  captures asked for `MaxDataCount = 4000`, which is why they page in small
  rounds. Paging is required of any server at 600 entries and a batch size of
  100, so a port that
  implements only reassembly, or only paging, is incomplete against both.
- Closing a search on both paths: `SMB_FIND_CLOSE_AT_EOS` on every FIND_NEXT2 as
  well as on the FIND_FIRST2, and `SMB_COM_FIND_CLOSE2` on a listing dropped
  before end-of-stream (see Handle lifetime).
- UNC construction from the host alone, one path for every use.
- `NTLMSSP_NEGOTIATE_SIGN` retained, `ALWAYS_SIGN` and
  `NTLMSSP_NEGOTIATE_VERSION` dropped.

## Implementation handoff

This section orients an implementation session. Everything it points at is
specified above; what it adds is the things a fresh session cannot see from the
document alone.

**The crate is built in a different repository from the design.** This one holds
the crate. The evidence repository holds the design record this file is a copy
of, together with the spike log, the design-prep brief and the wire-fixture
corpus the citations below name. The fixtures this design makes mandatory are
copied in here as test data, since this test suite cannot reach across to that
repository — and a digest manifest committed on both sides is what says the two
corpora still agree.

**The Go reference is pinned at `b948f59`.** Every `file:line` citation in this
document resolves there and will drift from any later commit. That repository
also holds root-level and `internal/` files of the same name, so a bare
`file.go` or `session.go` in a citation means the root-level one.

**Six notes in the Go repository are git-excluded and unreachable from a
clone.** Every claim this document draws from them is restated here or backed
by something reachable, so the design does not depend on them — but a session
that goes looking for them in a clone will not find them, and their contents
are the Go library's owed work rather than this port's.

**Nothing compiles until the status table exists.** The [MS-ERREF] scraper that
generates `status.rs` precedes the numbered build order and belongs to none of
its steps: a scraper, the generator behind it, and the committed table they
produce. It is not a small task, and the Go library's equivalent generator
cannot be reused — it is go-smb2-derived, which is the whole reason this table
is regenerated rather than transformed, and it is broken besides, since the MSDN
page it scrapes has moved and changed shape.

**The three fixtures this design called owed now exist.**
`spikes/capture-large/` carries the `WRITE_ANDX` frame,
`spikes/capture-trans/` the `SMB_COM_TRANSACTION` frame and the RAP parameter
block on it, and `spikes/srvsvc-synthesised/` the DCE/RPC exchange. With them
every one of the four offset back-patching sites has an offline oracle, and the
RAP encoder that rides on the transaction has one where it had none. What is
left is not to lose them: Fixture obligations says what each is for and what a
re-capture has to preserve.

**Two wire paths have no offline oracle of any kind**, and they are the
highest risk in the build: `SMB_COM_FIND_CLOSE2` and `SMB_COM_ECHO`, both
written from specification with nothing in the repository to check them against.
An earlier position in this design counted four, and the other two were closed
rather than argued away. RAP `NetShareEnum` is pinned on both sides:
`spikes/capture-rap/` carries a request and its successful reply, and
`spikes/capture-win-rap/` carries the request in the shape the port actually
sends it, `SetupCount = 0` included, which the first does not. The DCE/RPC
`NetrShareEnum` encoding has four oracles rather than none, and they are not
interchangeable. `spikes/capture-trans/` carries the whole exchange over the
write/read mode against the container — bind, `bind_ack`, request and response,
each a single PDU carrying `PFC_FIRST | PFC_LAST` — and
`spikes/srvsvc-synthesised/` carries that same mode in the embedded device's
shape. Neither reaches the **transact** mode, which this design also has the
port implementing: its request carries a `Name`, its setup words, and a
`DataOffset` displaced by the name's pad byte, none of which a write/read
capture pins. Two fixtures do: `spikes/capture-nmpipe/` against the container
and `spikes/capture-win-nmpipe/` against Windows, each carrying two
transact-mode calls answered `STATUS_SUCCESS`. Of those four oracles only
`spikes/capture-trans/` was taken by the reference library, which is what makes
it evidence of that library's own defects; the two transact corpora came from a
corrected harness and `spikes/srvsvc-synthesised/` from a generator, so those
three are evidence about a server rather than about what the reference sends
(see Fixture obligations). What no fixture reaches is
the multi-PDU assembly the design requires, every committed response being a
single fragment. `SMB_COM_FIND_CLOSE2` deserves the most care of the two:
it sits on the path that closes every dropped listing, and the leak it exists to
prevent is the defect that makes the reference library unable to delete a
directory of more than a hundred entries.

**Some choices are deliberately left open.** Error-variant names, fuzz targets
beyond the four this document names, the representation of the request table,
and the order in which multiplex IDs are handed out are the implementer's, and
this document says so where each arises. Do not read those silences as gaps.

**Where a decision turns out wrong, revise this document rather than working
around it.** The deviation protocol in `/egm-implement` governs: a design that
survives contact with the compiler unchanged is unusual, and the value of this
one is that it records why each choice was made, which is what makes a departure
legible. Several decisions here are reasoned from the protocol's shape rather
than measured — the `SMB_COM_ECHO` header values and byte area, the two dropped
NTLM flags, the permissive `ShareAccess`, and a `DesiredAccess` without
`SYNCHRONIZE`. All of them are on the conformance script, and all of them are
the kind of thing a real server may simply refuse.

**What the gates did and did not establish.** This document went through the
Goldfish gates and did not reach a clean pass; it reached zero critical findings
with five majors outstanding, which were then closed. Every fixture claim it
makes was decoded and verified byte for byte, every arithmetic and count claim
recomputed, and the Go citations checked against `b948f59`. What that leaves is
a specific residual risk worth carrying into implementation: four consecutive
review rounds each introduced a defect by fixing something elsewhere — an edit
that read correctly in place while contradicting a passage two hundred lines
away. Two of the last five majors were exactly that. Where this document
contradicts itself, the more specific passage is likelier to be right than the
summary, and the contradiction is worth reporting rather than resolving silently.

## Deferred and out of scope

1. **Deferred** — **P3.** Implement SMB1 message signing, or state its absence as a bounded non-goal? Evidence weakens the case for implementing: Windows with signing required accepted NTLMv2 auth and a tree connect from an entirely unsigned client.
   _Reason: The operator deferred it as follow-up work rather than part of this design. Evidence supports the deferral: Windows 11 24H2 with `RequireSecuritySignature=True` accepted NTLMv2 authentication and a tree connect from an entirely unsigned client, so no tested server actually requires it._
2. **Deferred** — **Independent dissector as a second oracle.** The campaign validated its fixture corpus by agreement between a seeded ground truth, the Go library, and tshark's independently-authored SMB1 dissector (finding C5).    _Reason: Deferred rather than rejected, with the residual stated in Acceptance Criteria: a misreading of the wire format shared by the fixtures, the Go library and this port would pass every check the design specifies, and the tested servers reduce that risk without removing it. 3. **Deferred** — **Publishing to crates.io.** The crate is written as a publishable one and the registry mechanism is specified. Should it actually be published?
